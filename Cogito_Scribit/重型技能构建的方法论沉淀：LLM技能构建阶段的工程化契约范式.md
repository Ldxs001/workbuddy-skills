# 重型技能构建的方法论沉淀：LLM技能构建阶段的工程化契约范式

> 这是方法论的第一篇（抑制LLM执行偏差的硬中断架构）的配套维度。第一篇回答了"运行时如何阻断偏差"，第二篇回答"构建时如何让运行侧的阻断有参照标准"。两篇共同构成一个完整的工程闭环。

---

## 两篇的关系

|  | 第一篇（运行时） | 第二篇（构建时） |
|---|------------|------------|
| **核心问题** | 执行过程中LLM偏离预期 | 构建阶段缺乏统一规范 |
| **核心机制** | 硬中断（阻断进程、挂起、恢复） | 强制契约（五层结构声明） |
| **作用时机** | 技能运行阶段 | 技能构建阶段 |
| **依赖关系** | 依赖构建侧提供"什么是对的"的参照 | 依赖运行侧校验契约是否被遵守 |
| **共同目标** | **把LLM的活动空间压缩到"填空题/选择题"的狭窄闸口内** | **让硬中断有据可依** |

**一句话概括闭环：**

> 构建时用五层契约锁定每个技能的"正确形态"，运行时用硬中断拦截任何偏离该形态的行为。前者给后者提供判断标准，后者让前者不至于沦为空文。


## 一、构建侧要解决的三个问题

第一篇留下了一个缺口：硬中断机制在运行时检查格式、路径、状态、时序，但它是怎么知道"什么是对的"的？

答案是：**它需要技能在构建时就提供结构化的声明。** 如同编译器需要有类型声明才能检查类型错误。

在受限框架下构建多个技能时，会反复遇到以下三个问题，它们本质上是同一类问题：

**第一个问题：不同人产出的技能结构不一致。**

开发者A习惯把配置放在`config.yaml`，开发者B习惯放在`settings.json`。同一个人今天写的技能和三个月前写的也可能不同。没有统一规范时，N个技能就有N种结构，维护成本非线性增加。

**第二个问题：上层调度器无法用统一方式识别技能接口。**

技能的配置入口、管理命令、执行参数各不相同，调度器要为每个技能单独适配。新增一个技能就需要新增一段适配代码。

**第三个问题：执行侧的硬中断没有判断依据。**

"检查输出格式"——但格式是什么？"检查数据路径"——但路径在哪里？这些信息必须在构建阶段就定义好，运行侧才能执行检查。

这三个问题的共同根源是**构建阶段缺乏强制性的结构规范**。


## 二、核心机制：构建时契约

### 2.1 什么是"构建时契约"

构建时契约是一组在技能构建阶段就确定并固定的结构化声明。它在技能运行前就已经存在，运行期间不改变。

它回答以下五个问题：

1. **你是谁**：技能的标识、版本、责任人
2. **什么时候用你**：触发条件、否定条件
3. **用你的时候什么不能做**：行为边界、强制约束
4. **怎么跟你交互**：配置入口、管理入口、执行入口
5. **你的数据放哪**：状态文件、产物目录、日志位置

### 2.2 契约的五个层次（为什么是五层）

实践中发现，上述五个问题自然独立，每个问题的答案不依赖其他问题的答案，且任何一层缺失都会导致"完整性"不足。少于五层会有信息缺失，多于五层会有重叠。

| 层 | 回答的问题 | 缺失后果 |
|---|-----------|---------|
| L1：身份声明 | 你是谁、什么版本 | 无法识别和追踪技能 |
| L2：触发与能力声明 | 什么时候用你 | 不知道何时调用 |
| L3：行为约束声明 | 用你时什么不能做 | 运行时无判断标准 |
| L4：接口声明 | 怎么跟你交互 | 无法统一调度 |
| L5：数据声明 | 你的数据放哪 | 无法统一管理产物 |

### 2.3 契约如何被实施

契约不是写在文档里的建议，而是被两个机制强制实施的：

**机制一：接入校验**

任何技能在接入系统前，必须通过五层契约的完整性校验。不完整则拒绝接入。校验是静态的，不依赖运行时。

**机制二：运行时对照**

技能执行过程中，第一篇的硬中断机制会对照契约进行检查——声明了输出格式，就检查输出格式；声明了数据路径，就检查数据路径。


## 三、逐层定义

### 3.1 L1：身份声明

**要回答的问题**：
- 这个技能叫什么名字？（与目录名一致）
- 当前是什么版本？（语义化版本）
- 谁负责维护？
- 使用什么协议？
- 它的数据存放在哪里？
- 什么词能触发它？（至少3个正向触发词）
- 什么条件下不应该触发它？

**为什么这些信息必须声明**：
- 没有名称，系统无法标识技能
- 没有版本，无法追踪演进和回滚
- 没有数据位置，运行时的产物无处存放
- 没有触发词，不知道何时调用

**关键约束**：
- 版本号必须在三个位置同步——入口文件、元数据文件、更新日志的最新一条记录
- 触发词至少3条，且必须有实际语义（"制作PPT"而不只是"制作"）
- 数据目录必须指向外部位置，不能指向技能内部

**校验方式**：静态读取+比对，不依赖运行时。

### 3.2 L2：触发与能力声明

**要回答的问题**：
- 什么情况下应该调用这个技能？（正向触发）
- 什么情况下不应该调用这个技能？（否定条件）
- 这个技能提供哪些能力？（能力列表）

**为什么触发条件必须区分正反**：
- 正向条件让系统知道"什么时候该用"
- 否定条件让系统知道"什么时候不该用"，避免误调用

**为什么能力必须与触发对应**：
- 触发词是用户的语言，能力是系统的语言
- 需要将用户的触发词映射到系统的具体动作
- 映射表由技能声明提供，不在调度层硬编码

### 3.3 L3：行为约束声明

**要回答的问题**：
- 执行过程中的红线是什么？
- 哪些步骤是强制顺序的？
- 失败重试的上限是多少？
- 空转多少次必须停止？

**约束的分级**：

约束分为两个级别，对应两种不同的执行方式：

| 级别 | 含义 | 执行方式 |
|------|------|---------|
| 硬约束 | 不能违反，违反则中断 | 由代码强制执行（对应第一篇的硬中断机制） |
| 软约束 | 建议遵守，但违反不一定中断 | 由LLM自觉遵守 |

**为什么需要硬约束**：
- 对应第一篇的硬中断机制——运行侧需要有"什么是越界"的判断标准
- 至少3条硬约束，否则技能与纯Prompt工程无异

**约束的设计原则**：
- 硬约束必须指向可校验的状态（"文件存在""格式符合""步骤已完成"）
- 软约束虽然不强制执行，但仍需明确定义，避免LLM不知道边界在哪里

### 3.4 L4：接口声明

**要回答的问题**：
- 如何配置这个技能？（配置入口）
- 如何管理这个技能的数据？（管理入口）
- 如何执行这个技能的核心功能？（执行入口）

**三个标准化入口**：

技能必须提供三个标准化的交互入口，对应三种交互场景：

| 入口 | 交互场景 | 必须支持的操作 |
|------|---------|--------------|
| 配置入口 | 查看/修改运行时参数 | 展示配置、修改配置、保存配置 |
| 管理入口 | CRUD技能管理的实体 | list、show、create、delete |
| 执行入口 | 执行核心功能 | 带参数执行、试运行（--dry-run）|

**为什么需要试运行（--dry-run）**：
- LLM任务往往有副作用（写文件、调接口）
- 试运行让LLM和用户在执行前看到执行计划
- 降低误操作成本

### 3.5 L5：数据声明

**要回答的问题**：
- 运行状态存在哪里？
- 执行产物存在哪里？
- 日志存在哪里？
- 锁文件怎么管理？

**为什么数据必须集中管理**：
- 技能可能被重新部署，内部数据会丢失
- 多个技能的数据需要统一清理、备份
- 第一篇的硬中断机制需要检查产出物，需要知道产出物的位置

**数据目录的固定结构**：

```
{data_dir}/
├── .state.json      # 运行状态（脚本维护，不可手工编辑）
├── .lock            # 锁文件（running/blocked）
├── .remaining.json  # 阻断时的问题清单
├── outputs/         # 最终产物
├── logs/            # 运行日志
└── temp/            # 临时文件
```

**状态文件的脚本化操作**：
- 状态文件不能手工编辑，只能通过脚本操作（init、update、complete）
- 这保证了状态变更的可追溯性
- 也避免了手工编辑导致的状态不一致


## 四、契约的强制力来源

### 4.1 它是通过什么方式强制实施的

契约的强制力来自**接入校验**：

任何技能在进入系统之前，必须通过五层契约的自动校验。校验不通过则拒绝加载。

校验是静态的——它只检查"是否声明了必要信息"和"声明是否一致"，不检查"声明是否正确"。

校验不修改技能。它只输出PASS/FAIL报告，指出具体问题位置。

### 4.2 契约和第一篇硬中断的关系

|  | 第一篇（硬中断） | 第二篇（契约） |
|---|-------------|-----------|
| 作用 | 运行时检查 | 构建时声明 |
| 问题 | "怎么知道执行偏离了预期" | "怎么让系统知道什么是预期" |
| 答案 | 对照契约检查格式/路径/状态 | 在构建时声明格式/路径/状态 |
| 关系 | 依赖第二篇的声明 | 为第一篇提供判断标准 |

**没有第二篇的契约，第一篇的硬中断没有参照标准。**
**没有第一篇的硬中断，第二篇的契约只是一纸空文。**

两者共同构成完整的闭环。

### 4.3 契约本身的质量如何保证

契约的"五层"结构本身是可校验的：
- L1的完整性可以检查（字段是否都存在、版本是否同步）
- L2的触发条件可以检查（数量是否≥3、是否有否定条件）
- L3的约束可以检查（数量≥5、硬约束≥3、硬约束有代码实现）
- L4的接口可以检查（三个入口是否存在、是否支持必要操作）
- L5的数据结构可以检查（目录是否存在、状态文件是否可创建）

这种"自举"式的设计——契约本身可以被校验契约的规则所检查——保证了五层契约不会变质。


## 五、控制循环：两篇方法论如何协同运作

### 5.1 闭环的完整步骤

前面分别描述了构建时契约（第二篇）和运行时硬中断（第一篇），但**它们之间的协同方式**才是这套方法论能否成立的关键。

完整控制循环如下：

```
【构建阶段】
    开发者创建技能
        ↓
    按照五层契约填充结构声明
        ↓
    接入校验（自动执行）
        ├─ L1-L5全部完整 → 继续
        └─ 任何一层不完整 → 拒绝接入，返回修复指引
        ↓
    技能接入系统，契约被持久化存储
    ↓
【执行阶段】
    上层系统调度技能
        ↓
    系统读取技能的契约声明（全部五层）
        ↓
    按契约中的触发条件（L2）确认是否应该调用
        ↓
    按契约中的步骤顺序开始执行
        ↓
    ┌─────────────────────────────────────────────┐
    │  【每步执行循环】                           │
    │                                              │
    │  步骤N开始前：                              │
    │    检查上一步的状态（L3硬约束）             │
    │    └─ 上一步已完成 → 继续                   │
    │    └─ 上一步未REVIEW → 触发中断            │
    │                                              │
    │  执行步骤N                                  │
    │                                              │
    │  步骤N完成后：                              │
    │    检查产出物格式（L3硬约束）               │
    │    └─ 符合声明格式 → 继续                   │
    │    └─ 不符合声明格式 → 触发中断             │
    │                                              │
    │    检查数据位置（L5数据声明）               │
    │    └─ 在声明的data_dir内 → 继续            │
    │    └─ 在data_dir外 → 触发中断              │
    │                                              │
    │    推进前检查：                              │
    │      重试计数是否≥3（L3硬约束）             │
    │      └─ <3 → 继续                          │
    │      └─ ≥3 → 触发中断                     │
    │                                              │
    │      空转计数是否≥3（L3硬约束）             │
    │      └─ <3 → 继续                          │
    │      └─ ≥3 → 触发中断                     │
    │                                              │
    └─────────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────────┐
    │  【硬中断触发时】                          │
    │                                              │
    │  写入锁文件（含阻断位置、原因、上下文）     │
    │  输出阻断信号到stderr（不被管道过滤）       │
    │  输出阻断信号到stdout（双重保障）           │
    │  进程退出，退出码=2                        │
    │                                              │
    └─────────────────────────────────────────────┘
        ↓
    ┌─────────────────────────────────────────────┐
    │  【恢复阶段】                              │
    │                                              │
    │  外部（开发者/上层调度器）读取锁文件        │
    │  修复问题                                   │
    │  传入--continue参数重新执行                 │
    │  系统读取锁文件，跳过已完成步骤             │
    │  从阻断点继续执行                          │
    │                                              │
    └─────────────────────────────────────────────┘
        ↓
    （回到"每步执行循环"，直到全部完成）
        ↓
    全部步骤完成 → 清理锁文件 → 任务结束
```

### 5.2 两篇方法论的职责分工

|  | 第二篇（契约） | 第一篇（硬中断） |
|---|-------------|----------------|
| **作用阶段** | 构建时 | 运行时 |
| **核心动作** | 声明、校验、存储 | 读取、对照、拦截 |
| **产出** | 技能的"规格说明书" | 阻断信号+锁文件 |
| **判断依据** | 结构是否完整 | 执行是否偏离契约 |
| **失败后果** | 技能无法接入系统 | 技能中断执行 |
| **修复方式** | 补齐缺失的声明 | 修复偏离的行为 |

**两者的关系不是"先后"，而是"互相依赖"：**

- 没有第二篇的契约，第一篇的硬中断没有参照标准——"我检查什么？"
- 没有第一篇的硬中断，第二篇的契约只是一纸空文——"你不检查我违反了又怎样？"

### 5.3 关键映射表：契约层 ↔ 硬中断检查点

五层契约中的具体声明，直接对应到第一篇硬中断机制中的具体检查点：

| 契约中的声明 | 对应硬中断检查点 | 触发条件 |
|-------------|----------------|---------|
| L3硬约束"上一步必须REVIEW才能执行下一步" | `hook_pre_execute()` | 发现上一步未标记REVIEW |
| L3硬约束"产出物必须符合声明格式" | `hook_post_execute()` | 产出物格式校验失败 |
| L3硬约束"重试不超过3次" | `hook_pre_advance()` | retry_count ≥ 3 |
| L3硬约束"空转不超过3次" | `hook_pre_advance()` | idle_count ≥ 3 |
| L5数据声明"数据存放在data_dir" | 路径检查 | 发现文件写入data_dir之外 |
| L5状态声明"状态通过脚本变更" | 状态检查 | 发现状态文件被手工编辑 |

**这个映射表说明**：第一篇的硬中断机制不是凭空检查，而是逐条对照第二篇契约中的声明来执行检查。

### 5.4 闭环形成的条件

两篇方法论形成闭环，需要满足三个条件：

**条件一：契约在构建时被完整声明**

技能接入系统时，L1-L5的声明必须全部存在且通过校验。不能"先接入后补声明"。

**条件二：契约在执行时可被读取**

系统在执行技能时，能读取到该技能的完整契约声明。契约存储在技能的元数据中，与技能代码一起部署。

**条件三：硬中断检查点覆盖契约声明**

每个L3硬约束和L5数据声明，都有对应的硬中断检查点。如果某个硬约束没有对应的检查点，它实际上只是个"空声明"。

### 5.5 当闭环失效时会发生什么

| 失效场景 | 后果 | 如何预防 |
|---------|------|---------|
| 契约声明了格式但无检查点 | 格式错误不会被发现 | L3校验时检查"硬约束是否有实现" |
| 契约检查点存在但未读取契约 | 检查的是硬编码值，不是实际声明 | 系统设计时强制先读契约再执行 |
| 契约接入时完整但执行前被修改 | 执行时读到的是旧契约 | 契约写死在技能元数据中，运行时只读 |
| 硬中断触发了但锁文件写入失败 | 无法恢复，需从头重跑 | L5数据声明中必须有.lock文件路径 |

### 5.6 闭环的工程验证方式

验证闭环是否生效，可以通过以下方式：

1. **单元测试**：模拟一个偏离契约的步骤，验证硬中断是否被触发
2. **端到端测试**：完整执行一个技能，验证所有检查点是否都被触发过
3. **审计日志**：检查系统日志中是否有"检查点X已触发"的记录
4. **契约覆盖度报告**：统计契约中的硬约束被检查点覆盖的比例

当一个技能的契约覆盖度达到100%（所有硬约束都有对应的检查点），且所有检查点在实际执行中都被触发验证过，这个闭环就"跑通了"。


## 六、边界

### 6.1 这套契约能解决的问题

- 多个技能结构不一致 → 五层统一
- 上层调度器无法识别技能接口 → L4统一
- 运行时硬中断没有判断标准 → L3提供行为边界
- 版本混乱无法追踪 → L1强制版本同步
- 数据散落无法清理 → L5统一数据位置

### 6.2 这套契约不能解决的问题

- 技能内容本身的正确性（只约束结构，不约束语义）
- 技能之间的依赖管理（跨技能编排的范畴）
- 技能的运行时性能（执行引擎的范畴）
- 技能的故障恢复（第一篇硬中断的范畴，但契约是它的前提）

### 6.3 适用前提

- 存在一个受限框架，框架提供了运行环境但不提供结构规范
- 需要维护多个技能，需要统一管理
- 有自动化的校验工具（或能实现这样的工具）


## 七、总结

### 7.1 一句话概括

**构建时用五层契约锁定结构，运行时用硬中断拦截偏离。前者给后者提供判断标准，后者让前者不至于沦为空文。**

### 7.2 五层对应五个"时点"

| 层 | 对应时点 | 解决的问题 |
|---|---------|----------|
| L1 | 发现技能时 | 能不能识别它 |
| L2 | 决定调用时 | 该不该用它 |
| L3 | 执行过程中 | 它越界了没 |
| L4 | 交互时 | 怎么跟它对话 |
| L5 | 管理数据时 | 它的数据在哪 |

### 7.3 两篇方法论的完整关系图

```
【构建阶段】
    开发者按照五层契约构建技能
        ↓
    契约被自动校验
        ↓
    通过校验 → 接入系统
        ↓
【运行阶段】
    技能被调度执行
        ↓
    硬中断机制对照契约检查每一步
        ↓
    偏离契约 → 阻断进程 → 挂起 → 等待修复后恢复
        ↓
    全部通过 → 任务完成
        ↓
【反馈循环】
    阻断时暴露的问题 → 回溯到契约定义不完善处 → 调整契约
```
