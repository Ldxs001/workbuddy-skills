# 重型技能构建的方法论沉淀：技能流水线编排范式

> 从"LLM 当大脑"到"技能是积木，编排是图纸"——用 Pipeline Orchestration 替代 ReAct 的架构范式。
> 更新：2026-07-06

---

## 一、背景：ReAct 的瓶颈

### 1.1 ReAct 循环的隐形成本

ReAct（Reasoning + Acting）循环是 LLM Agent 的主流架构：

```
LLM 思考 → LLM 决定行动 → 执行工具 → 观察结果 → LLM 再次思考 → ...
```

在技能数量较少（<5个）时，这个模式工作良好。但当技能数量增长到 20+ 个，问题显现：

| 问题 | 表现 | 根因 |
|------|------|------|
| **决策抖动** | 同样的任务每次走不同的技能路径 | LLM 是概率模型，每次推理的路径选择不同 |
| **循环失控** | LLM 在 2-3 个步骤间反复横跳 | ReAct 没有天然的终止条件 |
| **状态膨胀** | 上下文窗口中塞满历史观察 | 每一步的观察都累积，但大部分对后续无用 |
| **技能遗忘** | LLM 知道有某个技能但实际没用 | 技能列表太长 > LLM 的注意力窗口 |
| **不可复现** | 相同的输入可能得到完全不同的执行路径 | 概率生成 × 多次决策 = 结果不可控 |

### 1.2 "LLM 当大脑"的根本问题

ReAct 的隐含假设是：**LLM 应该理解整个任务并在每一步做出最佳决策**。

但这个假设在重型技能生态中不成立：

- LLM 无法同时掌握 20+ 个技能的接口细节
- LLM 的"计划"和"执行"没有硬性分离——它在执行时还能改计划
- 技能间的数据流转依赖 LLM 的"直觉"而非接口契约

## 二、核心命题

> **在多技能编排场景中，LLM 的角色应该从"大脑"降级为"胶水"——只做格式转换，不做路径决策。**

编排路径由用户（或固化算法）在**执行前**确定，LLM 只在每个步骤的**输入/输出边界**上做精确的格式转换。

### 2.1 基本判断

| 维度 | ReAct 范式 | Pipeline 编排范式 |
|------|-----------|-----------------|
| **决策时机** | 执行中动态决策 | 执行前静态确定 |
| **LLM 角色** | 大脑（思考+决策+执行） | 胶水（格式转换+内容生成） |
| **技能关系** | LLM 决定调用顺序 | 用户/算法决定顺序 |
| **可复现性** | 低（概率路径） | 高（确定路径） |
| **状态管理** | 隐式（上下文窗口） | 显式（Pipeline JSON） |
| **失败隔离** | 难（一步失败污染全局状态） | 易（步骤间通过 FILE marker 传递） |

### 2.2 核心命题的分解

**命题 A：确定性路径优先于智能路径**
- 用户手动编排的流水线总是优于 LLM 动态选择的路径
- 固化算法（skill-sub 优化）优于 LLM 优化
- LLM 只在确定性框架的"填空"处发挥作用

**命题 B：技能接口是契约，不需要 LLM 理解**
- 每个技能的输入/输出由 SKILL.md 定义
- LLM 不需要"理解"技能做了什么，只需要按格式转换
- 粘合层（_llm_glue）是唯一的 LLM 介入点

**命题 C：固化 > 调用**
- 确定性逻辑（依赖分析/颜色校验/文件操作/HTML 检查）不应调用 LLM
- 只有需要语义理解的地方（格式转换/内容生成）才用 LLM
- 固化功能越多，系统越稳定

## 三、架构范式

### 3.1 三层分离

```
┌─────────────────────────────────────────────────┐
│  规划层（蓝图）                                   │
│  用户编排 / 固化算法优化 / 语义拆分               │
│  输出: Pipeline JSON                            │
├─────────────────────────────────────────────────┤
│  执行层（引擎）                                   │
│  遍历 Pipeline 节点 / 粘合 / 脚本或 LLM 执行      │
│  输出: 步骤结果                                   │
├─────────────────────────────────────────────────┤
│  审查层（自检）                                   │
│  HTML 校验 / 颜色检查 / LLM 深度审查 / 重试       │
│  输出: 通过/不通过 + 反馈                          │
└─────────────────────────────────────────────────┘
```

**关键原则：每一层只能做自己层的事。**
- 规划层不做执行，执行层不做规划
- 审查层不修改内容，只返回通过/不通过

### 3.2 与 ReAct 的核心区别

| 维度 | ReAct | Pipeline Orchestrator |
|------|-------|----------------------|
| **执行前** | 无计划或模糊计划 | 精确 Pipeline JSON |
| **执行中** | LLM 可随时改计划 | 严格按 nodes 顺序执行 |
| **步骤间** | 隐式上下文传递 | 显式 output → input |
| **失败处理** | LLM 自行决定 | 固化重试策略（max 3 次） |
| **可审查** | 观察 LLM 的思考链 | 固化审查点（格式/颜色/内容） |

## 四、固化 vs 调用的权衡模型

### 4.1 决策树

判断一项能力应该被固化还是调用 LLM：

```
这项能力需要理解语义吗？
├── 是 → 需要外部数据/模型吗？
│      ├── 是 → 调用 LLM（如：格式转换/内容生成）
│      └── 否 → 固化 + LLM 混合（如：语义拆分中的 5W2H 提取用正则，步骤拆分用 LLM）
└── 否 → 可以固化吗？
       ├── 是 → 硬编码（如：颜色对比度计算/文件原子写入/HTML 标签配对）
       └── 否 → 保持外部调用（如：特定领域的专业脚本）
```

### 4.2 本项目的固化决策

| 能力 | 固化/LLM | 理由 |
|------|---------|------|
| 流水线优化（skill-sub） | 固化 | 依赖分析/并行检测是确定图算法 |
| 意图拆分（semantic-split） | 混合 | 5W2H 提取用正则，步骤拆解用 LLM |
| 输出审查（triphasic） | 混合 | HTML/颜色校验用算法，内容深度审查用 LLM |
| 颜色校验 | 固化 | WCAG 公式是确定的 |
| 文件操作 | 固化 | OS 原子操作 |
| Python 自动装包 | 固化 | pip install 是工具调用 |
| HTML 校验 | 固化 | 标签配对是字符串匹配 |

### 4.3 "可选功能"原则

所有增强功能都必须是可选的：

```
Pipeline 执行路径（无增强）：
  预检 → 执行 → 输出
  O(1) 性能，零额外开销

Pipeline 执行路径（全增强）：
  预检 → 语义拆分 → 优化 → 粘合 → 执行 → 审查 → 重试 → 输出
  O(n) 性能，每步增加审查开销
```

不勾选 = 直通执行。这是设计铁律。

## 五、与现有方法论文档的关系

### 5.1 方法论维度映射

| 方法论 | 核心关注 | 代表技能/工具 | 关系 |
|--------|---------|-------------|------|
| **第一篇：运行时硬约束** | 单技能内的 LLM 行为管控 | triphasic-execution | 编排器吸收其执行循环逻辑 |
| **第二篇：构建时契约** | 多技能的结构一致性 | skill-standardization | 编排器依赖契约来识读技能接口 |
| **第三篇：递归自举** | 方法论工具的自约束 | skill-standardization / triphasic-execution / git-sync | 编排器本身遵守固化>调用的原则 |
| **本篇：编排范式** | 多技能间的编排与执行 | Orchestrator | **调度层——前三维度在编排层面的应用** |

### 5.2 本篇的定位

前三篇解决的是"单技能的正确性"问题：

```
第一篇：技能执行时不出轨
第二篇：技能结构统一
第三篇：方法论工具不自欺
```

本篇解决的是"多技能如何组合"的问题：

```
Orchestrator：不是让单个技能更正确，而是让多个技能正确协作
```

### 5.3 各维度在编排器中的落地

| 方法论维度 | 在编排器中的体现 |
|-----------|----------------|
| 运行时硬约束（第一篇） | triphasic_execute_step() — 执行→审查→推进，最多 3 次重试 |
| 构建时契约（第二篇） | skill_scanner — 解析 SKILL.md 的 YAML frontmatter，识别技能接口 |
| 递归自举（第三篇） | 编排器使用固化算法而不是 LLM 来完成确定性任务——不自欺 |

## 六、工程实践总结

### 6.1 设计原则清单

1. **路径确定性** — 执行路径在执行前确定，不在执行中改变
2. **LLM 降级为胶水** — 只做格式转换，不做路径决策
3. **固化 > 调用** — 确定性逻辑永远不调用 LLM
4. **可选不强制** — 所有增强功能勾选才启用
5. **审查不修改** — 审查层只返回通过/不通过
6. **原子化传递** — 步骤间通过 FILE marker 显式传递结果
7. **配置驱动** — 所有参数（超时/tokens/续接）可配置

### 6.2 常见反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| **ReAct 残留** | 在执行循环中让 LLM 决定"下一步做什么" | 执行前确定 Pipeline，LLM 只填充内容 |
| **过固化** | 把需要语义理解的功能也硬编码（如自然语言理解） | 用 LLM 做语义部分，固化做算法部分 |
| **审查绕过** | 执行后不审查，直接输出 | 每次执行后必须有审查点 |
| **粘合过度** | 每一步之间都做 LLM 粘合（即使格式不需要转换） | 只在格式不匹配时做粘合 |

### 6.3 适用场景

**适合：**
- 3+ 个技能的流水线任务
- 技能间有明确的数据流转关系
- 执行路径需要可复现、可审计
- 需要混合脚本执行和 LLM 执行

**不适合：**
- 单步简单任务（直接用技能即可）
- 高度动态、每次路径都不同的探索性任务
- 需要实时人机交互的对话场景
