# 重型技能构建的方法论沉淀：抑制LLM执行偏差的硬约束架构


## 一、对LLM执行行为的基本判断

### 1.1 观察：某些偏差反复出现

在构建需要LLM参与的多步骤执行流程时，一种模式反复发生：

- **大方向正确**：LLM能理解任务目标，能识别需要调用哪些工具，能规划出大致合理的步骤顺序。
- **执行细节反复偏出预期**：输出格式有微小变体导致下游解析失败、文件写到了错误的位置、步骤之间的衔接状态丢失、在不该停的地方停下、在该停的地方继续推进。

这些偏差的共同特征是：**语义上没错，执行上错了。**

LLM生成的内容在"意思"上是合理的（所以不是"幻觉"）。但在格式、路径、时序、状态传递这些执行维度上，它反复偏离确定性流程的要求。

### 1.2 判断：这不是质量缺陷，是特性

这是LLM概率生成机制的固有特性。它的输出是"最可能的下一词"的链式组合，它没有"严格遵守格式/路径/状态契约"的硬约束能力。

- **这不是需要修复的bug。**
- **这是需要被管理的风险。**

你不可能通过"更好的Prompt"或"更详细的说明文档"来解决这个问题，因为你面对的不是理解能力不足，而是执行行为的不确定性。

### 1.3 核心命题

> **在多步骤确定性流程中，LLM的"自觉"是负资产。**

"自觉"在这里指：LLM在缺乏强外部约束时，倾向于主动补全、自行调整格式、自主决定推进节奏、自由解释指令边界。这些特性在对话场景中是优点，在需要严格遵循格式、路径、状态、时序的流程中，它们会持续引入偏差。

**解决方案的起点：不要试图让LLM更自觉。要用代码级手段压缩LLM的活动空间，让它只能在预先划定的狭窄闸口内活动。**


## 二、核心设计原理

### 2.1 原理一：步骤原子化

**基本判断**：LLM在处理"一整件事"时，最容易在边界处产生偏差——不知道什么时候开始、什么时候结束、什么时候必须等待。

**解决方案**：把所有任务拆解为原子步骤。步骤之间没有模糊地带，每个步骤的输入输出都被显式定义。

**步骤的定义**：

一个步骤是一个不可再分的最小执行单元。它必须包含：

1. **身份标识**：步骤的唯一ID，用于追踪和引用
2. **执行类型**：这个步骤由什么来执行（可以是自动化脚本，也可以是人工操作）
3. **输入契约**：执行这个步骤需要什么数据，格式是什么
4. **输出契约**：执行完成后产出什么，格式是什么
5. **约束集合**：这个步骤在什么条件下才能执行，什么条件下必须停止
6. **执行状态**：当前是待执行、执行中、成功、失败还是空转
7. **重试与空转计数**：失败了多少次，空转了多少次

**伪代码表示：**

```
Step {
    id: 唯一标识
    type: automation | manual | checkpoint
    input: { schema, required }
    output: { schema, optional }
    constraints: { hard: [], soft: [] }
    status: pending | executing | success | failed | idle
    retries: 0..max
    idle_count: 0..max
}
```

**为什么这个设计能抑制自觉**：当任务被拆解为原子步骤后，LLM不再需要"决定"下一步做什么。步骤的顺序已经在编排层预先定义好了。LLM只需要"填写"当前步骤所需的输入数据。

### 2.2 原理二：硬中断替代软约束

**基本判断**：所有"提示LLM要遵守"的软约束，LLM都有权选择忽略。它不是叛逆，而是概率模型的本性——"遵守指令"只是它输出概率中的一条路径，不是必然路径。

**解决方案**：不在文本层面约束LLM，在进程层面拦截越界行为。当LLM的行为偏离契约时，不发出"警告"，而是直接终止执行进程。

**中断触发器**：

| 触发条件 | 检查内容 | 后果 |
|---------|---------|------|
| 前置条件不满足 | 上一步未完成必要动作 | 中断，挂起 |
| 重试超限 | 同一步骤失败超过N次 | 中断，挂起 |
| 空转超限 | 同一步骤无进展超过N次 | 中断，挂起 |
| 产出物缺失 | 步骤结束后未生成预期文件 | 中断，挂起 |
| 格式不匹配 | 输出格式与契约不符 | 中断，挂起 |

**中断的执行方式**：

```
block(reason) {
    1. 输出阻断信号到stderr（避免被管道过滤）
    2. 同时输出阻断信号到stdout（双重保障）
    3. 写入锁文件（持久化阻断状态）
    4. 调用进程退出，退出码为2（区别于普通错误）
}
```

**为什么用退出码2而不是1**：

退出码的设计表达了错误的"恢复可能性"：

- `0`：正常完成，无需任何操作
- `1`：发生错误，修复后需要重新执行全部流程
- `2`：发生阻断，修复后可以从阻断点继续执行

`2`这个退出码配合锁文件，构成了"可恢复中断"的语义——上层调度器看到退出码2时，会读取锁文件，保留当前进度，等待修复后通过特定参数恢复。

### 2.3 原理三：双通道信号传输

**基本判断**：在子进程调用场景中，stdout往往被上层捕获并处理。阻断信号如果只写在stdout中，很可能被上层"消化"或"过滤"，导致阻断信号丢失——流程继续推进，但已经处于错误状态。

**解决方案**：关键信号必须走冗余通道。

**两条通道的分工**：

| 通道 | 内容 | 用途 |
|------|------|------|
| stdout | 简短状态信号（`[BLOCKED]`前缀） | 给正常捕获机制使用，机器可读 |
| stderr | 完整阻断信息（含原因、上下文） | 不被管道过滤，保留完整上下文 |
| 文件系统 | 锁文件（含完整阻断信息） | 持久化，支持后续恢复 |

**调用方的检查逻辑**：

```
output = stdout_content + stderr_content
if "BLOCKED" in output or "阻断" in output:
    // 检测到阻断，挂起流程
```

**为什么用中英文双关键词**：LLM的触发条件和输出可能混合多种语言，单一语言的关键词可能漏检。双关键词覆盖了更广的实际情况。

### 2.4 原理四：阻断→挂起→恢复的完整循环

**基本判断**：多步骤LLM任务的执行成本较高（Token消耗、时间开销）。如果阻断后必须从头重跑，整个方案的工程价值会大幅降低。

**解决方案**：阻断发生时，不销毁进度，而是将当前状态持久化，并提供明确的恢复路径。

**状态持久化的内容**：

```
{
    "blocked_at": "步骤X",
    "reason": "阻断原因",
    "completed_steps": [1, 2, 3],
    "pending_stage": "阶段名称",
    "timestamp": "阻断发生时间"
}
```

**恢复路径**：

```
正常执行 → 发生阻断 → 写入锁文件 → 进程退出(2)
    ↓
（外部修复问题）
    ↓
重新执行，传入恢复参数 → 读取锁文件 → 跳过已完成步骤 → 从阻断点继续
```

**这要求执行引擎具备以下能力**：

1. 能识别"恢复执行"模式（通过特定参数）
2. 能读取并解析锁文件中的状态
3. 能跳过已完成步骤，不从第一步重新开始
4. 在恢复完成后清理锁文件

### 2.5 原理五：准入门槛的强制校验

**基本判断**：即使有了步骤模型、硬中断和恢复机制，如果接入系统的"执行单元"本身就不规范，所有下游保障都会失效。就像你无法通过更严格的交通规则来弥补汽车本身刹车失灵的问题。

**解决方案**：在接入层面建立强制性的五层校验，任何执行单元必须全部通过才能运行。

**五层校验**：

| 层 | 检查内容 | 不通过后果 |
|---|---------|----------|
| 元数据层 | 身份信息是否完整（名称/版本/作者/描述/数据目录） | 拒绝接入 |
| 触发条件层 | 是否有明确的触发词和否定条件 | 拒绝接入 |
| 约束层 | 是否声明了至少N条强制约束，其中M条可由脚本自动校验 | 拒绝接入 |
| 工具链层 | 是否包含配置界面、管理CLI、执行引擎三个基础脚本 | 拒绝接入 |
| 数据持久化层 | 是否有标准的数据目录结构（状态/锁/产物/日志） | 拒绝接入 |

**校验的执行方式**：静态扫描，不依赖运行时。所有检查在接入阶段完成，不在执行阶段发现。

**为什么需要五层而不是一层**：单层校验总会有遗漏。五层分别对应"身份、行为、约束、工具、数据"五个维度，覆盖了执行单元可能出问题的所有方面。每一层的校验结果会叠加，任何一层不通过则整体拒绝。


## 三、这套机制为什么能工作

### 3.1 核心逻辑不是"教育LLM"，而是"缩小LLM的活动范围"

一个常见误解是"如何让LLM更好地遵守指令"——这导向的是更好的Prompt工程、更详细的输出格式说明。

这套方案的前提假定不同：**LLM在"自由输出"时产生偏差是必然的，你不可能通过"说清楚"来让它不偏差。**

唯一可靠的做法是：**让LLM只在"填空题"和"选择题"的范围内输出。**

- 填空题：填什么字段、填什么值
- 选择题：从预设选项中选择一个

其他所有事情——步骤的顺序、步骤间的依赖、重试次数的上限、空转的上限、中断的条件——全部由代码定义。

**LLM的角色被压缩为"小口径管道"中的内容生成器**，而不是"自主决策者"。

### 3.2 为什么硬中断比软约束更可靠

Prompt约束是概率性的：

> "请按格式输出" → LLM有90%的概率按格式输出，10%的概率不按格式输出。

即使提升到99%，在多步骤流程中（假设10个步骤），整体合规率 = 0.99^10 ≈ 90.4%——意味着几乎每10次执行就有1次在某处偏离。

硬中断是确定性的：

> 步骤执行后检查产出物 → 不符合契约 → 进程终止。

它不依赖LLM的选择，只依赖代码的检查。LLM是否愿意配合不影响检查结果。

### 3.3 为什么不是单纯的防御式编程

防御式编程在每个调用点检查返回值、处理异常路径。这套方案的不同之处在于：**它不是"检查不通过则处理异常"，而是"检查不通过则终止"。**

区别在于：

| 防御式编程 | 硬中断方案 |
|-----------|----------|
| 处理异常 | 终止执行 |
| 保留执行上下文 | 挂起并锁住上下文 |
| 继续后续流程 | 不允许继续 |
| 依赖调用者正确处理异常 | 调用者只能看到进程终止 |

硬中断方案的"终止并挂起"设计，确保了**错误状态不会被传递到下游**。它像电路中的保险丝——电流异常时熔断，而不是让异常电流继续通过。

### 3.4 为什么"填空题/选择题"模式对LLM有效

LLM在处理"生成一段描述"时，自由度高，偏差空间大。LLM在处理"从[A、B、C]中选择一个"时，自由度低，偏差空间小。

这种差异是显著的：约束越具体的任务，LLM输出与预期目标之间的方差越小。

这套方案通过步骤原子化和输入输出契约的定义，把LLM在大部分任务中都推到了"低自由度"的工作模式中。LLM仍然可以自由发挥的部分被严格限制在"填这个字段的值"的范围内。


## 四、这套方案的边界与局限

### 4.1 它管不了什么

**第一，管不了语义错误。**

如果LLM在"填空题"里填了错误的值——比如把"排班表"填成了"财务报表"——硬中断机制不会发现。因为它只检查"格式是否符合"和"字段是否存在"，不检查"内容是否正确"。

语义错误需要另外的手段处理：事实核查、知识库检索、人工校验。

**第二，管不了意图模糊。**

如果用户输入本身就不明确（"帮我做一下那个事"），这套方案无法工作。因为第一步"拆解为Step"就依赖明确的输入。意图识别是前置环节，不是这套方案的范畴。

**第三，管不了非执行层面的偏差。**

这套方案只约束执行行为——格式、路径、状态、时序。如果LLM在规划层面就错了（比如步骤顺序完全不合理），硬中断可能在流程推进到某个步骤时触发"前置条件不满足"，也可能永远不触发。

### 4.2 硬中断本身的脆弱性

**退出码依赖调用方检查。** 如果上层调用者不检查 `proc.returncode`，退出码2和0就没有区别。这套方案的有效性建立在"上层正确检查退出码"这个前提上。

**信号在多层管道中可能衰减。** stdout和stderr在多层嵌套调用中可能被重定向或丢弃。文件系统的锁文件是唯一持久化的信号载体，但它需要上层主动去读取。

**锁文件可能残留。** 进程被强制终止时（如kill -9），锁文件不会被清理。残留的锁文件会导致后续执行被误判为"已阻断"，除非实现超时机制。

### 4.3 需要LLM自觉的环节

以下两个约束无法被代码验证，只能由LLM自觉遵守：

**"换思路必须经完整三步循环"**：判断"当前方案已失效，需要换思路"是语义层面的决策，无法由代码检查。代码只能检查"重试次数已超限"并触发中断，但LLM可以选择在"换思路"后是否完整执行。

**"不倒回已完成步骤"**：判断"当前步骤的结果是否真的不可逆"同样涉及语义理解，代码无法确定"倒回"是否真的在发生。

这两条只能在强制约束表中声明为"AI自觉"项，无法升级为"Python强制"项。


## 五、这套方案沉淀了什么

### 5.1 一个基本判断

LLM在多步骤确定性流程中的偏差行为是概率性输出机制的自然结果，不是质量缺陷。应对方式不是"修复LLM"，而是"缩小LLM活动边界"。

### 5.2 五个设计原理

1. **步骤原子化**：把任务拆成不可再分的最小单元，LLM只负责填值
2. **硬中断替代软约束**：用进程终止代替文本警告
3. **双通道信号传输**：stdout + stderr + 文件系统，确保阻断信号不丢失
4. **阻断→挂起→恢复循环**：避免从头重跑，降低中断成本
5. **五层准入门槛**：不规范的执行单元根本进不了系统

### 5.3 一个完整的架构范式

```
输入（自然语言）
    ↓
[拆解] 将任务拆解为Step，每个Step有明确的输入输出契约
    ↓
[编排] 确定Step之间的顺序和依赖关系
    ↓
[执行] 按序执行Step，每个Step执行后检查产出是否符合契约
    ↓
[中断] 如产出不符合契约，写入锁文件，终止进程
    ↓
[恢复] 修复问题后，通过特定参数从锁文件记录的位置继续
```

### 5.4 一句可复用的话

> **把LLM的活动空间压缩到"填空题/选择题"的狭窄闸口内，用代码级硬中断在边界处拦截越界行为，用锁文件和恢复参数支持中断后的续跑。**


## 附录：这套方法论可以怎么迁移

| 场景 | 迁移方式 | 需要调整的部分 |
|------|---------|--------------|
| 非Skill框架的LLM应用 | 保留Step原语、硬中断、锁恢复机制 | 调整"五层校验"的检查项 |
| 单次LLM调用场景 | 硬中断机制可能过于重型 | 只需保留输出格式的契约检查 |
| 多步骤人工审核流程 | 可借鉴"阻断→挂起→恢复"循环 | 中断条件改为"等待人工确认" |
| 传统确定性工作流引擎 | 硬中断机制可增强现有错误处理 | 不需要Step拆解和LLM填充部分 |
