# 重型技能构建的方法论沉淀：递归自举的元验证范式

> 这是方法论的第三篇。第一篇（运行时硬约束）回答了"执行过程中如何阻断偏差"，第二篇（构建时契约）回答了"如何让构建被统一规范约束"。第三篇回答前两篇留下的那个缺口——"谁来确保这套方法论本身被遵守？"
>
> 答案是：**这套方法论自己验证自己。**

---

## 三篇的关系

|  | 第一篇（运行时） | 第二篇（构建时） | **第三篇（元验证）** |
|---|-------------|-------------|-----------------|
| **核心问题** | 执行偏差如何阻断 | 构建缺乏统一规范 | **方法论本身如何被确保** |
| **核心机制** | 硬中断 + 锁恢复 | 五层契约 + 接入校验 | **递归自举 + 自我审计** |
| **作用对象** | 技能的运行过程 | 技能的构建过程 | **方法论体系自身** |
| **依赖关系** | 依赖契约提供判断标准 | 依赖硬中断保障执行力 | **依赖前两者成立，然后验证它们自身也遵循同一套规则** |

---

## 一、元层面：任何方法论都需要被验证

### 1.1 一个递归问题

第一篇建立了一个架构：用代码级硬中断拦截LLM的越界行为，把LLM的活动空间压缩到填空题/选择题的闸口内。

第二篇建立了一个规范：用五层契约统一所有技能的结构，让硬中断有据可依，让调度可统一。

这两篇共同构成了一个"约束LLM的方法论"——对技能而言。但问题出现了：

**这套方法论本身，由谁来约束？**

- 标准化审计引擎 audit 别的技能——但谁审计它自己？
- triphasic-execution 约束别的任务的三步循环——但它自己的执行被谁约束？
- git-sync 同步别的技能——但它自己的配置谁来校验？

这不是一个理论问题。在构建20个技能的过程中，它真实地反复出现：

| 现象 | 本质 |
|------|------|
| 修改审计引擎后，需要手工确认它还能正确审计别的技能 | 审计引擎没有自我审计能力 |
| 修改执行框架后，它可能不再约束自身的执行顺序 | 执行框架没有自我约束机制 |
| 修改契约工具后，它自身的契约可能与声明的规范不一致 | 契约工具没有自我契约校验 |
| 修改测试套件后，测试套件本身可能不再通过它能发现的测试 | 测试套件没有自我测试 |

### 1.2 判断：这不是一个bug，是方法论完整性的必要条件

任何方法论如果只能约束"其他东西"而不能约束自己，它就有以下脆弱性：

1. **维护者悖论**：修改方法论工具的人不受方法论约束，所以工具在被修改时质量不可控
2. **递归中断**：方法论的迭代改善在某个点之后，依赖修改者的"自觉"——而第一篇文章证明自觉不可靠
3. **不可验证性**：你永远无法确定"当前方法论体系是否完整"，因为没有元层面的验证机制

### 1.3 核心命题

> **一套约束LLM的方法论，如果它不能约束自己，就不能声称自己能约束任何东西。**

"递归自举"在这里的含义是：**方法论中的每一条规则，都适用于定义这条规则的工具自身。** 审计引擎必须能被审计自身。契约系统必须能被自身的契约约束。执行框架必须遵循它自身定义的执行顺序。

这看起来像是一个哲学问题，但它有非常工程化的解决方案。

## 二、核心设计原理

### 2.1 原理一：自我审计

**基本判断**：如果一个工具审计其他技能的规则不能应用于自身，那么当这个工具被修改时，修改的质量无法被保证。审计引擎自身的退化会直接导致整个方法论体系的退化。

**解决方案**：审计引擎必须能够审计自己，且审计自身的规则与审计其他技能的规则相同。

**实施方式**：

```
技能标准化审计引擎（skill-standardization）
  │
  ├── 审计其他技能 ── 规则R-01 ~ R-26
  │    ├── frontmatter完整性
  │    ├── 版本号一致性
  │    ├── 数据目录合规性
  │    ├── 渐进式加载合规性
  │    └── 权限声明完整性
  │
  └── 审计自身 ── 同一条规则集
       ├── skill-standardization 自身的 frontmatter 完整吗？
       ├── 它自己的版本号三端一致吗？
       ├── 它自己的数据目录合规吗？
       └── 它自己的渐进式加载合规吗？
```

**自我审计与普通审计的差异**：规则相同，只是审计对象变成自己。不能使用"特殊豁免"，不能有"它因为是自己所以不需要遵守某条规则"。

**自我审计的制约条件**：自我审计不能无限递归。当审计引擎审计自己时，它不能要求"审计引擎的审计引擎"再来审计自己。递归终止于**规则被证明在自身身上可执行**，而不是"规则被另一个实体验证了"。

**如何避免无限递归**：

```
第1层：审计引擎 audit 其他技能 → 输出报告A
第2层：审计引擎 audit 自身 → 输出报告B
第3层：检查报告A和报告B的格式是否一致
         └─ 如果B的输出格式与A相同，且B中发现的问题被修复后重新审计通过
         └─ 自我审计即可"自洽"——不需要第4层
```

关键判断：**不是"谁审计审计者"，而是"审计者审计自己时，输出格式是否与被审计者一致"。** 如果格式一致，说明规则在自身身上同样可执行。如果格式不一致，说明规则有隐式豁免——这正是需要修复的。

### 2.2 原理二：自我约束

**基本判断**：执行框架定义了一套步骤间的约束——上一步必须REVIEW才能推进、重试不能超过3次、空转不能超过3次。但框架本身在执行时，也需要遵循这些约束。

**解决方案**：执行框架在执行自身的管理操作时，使用与约束技能执行相同的约束机制。

**实施方式**：

```
triphasic-execution 约束其他任务：
  步骤1 → REVIEW → ADVANCE → 步骤2 → REVIEW → ...
  失败3次 → 换方案
  空转3次 → 换方案

triphasic-execution 管理自身的操作（如安装、配置、升级）：
  同样使用三步循环
  同样有重试上限
  同样有Review后推进
```

**自我约束不是"建议执行框架遵守自己的规则"**，而是执行框架的安装脚本、配置操作、升级流程直接使用同一套三步循环。同一个 `task_progress.py` 既管理用户任务的进度，也管理自身的安装进度。

**自我约束的制约条件**：框架的管理操作通常比技能执行简单，可能不需要完整的3次重试。约束可以缩放——"三步循环"的模式不变，但具体的参数（重试上限、空转上限）可以不同。**模式一致，参数可调。**

### 2.3 原理三：自我契约

**基本判断**：契约系统定义了所有技能必须遵循的五层结构声明。但这个定义本身——契约系统的设计文档和执行代码——是否也遵循这五层结构？

**解决方案**：契约系统的定义自身必须是一份有效的五层契约。

**实施方式**：

```
契约系统（skill-standardization）的定义：

L1 身份声明
  名称：skill-standardization
  版本：语义化版本，三端同步
  作者：wUwproject
  数据目录：skills/.standardization/skill-standardization/data/

L2 触发与能力声明
  正向触发："审计这个技能"、"检查这个技能"、"创建一个新技能"
  否定条件：仅文件操作、不涉及技能结构时

L3 行为约束声明
  硬约束1：--mode 与 --command 必须一致，不一致则拒绝执行
  硬约束2：0 ERROR 0 WARN 后 才能 bump 版本
  硬约束3：auto-fix 最多运行3轮

L4 接口声明
  配置入口：--mode audit/create/update/refactor
  管理入口：--list-rules / --show-report / --classify
  执行入口：--mode audit <skill> --category <cat>

L5 数据声明
  数据目录：skills/.standardization/skill-standardization/data/
  规格文件：scripts/spec/rules.json, body.json, frontmatter.json
```

**自我契约的校验方式**：用契约系统自身的校验规则检查它自己的声明。如果它能通过自己定义的R-01到R-26检查，说明规则在自身身上成立。

**自我契约不是写一篇文档描述自己遵循了契约**，而是让契约引擎能够以普通技能的标准来审计自身，并得到PASS。

### 2.4 原理四：统一的元数据结构

**基本判断**：上述三个原理（自我审计、自我约束、自我契约）分散在不同层面，但它们指向同一个核心模式——**方法论系统中的每一个构件，都必须以统一的数据结构描述自身**。

**解决方案**：定义一份统一的元数据声明模板，方法论中的每一个工具（审计引擎、执行框架、测试套件、同步工具）都按照这份模板声明自己的身份、版本、约束、接口、数据位置。

**元数据结构**：

```
每一个"方法论工具"声明：
  1. 身份：名称、版本、作者、协议、数据目录
  2. 能力：它能做什么、什么时候该被调用、什么时候不该被调用
  3. 约束：它自己必须遵守的硬约束（例如"审计他人前必须自审"、"同步前必须通过审计"）
  4. 接口：调它的入口参数、它产出的数据格式、它接受的配置格式
  5. 数据：它的运行时状态存放位置、它的日志位置、它的锁文件位置
```

**为什么需要统一的元数据结构**：

不同的工具使用不同的元数据格式，会导致：

| 问题 | 后果 |
|------|------|
| 审计引擎的元数据格式与技能不同 | 无法用同一套规则审计审计引擎 |
| 执行框架的元数据格式与技能不同 | 无法用契约系统的校验器检查框架 |
| 同步工具的元数据格式与技能不同 | 版本号对比无法跨工具操作 |

如果所有方法论工具使用**与技能相同的元数据结构**，那么：

- 审计引擎可以审计自己（因为自己的元数据格式与技能一致）
- 契约系统的校验器可以校验契约系统自身
- 版本管理工具可以追踪所有方法论工具的版本

**统一并不意味着所有工具都使用同一个文件**，而是它们声明信息的字段、语义、校验规则是相同的。

### 2.5 原理五：自举链的有穷性

**基本判断**：递归必须终止。自举不是无限循环，而是以"自洽"为终点的有穷过程。

**解决方案**：定义自举的终止条件，不追求"完全形式化验证"，追求"工程上的自洽"。

**自举链的结构**：

```
方法论的定义（这套方法论文档本身）
   ↓ 指导
标准化审计引擎（skill-standardization）
   ↓ 能够审计
自身（包括它自己的代码、文档、元数据）
   ↓ 自审通过
方法论工具群（执行框架、测试套件、同步工具…）
   ↓ 每个工具自审通过
方法论体系可以声称"自洽"
```

**自举的终止条件**：

1. 每个方法论工具都能通过自己的元数据声明校验
2. 每个方法论工具在执行核心操作前，会验证自身状态一致
3. 方法论体系中的任何修改，都会触发自我审计
4. 自我审计发现的任何不一致，都被视为与方法论规则同等严重的问题

**什么不是自举的终止条件**：

- "所有规则都有形式化证明"——这不是工程，这是数学。方法论是工程的产物，不是数学定理
- "所有人都同意这套方法论很好"——共识不可校验
- "已经连续XX天没有问题了"——无故障运行时间不能证明方法论有效

## 三、自举链的完整路径

### 3.1 自举链的步骤

```
起点：方法论文档
  定义 "一个重型技能应该是什么样子"
    例如：有SKILL.md、有_meta.json、有五层声明、有双轨测试
    ↓

第一环：标准化审计引擎（skill-standardization）
  按照方法论文档定义，实现了审计规则（R-01 ~ R-26）
  能够检查一个技能是否符合方法论规范
    ↓

第二环：审计引擎审计自身
  用R-01 ~ R-26检查skill-standardization自己
  它有自己的SKILL.md、_meta.json、frontmatter、data_dir
  它自己的版本号三端一致吗？条件字段合规吗？
    ↓

第三环：审计通过（或修复后通过）
  skill-standardization被证明符合它自己执行的规范
  → 该方法论工具"自洽"
    ↓

第四环：其他方法论工具
  triphasic-execution：
    它的三步循环约束是否也约束它自己的管理操作？
    它能否通过标准化审计引擎的R-01~R-26审计？

  skill-function-test：
    它是否通过了它能发现和报告的测试标准？
    它的测试报告是否包含了对它自身的测试？

  git-sync：
    它的版本对比和敏感扫描是否也应用于自身？
    它同步其他人时，自己的版本和manifest是否一致？
    ↓

终点：方法论工具群全部自审通过
  不再证明"方法论有效"——而是"方法论中的每一个工具，都遵循方法论定义的规则"
```

### 3.2 自举不能跨越的边界

自举链不能回答以下问题：

**"这套方法论真的有效吗？"**

自举只回答"方法论中的工具遵守了方法论定义的规则"，不回答"方法论定义的规则本身是否正确"。后者需要外部验证——实践中的效果、独立第三方的评估、跨系统的迁移验证。

**"这套方法论比另一套更好吗？"**

自举不提供比较框架。比较需要独立的评估指标和对照组。

**"方法论文档本身是否遵循了方法论？"**

方法论文档是自举链的起点，不是自举链的检验对象。如果方法论文档本身写成了SKILL.md的格式，可以被审计引擎审计——这可以做，但不是自举的必要条件。文档的"正确性"由人类读者判断。

## 四、20个技能中的自举体现

在20个技能的实际构建中，自举模式反复出现：

### 4.1 skill-standardization 自举

这是最完整的自举案例。skill-standardization 维护了一个 `rules.json` 定义了 R-01 ~ R-26 审计规则。当这个文件被修改时，它必须重新审计自己——因为这些规则的定义本身是否符合这些规则。

实现方式：`--mode audit --target skill-standardization` 可以正常执行。

**自举成立的证据**：skill-standardization 自身的审计结果与其审计其他技能时的输出格式一致（version标记、三分类、ERROR/WARN体系）。

### 4.2 triphasic-execution 自举

triphasic-execution 定义了 Execute→Review→Advance 三步循环。它自身的安装脚本 `install.py` 同样使用这三步：
1. Execute：复制文件到目标目录
2. Review：检查安装完整性
3. Advance：输出安装报告或回滚

**自举成立的证据**：安装过程使用了与技能执行相同的进度文件管理（`task_progress.py`）。

### 4.3 git-sync 自举

git-sync 在同步前会进行版本号对比和敏感信息扫描。当它同步自身时：
1. 对比本地和远程的版本号（自身版本管理）
2. 扫描自身的代码和文档中的敏感信息
3. 更新 README.md 中关于 git-sync 自身的条目

**自举成立的证据**：git-sync 能够以处理其他技能完全相同的方式处理自身。它没有"因为是我自己，所以跳过检查"的例外路径。

### 4.4 skill-function-test 自举

skill-function-test 的 S1-S3 场景测试和 D1-D6 功能测试，同样可以应用于自身：
- S1：它能测试的 CLI 脚本，它自己也有
- D1：它能检查的语法问题，它自己的代码也有
- S4：它暴露的纸老虎约束，它自己也可能有

**自举成立的证据**：在测试其他技能之前，先用同一套测试流程测试自己。如果测试套件自己都不能通过D2（引用链路检查），它声称的"能检查引用链路"就不值得信任。

## 五、自举需要被作为架构设计而非事后检查

### 5.1 自举作为设计原则

自举不是一种验证手段——它是一个架构设计原则。

如果自举只在方法论体系建成后"补做"，它就不是自举。它是"补个检查"。真正的自举要求：**在方法论工具的架构中，就内置了"我也可以被自己检查"的能力。**

```
事后补做：
  造了审计引擎 → 其他人说"谁审计你？" → 加个"审计自己"的hook
  → 脆弱。hook可能被绕过，可能没有覆盖所有规则

架构内置：
  设计审计引擎时，就把"自身也接受审计"作为第一性原理
  → 没有绕过路径。审计自己的代码路径与审计他人完全相同
```

### 5.2 反模式：选择性自举

最常见的自举失败形式是**选择性自举**——方法论工具在自己的规则中给自己留了例外。

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 规则豁免 | "工具X不需要遵循规则R-XX，因为它是元工具" | 方法论有特权层，特权层不可验证 |
| 路径绕过 | 审计自身时使用不同的代码路径（轻量扫描） | 自审结果不可与普通审计对比 |
| 格式差异 | 自身声明使用不同的元数据结构 | 无法用统一校验器检查 |
| 跳过修复 | 自身发现问题但标记"已知问题，以后修" | 方法论不应用于自身时，它本身就没有被方法论约束 |

### 5.3 自举的孪生问题：自举不是自指

自举和自我指涉有一个关键区别：

| | 自举（Bootstrapping） | 自指（Self-reference） |
|---|---------------------|---------------------|
| **目标** | 证明规则在自身身上可执行 | 证明"自己是对的" |
| **方式** | 用同一套规则检查自己 | 引用自己来证明自己 |
| **结果** | 自洽（输出格式一致、规则覆盖一致） | 悖论（"这句话是假的"） |
| **工程可行性** | 可行。输出格式可以比较 | 不可行。循环论证 |

自举的核心是：**它不证明"自己是对的"，它只证明"自己对他人和对自己的标准一致"。** 后者是可判断的——审计引擎审计别人输出A格式，审计自己输出A格式，两者格式一致。标准一致不等于标准正确，但标准一致保证了方法论不自欺。

---

## 六、边界

### 6.1 自举能解决的问题

- 方法论工具维护时的质量退化 → 自审可以提前发现
- 方法论体系内部的规则豁免 → 自审可以暴露例外
- 工具修改后的回归确认 → 自审可以作为回归标准
- 方法论体系的完整性证明 → 自审证明"规则至少在被自己遵守"

### 6.2 自举不能解决的问题

- **方法论规则本身的正确性**：自举只证明"规则被遵守了"，不证明"规则是对的"
- **方法论体系的外部有效性**：自举不告诉你"这套方法论在别的系统上能工作"
- **方法论与目标的因果关系**：自举不证明"因为遵守了方法论，所以技能质量高"——这需要对比实验
- **方法论体系的完整性**：自举不保证"规则集覆盖了所有需要约束的方面"。可能有规则缺口，自举只能证明现有规则被遵守
- **规则之间的优先级冲突**：当两条规则冲突时，自举不能选出应该遵循哪一条——这是元规则层面的问题

### 6.3 自举链的固有脆弱性

**脆弱的起点**：自举链始于方法论文档。如果方法论文档本身写错了方向——例如定义了错误的规则——自举只能保证这个错误的规则被一致地遵守，不能发现规则本身的错误。

**退化性修改**：一个恶意的（或认知能力不足的）维护者可以同时修改工具本身和它的自我审计标准，使自审仍然通过但规则被削弱。自举不能防止"自己降低自己的标准"。

**审计引擎的盲区**：如果审计引擎本身有某种缺陷——比如它检查"版本号一致性"但不检查"版本号语义正确性"——这种缺陷会在自举中保留，因为它不在规则覆盖范围内。

## 七、总结

### 7.1 一句话概括

> **方法论不约束自己，就没有约束任何东西的资格。自举不证明方法论正确，只证明方法论不自欺。**

### 7.2 五个原理对应五个"元层面"

| 原理 | 解决的问题 |
|------|----------|
| 自我审计 | 审计引擎的规则是否适用于审计引擎自身 |
| 自我约束 | 执行框架的约束是否约束框架自身 |
| 自我契约 | 契约系统的结构声明是否包含系统自身 |
| 统一元数据结构 | 方法论工具能否用同一套校验规则统一检查 |
| 自举链有穷性 | 递归在何处终止，不自相矛盾 |

### 7.3 三篇方法论的完整关系

```
【第二篇：构建时契约】
  定义 "一个正确的技能应该长什么样"
    五层结构声明 → 接入校验 → 技能接入系统

【第一篇：运行时硬中断】
  定义 "正确的执行应该怎么被保障"
    步骤原子化 → 硬中断检查 → 阻断/挂起/恢复

【第三篇：递归自举】
  定义 "方法论本身如何被确保"
    审计引擎审计自己 → 框架约束自己 → 契约系统声明自己
    同一套规则 → 不自欺
    不自欺 → 方法论完整
```

三篇方法论各自独立，又互相依赖。它们的依赖关系不是线性的，而是环形的：

```
第二篇（契约） → 第一篇（硬中断需要契约提供判断标准）
第一篇（硬中断） → 第三篇（自举需要硬中断来保障自审不被打断）
第三篇（自举） → 第二篇（自举的起点是契约系统）
```

这是一个**环形自洽**的结构——三篇中没有哪一篇是"最终权威"。每一篇都依赖另外两篇来完成自己的功能。

### 7.4 一句可复用的话

> **你能用你的方法论来检查你自己吗？如果能，你的方法论是完整的。如果不能，你的方法论有一个你还没发现的名字——它叫信仰。**
