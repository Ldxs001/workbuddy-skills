# 结构化写作的方法论沉淀：子结构驱动的逐段生成范式

## 一、对长文写作的基本判断

### 1.1 观察：LLM 写长文时的三种失效模式

在构建基于 LLM 的结构化长文写作系统时，三种失效模式反复出现：

- **前重后轻**：文章前半部分详尽充实，后半部分逐渐空洞。LLM 在长篇输出中表现出明显的注意力衰减——越往后信息密度越低，论证深度减弱，甚至出现重复表述。
- **上下文污染**：先写的章节中隐含了尚未展开的结论、错误的引用、或者不适合后续章节的表述。LLM 不具备"回头修改"的能力，错误一旦生成就固化在文中。
- **格式塌缩**：要求 LLM 一次输出完整的多章节长文时，Markdown 标题层级混乱、列表断裂、引用格式不统一。随着输出长度增加，格式一致性呈阶梯式下降。

这些失效模式的共同特征是：**LLM 在整篇尺度上的控制力远弱于段落尺度。**

LLM 能在 500 字内保持结构清晰、论证严密、格式一致。但当输出扩展到 3000 字以上时，它在"全局结构"维度上的控制力指数级衰减。

### 1.2 判断：不是模型大小问题，是生成范式的边界

这不是"换个更大的模型"能解决的问题。即使 GPT-4 级别模型，在一次性生成长文时同样表现出衰减趋势。因为：

- LLM 的注意力机制本质上是局部的——即使有 128K 上下文，它对开头内容的注意力权重仍然低于末尾
- LLM 的生成是**单向的**——它不能回退修改已生成的内容，错误的累积是单向递增的
- LLM 的格式控制是**隐式的**——它没有"我目前在写第几章第几节"的显式状态，只有 token 序列中的隐含位置

### 1.3 核心命题

> **长文写作的正确范式不是"让 LLM 一次写完"，而是"让 LLM 一次只写一段，由编排层负责全局结构。"**

"子结构驱动"在这里指：人（或上层系统）负责决定文章的骨架——分几章、每章几个子主题、顺序如何——LLM 只负责填充每个子主题的具体内容。LLM 不决策文章结构，不决策写作顺序，不决策哪些子主题需要合并或拆分。

**解决方案的起点：把文章"写什么"和"怎么写"彻底分离。写什么由大纲决定，怎么写由 LLM 填充。LLM 的活动范围被限制在"一段子结构正文"的狭窄闸口内。**

## 二、核心设计原理

### 2.1 原理一：子结构原子化

**基本判断**：LLM 写 500 字的质量远高于写 5000 字。段落是 LLM 的舒适区，篇章是它的盲区。

**解决方案**：把文章拆解为原子级的"子结构"。每个子结构相当于传统写作中的一个"段落群"——3-5 段文字围绕一个子主题展开。子结构之间没有模糊地带，每个子结构的输入输出被显式定义。

**子结构的定义**：

一个子结构是一个不可再分的最小写作单元。它必须包含：

1. **身份标识**：子结构的唯一 ID（如 `s1_2` 表示第一节第二个子结构），用于追踪状态和引用
2. **标题**：子结构的主题，LLM 据此决定写什么
3. **写作要点**：30-50 字的方向指引，LLM 据此决定怎么写
4. **字数约束**：目标字数，LLM 据此控制篇幅
5. **写作状态**：pending / in_progress / done，系统据此恢复断线任务
6. **勾选标记**：用户可取消勾选来跳过该子结构

**伪代码表示**：

```
SubSection {
    id: "s1_2"
    title: "技术演进背景"
    summary: "简述Transformer诞生前的技术状态"
    word_count: 400
    status: pending | in_progress | done
    _checked: true
    actual_word_count: 0
}
```

**为什么这个设计能解决前重后轻**：当每个 LLM 调用只写一段 500 字的子结构时，它在开头 500 字的注意力水平和在末尾 500 字的注意力水平是一致的。LLM 不需要维持"整篇文章"的全局状态——全局状态由编排层的 state_manager 维护。

### 2.2 原理二：材料分级注入

**基本判断**：给 LLM 一份长资料让它"参考"，它会不加区分地使用。但文章的不同部分需要不同粒度的支持材料。

**解决方案**：两级 RAG 查询——节级别查背景资料（宽泛相关），子结构级别查针对性资料（精准匹配）。在 prompt 中分两段注入。

**为什么这个设计能提高内容精准度**：

- 节级别的材料提供了"这篇文章在讨论什么领域"的上下文
- 子结构级别的材料提供了"这段子结构的具体论据"
- LLM 看到两段材料时，会自然地做分层引用——背景用于建立语境，针对性材料用于支撑论点
- 错误处理：RAG 超时或失败时不塞进 prompt（污染输入），仅通过 status_text 告知用户

### 2.3 原理三：续写代替截断

**基本判断**：LLM 的输出被 max_tokens 截断是不可完全避免的——尤其是推理模型，思维链会消耗大量 token。截断后丢弃已有内容是不可接受的。

**解决方案**：检测 `finish_reason="length"`，将已写内容作为 assistant 消息放入下一轮请求，追加"请继续写"指令，最多重试 5 次。

```
LLM 输出 800 字
  → finish_reason == "length"
  → 把 800 字作为 assistant 消息 + "请继续写"
  → LLM 接着写 600 字
  → finish_reason == "stop" → 完成
```

**为什么这个设计能防止内容丢失**：通过 chat 格式的 assistant 角色消息，LLM 看到自己之前写的内容，自然知道"写到哪了"。续写指令给出明确边界——不能重复，不能回退，只能向前。

**边界处理**：如果 content 为空（推理吃光了所有 token），续写也没有意义——assistant 消息是空的，LLM 不知道从哪继续。此时放弃续写，跳过该子结构。

### 2.4 原理四：可交互状态 ≠ 黑盒执行

**基本判断**：用户对最终输出有控制权——不应该由 LLM 单方面决定文章的结构和内容。

**解决方案**：大纲完全暴露为交互式 UI，所有字段可调整：

| 操作 | 效果 |
|------|------|
| 取消整节 checkbox | 该节及其所有子结构不输出 |
| 取消子结构 checkbox | 单独跳过该子结构 |
| 修改字数 | 调整 LLM 的 max_tokens 约束 |
| 标记重点 | 重点子结构字数上浮 50% |
| 调整排序 | 改变写作顺序 |
| 绑定 RAG + KB | 启用特定知识库的上下文增强 |

**为什么这个设计优于全自动**：用户对文章最终形态的判断——哪些话题需要展开、哪些可以略过、引用的知识库来源于哪个领域——是 LLM 无法替代的领域知识。大纲交互让用户成为"架构师"，LLM 成为"执行者"。

## 三、实现架构

### 3.1 文件结构

```
structured-writer/
├── main.py                           # 入口
├── structured_writer/                # 核心包
│   ├── planner.py                    # 大纲规划器
│   ├── writer.py                     # 串行写作器（两级 RAG + 续写）
│   ├── rag_client.py                 # RAG 客户端
│   ├── llm_client.py                 # LLM 统一客户端
│   ├── state_manager.py              # 状态管理
│   ├── web_ui.py                     # HTTP 服务器 + 交互式前端
│   └── config_manager.py             # 配置持久化
```

### 3.2 子结构在编排层中的状态流转

```
planner.py → 生成大纲（含 sub_sections）
  ↓ 每个子结构初始状态: {status: "pending", _checked: true}
  ↓
交互式大纲 → 用户调整勾选/排序/字数
  ↓ 生成时后端过滤未勾选项
  ↓
writer.py → 逐子结构:
  1. status → "in_progress"
  2. RAG 查询 → 注入 prompt
  3. LLM 写作 → 续写循环
  4. status → "done"
  5. actual_word_count → 写入
  ↓
全部完成 → phase → "done"
```

### 3.3 state_manager 的双层粒度

状态管理器维护两层进度粒度：

- **节层**：记录每节的总状态（pending / done）和 actual_word_count
- **子结构层**：记录每个子结构的独立状态和字数的细粒度进度

这种双层设计允许断线重连后精确恢复到"上一个未完成的子结构"，而不是"上一个未完成的节"。

### 3.4 max_tokens 的配置化

对比"硬编码 max_tokens"和"从配置读取"：

- 配置化了 planner 和 writer 各自的 max_tokens，从 config.json 中的 `planner_model.max_tokens` 和 `writer_model.max_tokens` 读取
- 写入 LLMClient 实例属性，writer.py 不再自行计算覆盖——这解决了"我设置了 81920 但代码用的是 1024"的经典 bug

## 四、与现有方法论体系的关系

### 4.1 对应的方法论维度

| 方法论维度 | 对应组件 |
|-----------|---------|
| **第一步：原子化**（第一篇） | 子结构是原子写作单元，每个 LLM 调用只写一段 |
| **硬中断**（第一篇） | 续写检测（finish_reason）替代了"让 LLM 自己决定写多少" |
| **构建时契约**（第二篇） | JSON 大纲 schema 定义了每个子结构的字段约束 |
| **编排理论**（第四篇） | 写作管线是编排的典型应用——步骤序列化，LLM 做胶水 |
| **链驱动执行**（第六篇） | state_manager 维护进度链，writer.py 是链的执行器 |

### 4.2 子结构范式在方法论全景中的位置

结构化写作智能体是**第三篇（递归自举）之后的一个领域应用案例**——它展示了"原子化 + 硬中断 + 配置契约"三篇方法论如何在"长文写作"这个具体领域落地。

与第五篇（RAG Assistant）的链式不同，Structured Writer 的写作管线是**串行的、有状态的长流程**——每个子结构依赖前一个子结构的输出作为上下文。这是"编排层"（第四篇）而非"查询策略规划层"（第五篇）的典型模式。

### 4.3 已知盲区

| 问题 | 描述 | 状态 |
|------|------|------|
| **子结构粒度的最优值** | 2-4 个子结构/节是经验值，没有定量实验支撑 | 📌 待验证 |
| **上下文窗口的合理截断** | 当前用最近 800 字作为前文引用，长度是硬编码 | ⚠️ 需配置化 |
| **多模板的切换开销** | 切换模板时用户的模型参数（model/max_tokens）不继承 | 📌 后续版本 |
| **RAG context 长度控制** | 长 RAG 上下文可能挤压 LLM 的生成空间，目前无截断策略 | 📌 待设计 |
| **跨会话并行写作** | 当前只支持单次写作任务，不支持多会话同时生成 | 📌 后续版本 |

---

## 五、一句话总结

> 结构化写作不是让 LLM 写整篇文章，而是让 LLM 只写一段 500 字的子结构。文章结构由 JSON 大纲显式定义，写作顺序由编排层控制，内容质量由两级 RAG 增强。通过把"一篇长文"压缩为"一组短文的串行执行"，将 LLM 从不可靠的全局规划者降级为可预测的段落执行器。
