# Cogito Scribo — 方法论体系总览

> **Cogito, Scribo.** (我思，故我写。)
>
> 这里是 wUwproject 重型技能构建过程中沉淀的方法论体系。八篇文章 + 一篇操作层，一个闭环、一种架构范式。第八篇是收束——把三个独立智能体的共同架构选择归结为有限决策范式；08a 是操作层——回答"怎么做到第一次就做对"（前置规范 > 后置验证）。

八篇之间的关系（第八篇为独立领域应用）：

```
第七篇（元逻辑） → 统摄前六篇的"加法"不违反四条"减法"原则
第二篇（契约） → 第一篇（硬中断需要契约提供判断标准）
第一篇（硬中断） → 第三篇（自举需要硬中断来保障自审不被打断）
第三篇（自举） → 第二篇（自举链的起点是契约系统）
前三篇（单技能正确性） → 第四篇（编排层需要契约+硬中断+自举来保障多技能协作的正确性）
第四篇（编排理论） → 第五篇（链驱动执行是编排理论的工程实现）
第五篇（链驱动执行） → 第六篇（领域智能体是链驱动执行的一个具体应用案例）
**第八篇（智能体协作）** → 有限决策范式的三体印证，证明三条原则在三个独立智能体中的一致性。第七篇的实践验证，第八篇是智能体协作方法论的范式层入口
**08a（操作层）** → 第八篇的"怎么做"：前置规范 > 后置验证（错误空间前移封堵）、最小尝试次数（一次做对的概率结构）、分工先于名分（agent 定义之争的消解）、监督的时间非对称性（越到后期越不可能逃避）
**08 系列（容器约定）** → 智能体协作观点的沉淀容器是"08 系列"（08 + 08a + 未来同主题篇章），不是 08 单篇。后续不新增方法论维度的扩展进 08 系列，新增独立维度的另开新篇
```

## 八篇各自解决的问题

### 第一篇：运行时硬约束

| 维度 | 内容 |
|------|------|
| **核心问题** | LLM在多步骤执行中反复偏离预期——格式不一致、路径写错、状态丢失 |
| **基本判断** | 这不是bug，是LLM概率生成机制的固有特性。不可能通过"更好的Prompt"解决 |
| **核心命题** | **在多步骤确定性流程中，LLM的"自觉"是负资产** |
| **5个原理** | 步骤原子化 → 硬中断替代软约束 → 双通道信号 → 阻断→挂起→恢复 → 五层准入门槛 |
| **一句话** | 把LLM的活动空间压缩到"填空题/选择题"的狭窄闸口内，用代码级硬中断在边界处拦截越界行为 |
| **代表技能** | triphasic-execution |
| **读它的人** | 想知道"为什么LLM总是不按我写的步骤执行"的人 |

### 第二篇：构建时契约

| 维度 | 内容 |
|------|------|
| **核心问题** | N个技能有N种结构，上层调度器无法统一识别，运行时硬中断没有判断依据 |
| **基本判断** | 构建阶段缺乏强制性的结构规范，问题根源不是"写错了"而是"没有统一承诺" |
| **核心命题** | **构建时用五层契约锁定每个技能的"正确形态"** |
| **5个层次** | L1身份 → L2触发条件 → L3行为约束 → L4接口 → L5数据声明 |
| **一句话** | 构建时用五层契约锁定结构，让硬中断有据可依 |
| **代表技能** | skill-standardization |
| **读它的人** | 想统一管理多个技能、让它们结构一致的人 |

### 第三篇：递归自举

| 维度 | 内容 |
|------|------|
| **核心问题** | 方法论工具（审计引擎、执行框架、同步工具）由谁约束？它们自己能通过自己定义的规则吗？ |
| **基本判断** | 方法论不能只约束"其他东西"而豁免自己。否则方法论体系存在特权层，特权层不可验证 |
| **核心命题** | **方法论不约束自己，就没有约束任何东西的资格** |
| **5个原理** | 自我审计 → 自我约束 → 自我契约 → 统一元数据结构 → 自举链有穷性 |
| **一句话** | 自举不证明方法论正确，只证明方法论不自欺 |
| **代表技能** | 所有7个元方法论工具（skill-standardization / triphasic-execution / git-sync / skill-function-test / skill-sub / semantic-split / universal-file-ops） |
| **读它的人** | 看完前两篇后问"谁来保证这套体系不被破坏"的人 |

### 第四篇：编排范式

| 维度 | 内容 |
|------|------|
| **核心问题** | N个技能如何组合成流水线？LLM在编排中的角色应该是什么？ |
| **基本判断** | 多技能编排不能用 ReAct 循环——LLM 做路径决策导致不可复现、不可审计 |
| **核心命题** | **LLM 应从"大脑"降级为"胶水"，只做格式转换，不做路径决策** |
| **5个原理** | 路径确定性 → LLM 降级 → 固化>调用 → 可选不强制 → 审查不修改 |
| **一句话** | 技能是积木，编排是图纸，LLM 是胶水 |
| **代表工具** | Orchestrator（Skill Pipeline Orchestrator） |
| **读它的人** | 有多个技能，想让它们协作完成任务但不想用 ReAct 的人 |

### 第五篇：领域智能体 (Domain Agent)

| 维度 | 内容 |
|------|------|
| **核心问题** | 复杂知识库问答中，单轮 RAG 检索总是遗漏关键侧面——实体丢失、属性模糊、上下文孤岛 |
| **基本判断** | 问题不是检索太弱，而是检索之前没有分解。用户问题是一个复合指令，不是检索查询 |
| **核心命题** | **LLM 应承担"查询策略规划者"——将问题分解为 entities + attrs 元组，穷举组合后多路检索** |
| **5个原理** | LLM 分解 → 穷举组合 → 多路独立检索 → SM3 去重合并 → LLM 综合回答 |
| **一句话** | 切片检索替代单轮 RAG，被动的知识库变成了主动的检索阵列 |
| **代表工具** | RAG Assistant |
| **读它的人** | 用 RAG 但总是查不全、想做多知识库数据埋点分析的人 |

### 第六篇：编排智能体 (Orchestrator)

| 维度 | 内容 |
|------|------|
| **核心问题** | 编排好多个技能后，怎么真正执行？ReAct 循环中的 LLM 频繁在路径选择上出错 |
| **基本判断** | LLM 做路径决策不是优势而是负担——预编排的链已经定义了顺序，ReAct 的"思考"是多余开销 |
| **核心命题** | **链是主体，对话是附属。LLM 不应当"大脑"而应当是"执行器"——只负责执行链中的每个步骤** |
| **5个原理** | 链驱动 → 需求分析 → (skill-sub优化) → 逐步执行 → 配置可调 |
| **一句话** | 链是图纸，LLM 是施工队——不决策、只干活 |
| **代表工具** | Orchestrator（Skill Pipeline Orchestrator） |
| **读它的人** | 用 Pipeline 编排了技能链但发现实际执行时 LLM 还在乱走的人 |

### 第七篇：四条原则的元逻辑

| 维度 | 内容 |
|------|------|
| **核心问题** | 前六篇一直在"加"规则——加契约、加中断、加自举、加编排——但四条原则说"如无必要勿增实体"。它们是不是矛盾的？ |
| **基本判断** | 不矛盾。四条原则约束的是**架构**（系统应该长什么样），六篇文章约束的是**执行**（系统应该怎么运行）。架构要求"少"，执行要求"多" |
| **四条原则** | 如无必要勿增实体 → 如无规矩勿增操作 → 如无能力勿增限制 → 如无资源勿增承诺 |
| **一句话** | 所有规则加起来，都是在做同一件事：让不可靠的东西按可靠的方式执行，用代码级的硬约束替代人性级的自觉 |
| **读它的人** | 看完前六篇后感觉"规则太多"又觉得"每条都有道理"——想知道为什么的人 |

### 第八篇：智能体协作

| 维度 | 内容 |
|------|------|
| **核心问题** | 三个智能体各自独立构建，但不约而同做出了同一个架构选择——不让 LLM 做决策。这是巧合还是必然？ |
| **基本判断** | 不是巧合。有限决策（Bounded Decision-Making）是 2026 年 LLM 能力约束下的最优架构范式 |
| **核心命题** | **不要让今天的 LLM 做明天 AGI 才能做的事。LLM 只填空（生成/转换/理解），决策由确定性系统或人类持有** |
| **印证** | Orchestrator × 如无规矩勿增操作 / RAG Assistant × 如无能力勿增限制 / Structured Writer × 如无资源勿增承诺 |
| **一句话** | 以"现在的 LLM 能做什么"为参考系，而非"未来的 LLM 应该能做什么" |
| **代表工具** | Orchestrator + RAG Assistant + Structured Writer（三个智能体的共同框架） |
| **读它的人** | 构建需要 LLM 参与的智能体系统，想知道"LLM 应该承担什么角色"的人 |

### 08a：操作层——前置规范 > 后置验证

| 维度 | 内容 |
|------|------|
| **核心问题** | 范式层回答了"谁做决策"，但没回答"填空之后，怎么做到第一次就做对" |
| **基本判断** | 后验证（检测→定位→修复→回归）是概率衰减的补救；前置规范把错误空间封堵在生成时刻。LLM 是概率生成器，"必须一次做对"的环节天然与它相悖 |
| **核心命题** | **前置规范 > 后置验证。做对 = 首次尝试即符合契约的概率，不是"出错后能修回来"。分工先于名分，监督前移、试错留白** |
| **四个论点** | 最小尝试次数（一次做对的概率结构）/ 监督的时间非对称性（越到后期越不可能逃避）/ 错误空间前移封堵（validate 死代码铁证）/ 分工先于名分（agent 定义之争的消解） |
| **一句话** | 先分工，后名分；先封堵，后验证；监督前移，试错留白 |
| **代表工具** | Structured Writer 的引用后处理（cite 管线的确定性实现，validate 被淘汰） |
| **读它的人** | 第八篇之后想知道"填空之后如何保证正确性"、以及正在争论"这算不算真正的 agent"的人 |

## 八篇的阅读顺序

**推荐阅读顺序：第一篇 → 第二篇 → 第三篇 → 第四篇 → 第五篇 → 第六篇 → 第七篇 → 第八篇 → 08a**

- 第一篇是最容易入手的——它从问题出发：LLM不听话。这个现象谁都能理解，不需要任何前置知识
- 第二篇需要理解"因为LLM不可靠，所以不能靠LLM自觉来保证结构一致性"——这是第一篇的结论。所以第二篇依赖第一篇
- 第三篇需要理解前两篇构成了一个对"技能"的约束体系——然后问"谁约束这个约束体系"——所以第三篇依赖前两篇
- **08a 依赖第八篇**——它回答的是第八篇之后的下一个问题："填空之后怎么保证第一次就做对"。没有第八篇的有限决策范式，08a 的"分工先于名分"就没有支点
- 第四篇需要理解前三篇全部——编排层是在前三篇"单技能正确性"的基础上，解决"多技能如何组合"
- 第五篇是第四篇的一个具体实现案例——用编排范式构建一个独立的知识库智能体。可在第四篇之后独立阅读
- 第六篇是第四篇的工程实现——用链驱动架构将编排范式落地为可执行代码。可在第四篇之后阅读
- **第七篇统摄所有前六篇**——它不增加方法论维度，而是回答为什么前六篇的每一个"加法"都不违反四条"减法"原则。建议在通读前六篇之后阅读，起到"往回看"的收束作用
- **第八篇是收束篇（范式层）**——它不再重复前七篇的机制论证，而是把三个独立构建的智能体的共同架构选择归结为有限决策范式，作为智能体协作方法论的范式层收束。但它不是系列的终点：智能体协作主题的后续沉淀进入 **08 系列**（08 范式层 / 08a 操作层 / 未来同主题扩展），而非全部砸进第八篇单篇
- **08a 是操作层**——第八篇回答"谁做决策"（范式层），08a 回答"怎么做到第一次就做对"（操作层）：前置规范 > 后置验证、最小尝试次数、分工先于名分、监督的时间非对称性。它从第八篇出发，向"正确性的概率结构"推进，是 2026-08-02 新增的独立篇章

**如果时间有限，只读每篇的"核心命题"和"基本判断"段落**——这些段落包含了全部前提假设和结论。其余章节是论证和展开。

### 领域工具（共14个）

这些技能是方法论的应用案例，展示了"填空题/选择题"模式在具体领域的落地：

| 类别 | 技能 | 体现的模式 |

## 这个方法论体系能做什么

- **约束LLM的执行行为**：不让LLM自由输出，只让它填值
- **统一多技能的结构**：20个技能，一套元数据声明，同一个校验规则
- **验证方法论本身**：审计引擎审计自己，执行框架约束自己
- **保证修改不退化**：备份→基线→修改→校验→双零准入→版本同步
- **编排多技能协作**：用确定性 Pipeline 替代 ReAct 循环，让 LLM 只做格式转换
- **分层注入与原子容错长程生成**：20+ 轮依赖型 LLM 调用管线中，容错不是 retry 而是 isolation

## 这个方法论体系不能做什么

- **保证方法论规则本身的正确性**：规则是人（和LLM）定的，可能定错
- **保证跨系统迁移有效性**：这套方法论在WorkBuddy生态中验证，不一定适用于所有平台
- **防止"自己降低自己的标准"**：恶意修改方法论工具的审计标准，可以绕过自举验证
- **代替领域专业知识**：分析数据的、画流程图的、做颜色转换的——方法论不替代这些领域的专业能力
- **消除 LLM 作为胶水的不确定性**：即使把 LLM 降级为"胶水"，它仍然是概率模型——格式转换仍可能出错
