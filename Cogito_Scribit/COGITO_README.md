# Cogito Scribo — 方法论体系总览

> **Cogito, Scribo.** (我思，故我写。)
>
> 这里是 wUwproject 20 个重型技能构建过程中沉淀的方法论体系。三篇文章、一个闭环、一种架构范式。

---

## 体系全景

```
                    ┌─────────────────────────┐
                    │   第二篇：构建时契约      │
                    │   "什么是正确的结构"      │
                    │   五层声明 + 接入校验      │
                    └──────────┬──────────────┘
                               │ 提供判断标准
                               ↓
                    ┌─────────────────────────┐
                    │   第一篇：运行时硬中断     │
                    │   "执行时怎么不出错"      │
                    │   步骤原子化 + 硬约束阻断   │
                    └──────────┬──────────────┘
                               │ 提供自举证明
                               ↓
                    ┌─────────────────────────┐
                    │   第三篇：递归自举        │
                    │   "方法论怎么确保自己"    │
                    │   自我审计 + 自我约束     │
                    └──────────┬──────────────┘
                               │ 回到起点，验证契约
                               ↓
                    ┌─────────────────────────┐
                    │       方法论完整闭环       │
                    └─────────────────────────┘
```

三篇之间的关系是**环形依赖**，不是线性递进：

```
第二篇（契约） → 第一篇（硬中断需要契约提供"什么是对的"的判断标准）
第一篇（硬中断） → 第三篇（自举需要硬中断来保障自审不被打断）
第三篇（自举） → 第二篇（自举链的起点是契约系统，自举的终点是"契约也适用于定义契约的工具自身"）
```

**没有哪一篇是"最终权威"。每一篇都依赖另外两篇来完成自己的功能。**

## 三篇各自解决的问题

### 第一篇：运行时硬约束

| 维度 | 内容 |
|------|------|
| **核心问题** | LLM在多步骤执行中反复偏离预期——格式不一致、路径写错、状态丢失 |
| **基本判断** | 这不是bug，是LLM概率生成机制的固有特性。不可能通过"更好的Prompt"解决 |
| **核心命题** | **在多步骤确定性流程中，LLM的"自觉"是负资产** |
| **5个原理** | 步骤原子化 → 硬中断替代软约束 → 双通道信号 → 阻断→挂起→恢复 → 五层准入门槛 |
| **一句话** | 把LLM的活动空间压缩到"填空题/选择题"的狭窄闸口内，用代码级硬中断在边界处拦截越界行为 |
| **代表技能** | triphasic-execution |
| **读它的人** | 想知道"为什么LLM总是不按我写的步骤执行"的人 |

### 第二篇：构建时契约

| 维度 | 内容 |
|------|------|
| **核心问题** | N个技能有N种结构，上层调度器无法统一识别，运行时硬中断没有判断依据 |
| **基本判断** | 构建阶段缺乏强制性的结构规范，问题根源不是"写错了"而是"没有统一承诺" |
| **核心命题** | **构建时用五层契约锁定每个技能的"正确形态"** |
| **5个层次** | L1身份 → L2触发条件 → L3行为约束 → L4接口 → L5数据声明 |
| **一句话** | 构建时用五层契约锁定结构，让硬中断有据可依 |
| **代表技能** | skill-standardization |
| **读它的人** | 想统一管理多个技能、让它们结构一致的人 |

### 第三篇：递归自举

| 维度 | 内容 |
|------|------|
| **核心问题** | 方法论工具（审计引擎、执行框架、同步工具）由谁约束？它们自己能通过自己定义的规则吗？ |
| **基本判断** | 方法论不能只约束"其他东西"而豁免自己。否则方法论体系存在特权层，特权层不可验证 |
| **核心命题** | **方法论不约束自己，就没有约束任何东西的资格** |
| **5个原理** | 自我审计 → 自我约束 → 自我契约 → 统一元数据结构 → 自举链有穷性 |
| **一句话** | 自举不证明方法论正确，只证明方法论不自欺 |
| **代表技能** | 所有7个元方法论工具（skill-standardization / triphasic-execution / git-sync / skill-function-test / skill-sub / semantic-split / universal-file-ops） |
| **读它的人** | 看完前两篇后问"谁来保证这套体系不被破坏"的人 |

## 三篇的阅读顺序

**推荐阅读顺序：第一篇 → 第二篇 → 第三篇**

- 第一篇是最容易入手的——它从问题出发：LLM不听话。这个现象谁都能理解，不需要任何前置知识
- 第二篇需要理解"因为LLM不可靠，所以不能靠LLM自觉来保证结构一致性"——这是第一篇的结论。所以第二篇依赖第一篇
- 第三篇需要理解前两篇构成了一个对"技能"的约束体系——然后问"谁约束这个约束体系"——所以第三篇依赖前两篇

**如果时间有限，只读三篇的"一、对XY的基本判断"和"核心命题"段落**就够了——这三个段落包含了三篇的全部前提假设和结论。其余章节是论证和展开。

## 这个方法论体系能做什么

- **约束LLM的执行行为**：不让LLM自由输出，只让它填值
- **统一多技能的结构**：20个技能，一套元数据声明，同一个校验规则
- **验证方法论本身**：审计引擎审计自己，执行框架约束自己
- **保证修改不退化**：备份→基线→修改→校验→双零准入→版本同步

## 这个方法论体系不能做什么

- **保证方法论规则本身的正确性**：规则是人（和LLM）定的，可能定错
- **保证跨系统迁移有效性**：这套方法论在WorkBuddy生态中验证，不一定适用于所有平台
- **防止"自己降低自己的标准"**：恶意修改方法论工具的审计标准，可以绕过自举验证
- **代替领域专业知识**：分析数据的、画流程图的、做颜色转换的——方法论不替代这些领域的专业能力

## 维护说明

- 本目录（`Cogito_Scribit/`）由WorkBuddy在主人思淼的指导下撰写和维护
- 三篇文章的修改应遵循第三篇"递归自举"的原则：修改方法论的工具应该被方法论约束
- 新增方法论文章需满足：它所覆盖的维度不能是已有三篇中任意一篇的"边界"或"不解决的问题"
- 领域文章（如"drawiodo中的方法论体现"）不受此限制，它们是对方法论的应用展示而不是方法论本身
