# Cogito Scribo — 方法论体系总览

> **Cogito, Scribo.** (我思，故我写。)
>
> 这里是 wUwproject 重型技能构建过程中沉淀的方法论体系。四篇文章、一个闭环、一种架构范式。

---

## 体系全景

```
                    ┌─────────────────────────┐
                    │   第二篇：构建时契约      │
                    │   "什么是正确的结构"      │
                    │   五层声明 + 接入校验      │
                    └──────────┬──────────────┘
                               │ 提供判断标准
                               ↓
                    ┌─────────────────────────┐
                    │   第一篇：运行时硬中断     │
                    │   "执行时怎么不出错"      │
                    │   步骤原子化 + 硬约束阻断   │
                    └──────────┬──────────────┘
                               │ 提供自举证明
                               ↓
                    ┌─────────────────────────┐
                    │   第三篇：递归自举        │
                    │   "方法论怎么确保自己"    │
                    │   自我审计 + 自我约束     │
                    └──────────┬──────────────┘
                               │ 回到起点，验证契约
                               ↓
                    ┌──────────────────────────────────┐
                    │   第四篇：编排范式                │
                    │   "多个技能怎么组合"              │
                    │   Pipeline 编排 + LLM 当胶水      │
                    └──────────┬───────────────────────┘
                               │ 是前三篇的调度层：在编排层面统一应用
                               ↓
                    ┌─────────────────────────┐
                    │       方法论完整闭环       │
                    └─────────────────────────┘
```

四篇之间的关系：

```
第二篇（契约） → 第一篇（硬中断需要契约提供判断标准）
第一篇（硬中断） → 第三篇（自举需要硬中断来保障自审不被打断）
第三篇（自举） → 第二篇（自举链的起点是契约系统）
前三篇（单技能正确性） → 第四篇（编排层需要契约+硬中断+自举来保障多技能协作的正确性）
```

## 三篇各自解决的问题

### 第一篇：运行时硬约束

| 维度 | 内容 |
|------|------|
| **核心问题** | LLM在多步骤执行中反复偏离预期——格式不一致、路径写错、状态丢失 |
| **基本判断** | 这不是bug，是LLM概率生成机制的固有特性。不可能通过"更好的Prompt"解决 |
| **核心命题** | **在多步骤确定性流程中，LLM的"自觉"是负资产** |
| **5个原理** | 步骤原子化 → 硬中断替代软约束 → 双通道信号 → 阻断→挂起→恢复 → 五层准入门槛 |
| **一句话** | 把LLM的活动空间压缩到"填空题/选择题"的狭窄闸口内，用代码级硬中断在边界处拦截越界行为 |
| **代表技能** | triphasic-execution |
| **读它的人** | 想知道"为什么LLM总是不按我写的步骤执行"的人 |

### 第二篇：构建时契约

| 维度 | 内容 |
|------|------|
| **核心问题** | N个技能有N种结构，上层调度器无法统一识别，运行时硬中断没有判断依据 |
| **基本判断** | 构建阶段缺乏强制性的结构规范，问题根源不是"写错了"而是"没有统一承诺" |
| **核心命题** | **构建时用五层契约锁定每个技能的"正确形态"** |
| **5个层次** | L1身份 → L2触发条件 → L3行为约束 → L4接口 → L5数据声明 |
| **一句话** | 构建时用五层契约锁定结构，让硬中断有据可依 |
| **代表技能** | skill-standardization |
| **读它的人** | 想统一管理多个技能、让它们结构一致的人 |

### 第三篇：递归自举

| 维度 | 内容 |
|------|------|
| **核心问题** | 方法论工具（审计引擎、执行框架、同步工具）由谁约束？它们自己能通过自己定义的规则吗？ |
| **基本判断** | 方法论不能只约束"其他东西"而豁免自己。否则方法论体系存在特权层，特权层不可验证 |
| **核心命题** | **方法论不约束自己，就没有约束任何东西的资格** |
| **5个原理** | 自我审计 → 自我约束 → 自我契约 → 统一元数据结构 → 自举链有穷性 |
| **一句话** | 自举不证明方法论正确，只证明方法论不自欺 |
| **代表技能** | 所有7个元方法论工具（skill-standardization / triphasic-execution / git-sync / skill-function-test / skill-sub / semantic-split / universal-file-ops） |
| **读它的人** | 看完前两篇后问"谁来保证这套体系不被破坏"的人 |

### 第四篇：编排范式

| 维度 | 内容 |
|------|------|
| **核心问题** | N个技能如何组合成流水线？LLM在编排中的角色应该是什么？ |
| **基本判断** | 多技能编排不能用 ReAct 循环——LLM 做路径决策导致不可复现、不可审计 |
| **核心命题** | **LLM 应从"大脑"降级为"胶水"，只做格式转换，不做路径决策** |
| **5个原理** | 路径确定性 → LLM 降级 → 固化>调用 → 可选不强制 → 审查不修改 |
| **一句话** | 技能是积木，编排是图纸，LLM 是胶水 |
| **代表工具** | Orchestrator（Skill Pipeline Orchestrator） |
| **读它的人** | 有多个技能，想让它们协作完成任务但不想用 ReAct 的人 |

### 第五篇：本地知识库智能体

| 维度 | 内容 |
|------|------|
| **核心问题** | 复杂知识库问答中，单轮 RAG 检索总是遗漏关键侧面——实体丢失、属性模糊、上下文孤岛 |
| **基本判断** | 问题不是检索太弱，而是检索之前没有分解。用户问题是一个复合指令，不是检索查询 |
| **核心命题** | **LLM 应承担"查询策略规划者"——将问题分解为 entities + attrs 元组，穷举组合后多路检索** |
| **5个原理** | LLM 分解 → 穷举组合 → 多路独立检索 → SM3 去重合并 → LLM 综合回答 |
| **一句话** | 切片检索替代单轮 RAG，被动的知识库变成了主动的检索阵列 |
| **代表工具** | RAG Assistant |
| **读它的人** | 用 RAG 但总是查不全、想做多知识库数据埋点分析的人 |

## 五篇的阅读顺序

**推荐阅读顺序：第一篇 → 第二篇 → 第三篇 → 第四篇 → 第五篇**

- 第一篇是最容易入手的——它从问题出发：LLM不听话。这个现象谁都能理解，不需要任何前置知识
- 第二篇需要理解"因为LLM不可靠，所以不能靠LLM自觉来保证结构一致性"——这是第一篇的结论。所以第二篇依赖第一篇
- 第三篇需要理解前两篇构成了一个对"技能"的约束体系——然后问"谁约束这个约束体系"——所以第三篇依赖前两篇
- 第四篇需要理解前三篇全部——编排层是在前三篇"单技能正确性"的基础上，解决"多技能如何组合"
- 第五篇是第四篇的一个具体实现案例——用编排范式构建一个独立的知识库智能体。可在第四篇之后独立阅读

**如果时间有限，只读每篇的"核心命题"和"基本判断"段落**——这四段包含了全部前提假设和结论。其余章节是论证和展开。

## 第四、五篇的已知盲区

以下是在撰写第四、五篇时识别到的、仍在思考中的问题：

| 问题 | 描述 | 状态 |
|------|------|------|
| **固化粒度的精确标准** | 文章提出了"固化>调用"原则，但未给出精确的决策阈值——"何时算足够确定性以固化" | ⚠️ 需细化 |
| **编排层自举** | 编排器使用固化算法完成确定性任务——但它本身是否也需要自我审计？目前的固化算法没有自检机制 | 📌 待验证 |
| **LLM 粘合的边界** | 粘合层调用 LLM 做格式转换，但 LLM 可能"理解过度"——把 A 的输出改成了与 B 所需格式无关的内容 | 📌 待设计 |
| **跨流水线状态共享** | 当前设计是单流水线执行，没有跨流水线的状态/数据共享机制 | 📌 后续版本 |
| **切片数量爆炸** | 多实体 × 多属性 × 关系衍生 → 切片数量多项式增长，大 prompt 使 tokens 成本上升 | 📌 需限流策略 |
| **路由精度上限** | 语义路由（FallbackRouter）依赖 reranker 模型的边界，当 KB 数量 > 10 时路由精度下降 | 📌 需分层路由 |

## 这个方法论体系能做什么

- **约束LLM的执行行为**：不让LLM自由输出，只让它填值
- **统一多技能的结构**：20个技能，一套元数据声明，同一个校验规则
- **验证方法论本身**：审计引擎审计自己，执行框架约束自己
- **保证修改不退化**：备份→基线→修改→校验→双零准入→版本同步
- **编排多技能协作**：用确定性 Pipeline 替代 ReAct 循环，让 LLM 只做格式转换

## 这个方法论体系不能做什么

- **保证方法论规则本身的正确性**：规则是人（和LLM）定的，可能定错
- **保证跨系统迁移有效性**：这套方法论在WorkBuddy生态中验证，不一定适用于所有平台
- **防止"自己降低自己的标准"**：恶意修改方法论工具的审计标准，可以绕过自举验证
- **代替领域专业知识**：分析数据的、画流程图的、做颜色转换的——方法论不替代这些领域的专业能力
- **消除 LLM 作为胶水的不确定性**：即使把 LLM 降级为"胶水"，它仍然是概率模型——格式转换仍可能出错

- 领域文章（如"drawiodo中的方法论体现"）不受此限制，它们是对方法论的应用展示而不是方法论本身
