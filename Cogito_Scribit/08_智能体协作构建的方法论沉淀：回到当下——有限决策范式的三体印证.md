# 智能体协作构建的方法论沉淀：回到当下——有限决策范式的三体印证

> 把真正的选择权拿回人类手中或未来的AGI中，而不是用当下去幻想未来，用梦想来要求现实。
> 更新：2026-07-26（启动篇），2026-07-29（补充：模板锚点 + 引用后处理），2026-08-02（操作层独立为 08a：前置规范 > 后置验证）

---

## 一、背景：三条独立路径的同一个发现

### 1.1 三个独立智能体

Orchestrator、RAG Assistant、Structured Writer 是三个独立构建的智能体系统，解决三个完全不同的问题：

| 智能体 | 要解决的问题 | 构建起点 |
|--------|------------|---------|
| **Orchestrator** | 多技能如何编排执行 | ReAct 循环不可复现、不可审计 |
| **RAG Assistant** | 复杂知识库查不全 | 单轮 RAG 丢失实体/属性/关系维度 |
| **Structured Writer** | 长文写作前重后轻、中途截断 | LLM 在篇章尺度控制力衰减 |

三个智能体的构建时间不同、解决的问题不同、技术栈不同——但它们在架构层面做出了同一个基本判断。

### 1.2 同一个发现

在三个独立的设计过程中，每隔一段时间就会遇到同一个问题：**"要不要让 LLM 来做这个决策？"**

| 智能体 | 那个具体的选择 | 看起来合理的理由 |
|--------|-------------|----------------|
| **Orchestrator** | 要不要让 LLM 决定下一步执行什么技能？ | "LLM 能理解上下文，应该能自行编排步骤顺序" |
| **RAG Assistant** | 要不要让 LLM 决定查知识库的哪些维度？ | "LLM 理解了问题，应该知道找什么资料" |
| **Structured Writer** | 要不要让 LLM 决定文章的结构和顺序？ | "LLM 理解了主题，应该能规划文章框架" |

三个答案都是：**不让。**

不是基于不信任，而是基于同一个观察：**LLM 做出正确路径决策的概率，远低于它正确填空的概率。**

同一个选择，做了三次。这就是"有限决策"范式的起点。

---

## 二、核心命题

> **在确定的边界内让 LLM 填空，在确定的边界外由确定性系统决策。LLM 的能力边界不是假设出来的，是测量出来的。**

### 2.1 基本判断

| 维度 | 让 LLM 决策 | 让 LLM 填空 |
|------|-----------|-----------|
| **可靠性** | 路径复现率 < 50% | 500 字内容准确率 > 90% |
| **可审计性** | LLM 的路径选择无显式记录 | 填空的输入输出 schema 可记录 |
| **错误范围** | 路径错误可能导致连锁失败 | 填空错误局限在一个单元格内 |
| **调试成本** | 需要回溯 LLM 的思维链 | 只需要校验输入输出 schema |
| **升级影响** | 换模型可能导致路径变化 | 换模型不影响填空的边界定义 |

| 智能体 | LLM 填空的内容 | 确定性锚点 | 边界划定者 |
|--------|--------------|-----------|-----------|
| **Orchestrator** | 当前步骤的输出文本 | Pipeline 链（seq/par/loop） | 编排器 |
| **RAG Assistant** | entities/attrs/rel 的语义标注 | 穷举组合策略（N×M 切片） | 算法 |
| **Structured Writer** | 子结构的 500 字正文 | JSON 大纲 | 用户 + 大纲规划器 |

三个填空场景的 schema 不同，但结构相同：LLM 在确定的输入约束和确定输出格式之间填充内容。

### 2.2 核心命题的分解

**命题 A：LLM 的可靠性与"决策半径"负相关**

LLM 在 500 字内填空的准确率远高于在 5000 字范围内做结构规划。这不是模型大小的问题——三个智能体的构建过程中积累的一致观察：让 LLM 做路径选择（"下一步做什么"）时，出错率远高于让它做内容填充（"填这个槽位"）。

这意味着：**可靠性要求越高的地方，LLM 的决策半径应该越小。** 三个智能体各自把 LLM 的决策半径压缩到了它确实能稳定工作的范围内。

**命题 B：确定性锚点不是限制，是杠杆**

Pipeline 链、穷举组合策略、JSON 大纲——这些确定性锚点不是对 LLM 的限制，而是让 LLM 的填空能力得以发挥的杠杆。没有链，LLM 不知道该执行什么；没有穷举策略，LLM 不知道查哪些维度；没有大纲，LLM 不知道文章结构。但有了锚点之后，LLM 在这些结构内的工作质量是可预测的。

**命题 C：三个填空域的边界不重叠**

Orchestrator 的填空域是"一个技能步骤的输出"，RAG Assistant 的填空域是"一个查询切片的语义标注"，Structured Writer 的填空域是"一个子结构的正文"。这三个域不重叠、不冲突、不包含关系。它们互补：

```
Orchestrator（执行链）
  ↓ 调用技能
RAG Assistant（检索知识库） → 提供材料
  ↓ 提供上下文
Structured Writer（写作）
```

Structured Writer 调用 RAG Assistant 获取材料，这是编排层（Orchestrator 模式）调用领域智能体（RAG Assistant 模式）的具体实现。三个智能体可以串联使用，形成完整的"检索→理解→生成"管线。

**命题 D："回到当下"不是战术选择，是架构原则**

"回到当下"的含义是：**以今天 LLM 的能力测量结果为设计依据，不以未来的可能性为设计假设。**

这不是保守。三个智能体都在"当下能力"的边界内交付了高质量的工作。Orchestrator 的链驱动执行正确率 > 95%，RAG Assistant 的组合检索覆盖度比单轮 RAG 提高 3 倍，Structured Writer 的 30% 调用失败率下仍然交付完整文章。这些成果来自对"现在 LLM 能做什么"的确切理解，而非对"将来 LLM 应该能做什么"的乐观预期。

## 三、三智能体的填空域设计

### 3.1 Orchestrator：步骤填空 × 链确定性

**确定性锚点**：Pipeline 链。链在编排时确定（seq/par/loop），执行时不可修改。

**LLM 填空内容**：当前步骤的输出文本。LLM 看到的是"技能描述 + 参数 + 上一步输出"，输出的是"当前步骤的结果"。

```
链定义：
  [seq] 技能A
  [seq] 技能B
  [par] 技能C, 技能D

执行时 LLM 的角色：
  步骤 A：LLM(技能A描述 + 参数) → 输出 A
  步骤 B：LLM(技能B描述 + 参数 + 输出 A) → 输出 B
  步骤 C：LLM(技能C描述 + 参数 + 输出 A+B) → 输出 C  （并行）
  步骤 D：LLM(技能D描述 + 参数 + 输出 A+B) → 输出 D  （并行）
```

**边界划定者**：编排器（以及使用编排器的用户）。用户编排链，系统执行链，LLM 只填每步的输出。

**对应原则（第七条）**：如无规矩，勿增操作——链中的每个步骤必须有定义的 mode（seq/par/loop）和参数，缺少任何一项都不执行。

### 3.2 RAG Assistant：查询分解填空 × 穷举确定性

**确定性锚点**：穷举组合策略。所有 entities × attrs 组合都查一遍，不预判哪组最优。

**LLM 填空内容**：entities/attrs/rel 的语义标注。LLM 从用户问题中提取实体、属性、关系三个维度的信息。这些标注的质量决定了后续检索的覆盖度。

```
用户问题："三个代表与无为而治的异同"
  ↓
LLM 填空 → entities="三个代表重要思想,老子无为而治"
             attrs="核心观点,相同点,不同点"
             rel="思想渊源比较"
  ↓
穷举展开（确定性算法，LLM 不参与）：
  第一层：entity 单独 → "三个代表重要思想", "老子无为而治"
  第二层：entity×attr → "三个代表重要思想 核心观点", "老子无为而治 不同点" ...
  第三层：两两配对×rel → "三个代表重要思想 老子无为而治 思想渊源比较" ...
  ↓
多路检索（每个切片独立）
  ↓
SM3 去重 → 综合回答
```

**边界划定者**：算法。展开策略（穷举组合）、去重策略（SM3）、检索流程（路由→检索→reranker→NLI）全部由算法确定，LLM 不参与。

**对应原则（第七条）**：如无能力，勿增限制——LLM 在分解实验中的准确率 > 90% 证明它确实有这个能力，所以"先分解再检索"是合法约束。如果准确率 < 50%，这条约束就不该存在。

### 3.3 Structured Writer：段落填空 × 大纲确定性

**确定性锚点**：模板 + JSON 大纲 + 引用后处理。

模板定义了文章的 meta+content 结构（内置或用户自定义，代码级只读保护），大纲定义了节结构、子结构、字数、顺序、勾选状态，引用后处理将 LLM 的自然语言标记（`引用自{文件名}`）通过确定性正则替换为编号 `[N]` 并自动生成参考文献节。模板和引用后处理是锚点的两层扩展——模板约束文章框架，引用后处理约束输出格式。

**LLM 填空内容**：每个子结构的 500 字正文 + 引用标记。LLM 看到的是标题 + 写作要点 + 前文上下文 + 两级 RAG 材料 + 文档元数据，输出的是该子结构的正文（含 `引用自{文件名}` 标记）。

```
模板定义（用户选择，内置只读 / 用户自定义可编辑）：
  meta: [标题, 作者, 单位, ...]
  content: [摘要(leaf), 引言(section), 方法(section), ...]

大纲定义（生成或用户编排时确定）：
  节 1：引言
    ├── 子结构 1_1：技术演进背景（400 字）
    ├── 子结构 1_2：研究动机与目标（400 字）
    └── 子结构 1_3：文章结构与安排（400 字）

执行时 LLM 的角色：
  子结构 1_1：LLM(节RAG + 子结构RAG + 文档元数据 + 前文) → 400 字正文（含引用标记）
  子结构 1_2：LLM(新子结构RAG + 累积文档元数据 + 前文(含 1_1)) → 400 字正文
  ...
  所有节完成后 → 确定性引用后处理（LLM 不参与）:
    正则扫描 → 去重编号 → [N] 替换 → 参考文献节自动填充
```

**文档元数据全局累积**：各节 RAG 查询返回的文档元数据（标题/作者）累积到全局字典，后面任何节都可以引用前面节见过的文档。语义检索内容逐节独立，元数据全文共享。

**边界划定者**：用户 + 模板系统 + 大纲规划器。用户选择模板（内置只读边界不可突破），通过交互式大纲调整勾选/排序/字数/RAG，大纲规划器（也是 LLM）生成初始结构——但规划器的输出可被用户否决。模板的引用字段配置决定是否启用引用后处理。

**对应原则（第七条）**：如无资源，勿增承诺——不承诺每篇文章都完整输出，但承诺"在可用资源内尽力交付"。失败子结构被隔离，不影响后续。引用标记缺失不阻断全文生成，仅影响参考文献节。

## 四、三体印证

### 4.1 三连线不重叠

三个智能体的填空域划定了一条清晰的边界线：

| 维度 | Orchestrator | RAG Assistant | Structured Writer |
|------|-------------|---------------|-------------------|
| **LLM 填什么** | 步骤输出 | 实体/属性/关系标注 | 子结构正文 + 引用标记 |
| **锚点** | Pipeline 链 | 穷举组合策略 | 模板 + JSON 大纲 + 引用后处理 |
| **失败隔离** | 步骤级重试/跳过 | 切片级独立 | 子结构级隔离 |
| **边界划定者** | 编排器/用户 | 算法 | 用户 + 模板系统 + 规划器 |
| **输出粒度** | 一段文本 | 3 个字段 | 500 字段落 |

这三条线不重叠——Orchestrator 的填空域是"当前步骤"，RAG Assistant 的填空域是"查询语义"，Structured Writer 的填空域是"段落内容"。它们可以各自独立运行，也可以串联使用。

### 4.2 与第七条的四原则对应

| 原则 | LLM 不做的 | 对应智能体 | 具体体现 |
|------|-----------|-----------|---------|
| **无规矩勿增操作** | 不做路径决策 | Orchestrator | 链定义执行顺序，LLM 只填每步输出 |
| **无能力勿增限制** | 不做超能力承诺 | RAG Assistant | LLM 做分解（已验证能力），不做路由（由算法） |
| **无资源勿增承诺** | 不做交付保证 | Structured Writer | 子结构失败隔离，不承诺完整输出 |
| **无必要勿增实体** | 统摄全局 | 三个智能体 | 不增加第四个做同样的事 |

### 4.3 已知盲区

| 问题 | 描述 | 状态 |
|------|------|------|
| **能力边界的时效性** | LLM 版本升级后填空域可能扩大。当前的边界划分在三个月后是否仍然最优？ | 📌 需定期验证 |
| **三条线的串联接口** | 三个智能体可串联但当前没有统一协议标准 | 📌 后续版本 |
| **填空 schema 的通用化** | 三种填空（步骤/标注/正文）是否有统一的 schema 描述方式 | 📌 待设计 |
| **锚点的自举验证** | Pipeline 链、穷举策略、JSON 大纲——锚点本身如何验证其正确性？ | 📌 待论证 |

---

## 五、一句话总结

> 把真正的选择权拿回人类手中，或等 AGI 来了再给它。在此之前，LLM 只填空，不决策。这是对"现在"的尊重，也是对"未来"的预留——等真正的 AGI 出现了，把线画宽一点就好。
