# 智能体协作构建的方法论沉淀：回到当下——有限决策范式的三体印证

> 别让今天的 LLM 做明天的 AGI 才能做的事。把选择权交还给确定性系统——或等 AGI 来了再说。
> 更新：2026-07-26（启动，后续在本篇内扩展）

---

## 一、背景：三个独立智能体的同一个困境

### 1.1 三条独立的构建路径

Orchestrator、RAG Assistant、Structured Writer 是三个独立构建的智能体，解决三个不同的问题：

| 智能体 | 核心问题 | 解决策略 |
|--------|---------|---------|
| **Orchestrator** | 多技能如何编排执行 | 链驱动 Pipeline 替代 ReAct 循环 |
| **RAG Assistant** | 复杂知识库查不全 | 组合式穷举检索替代单轮 RAG |
| **Structured Writer** | 长文写作前重后轻 | 子结构逐段生成替代整篇输出 |

这三个智能体的构建时间不同、解决的问题不同、技术栈细节不同——但它们在架构层面做出了同一个基本判断。

### 1.2 同一个基本判断

每个智能体的设计过程中，都遇到了同一个选择：**"要不要让 LLM 来做这个决策？"**

- Orchestrator：要不要让 LLM 决定下一步执行什么技能？
- RAG Assistant：要不要让 LLM 决定如何分解查询？（路由是标准能力，但"先拆解再路由"的策略是 LLM 驱动的）
- Structured Writer：要不要让 LLM 决定文章的结构和顺序？

三个团队（就是同一个人）的答案都是：**不让。**

这个答案不是来自对 LLM 的不信任，而是来自对"当下能力边界"的清醒认知。LLM 在 2026 年的能力边界是：

```
✓ 语义理解（实体识别、意图分类、关系抽取）
✓ 格式转换（自然语言 → JSON、表格、结构化文本）
✓ 受控生成（给定结构和约束，填充内容）
✗ 路径决策（在不确定的环境中做多步规划）
✗ 承诺交付（保证输出可解析、格式正确、长度可控）
✗ 自我修正（识别并修复自己输出的错误）
```

三个智能体的共同设计选择是：**只让 LLM 做它擅长的事，把决策权交还给确定性系统。**

## 二、核心命题

> **不要把今天的 LLM 当作明天的 AGI 来设计。给 LLM 的能力划一条确界线：线内填空，线外决策。决策权由确定性系统或人类持有，LLM 不介入。**

### 2.1 "有限决策"的定义

有限决策（Bounded Decision-Making）是一个架构原则，包含三层含义：

1. **LLM 不做路径决策** — 它不决定"接下来做什么"，只执行预先定义好的步骤
2. **LLM 不做承诺** — 它不保证输出长度、格式、可解析性。系统通过硬约束和容错机制来保障这些
3. **LLM 不自我修正** — 它不纠正自己的错误。错误由上层系统检测并隔离

这三个"不"的代价是：系统需要更多的确定性组件（编排器、状态管理器、错误处理器）。但收益是：LLM 的不可预测性被限制在最小范围内。

### 2.2 基本判断

| 维度 | "让 LLM 多想想"范式 | 有限决策范式 |
|------|-------------------|-------------|
| **LLM 角色** | 决策者 + 执行者 | 填空者（填充预先定义好的槽位） |
| **路径选择** | LLM 自己决定下一步 | 系统预先编排好路径 |
| **错误处理** | LLM 自己修正错误 | 系统隔离错误，LLM 不参与 |
| **输出承诺** | LLM 承诺输出格式和质量 | 系统通过硬约束保障 |
| **扩展方向** | 让 LLM 能做更多事 | 让系统更好地框住 LLM |
| **设计时间参考系** | "未来 LLM 应该能做到" | "现在的 LLM 能做什么" |

有限决策范式的核心不是"限制 LLM"，而是**把 LLM 的活动空间压缩到它当前能力确实覆盖的范围内**。超出这个范围的事，由确定性系统或人类处理。

### 2.3 核心命题的分解

**命题 A：给 LLM 的每个任务都必须是"填空题"**

"填空题"的定义：输入和输出都有明确的 schema。LLM 不决定"填什么"（这是系统决定的），只决定"怎么填"。

- Orchestrator：LLM 填的是"当前步骤的输出"，不决定"当前是什么步骤"
- RAG Assistant：LLM 填的是"查询切片的内容"，不决定"查哪些切片"
- Structured Writer：LLM 填的是"一个子结构的正文"，不决定"写哪个子结构"

三种填空题的 schema 维度不同，但结构相同——输入有 schema（约束 + 上下文），输出有 schema（格式 + 字数），LLM 在两者之间填空。

**命题 B：系统的复杂度必须适配 LLM 的不可靠性，而非相反**

当 LLM 的输出不可靠时（输出空内容、格式错误、截断），系统的反应不应该是"让 LLM 修复自己"，而应该是"在 LLM 输出到达用户之前拦截并处理"。

这个命题在三个智能体中的实现：

- Orchestrator：步骤失败时重试/跳过，不依赖 LLM 意识到自己失败了
- RAG Assistant：切片查询失败时不影响其他切片，不依赖 LLM 调整查询策略
- Structured Writer：子结构空输出时跳过，不依赖 LLM 补充内容

**命题 C：确定性与 LLM 的边界由"能力证据"而非"能力假设"决定**

不要在 LLM 证明它能做到某件事之前，假设它能做到。

这条命题来自"如无能力，勿增限制"原则——它要求每个"让 LLM 负责的事"都要有实验或观察证据，证明 LLM 在当前版本下确实能稳定完成。

在三个智能体构建过程中积累的证据：

| 证据 | 来源 | 结论 |
|------|------|------|
| LLM 在 500 字内格式错误率 < 2%，5000 字 > 15% | Structured Writer 实验 | 子结构粒度 400-600 字 |
| LLM 做实体/属性分解的准确率 > 90% | RAG Assistant 实验 | LLM 可以承担查询策略规划 |
| LLM 做路径决策的复现率 < 50% | Orchestrator 实验 | 路径必须由编排器决定 |

**命题 D：三个"不"对应三条原则**

| 原则（第七条） | LLM 不做的 | 对应的智能体 |
|--------------|-----------|------------|
| **如无规矩，勿增操作** | 不做路径决策 | Orchestrator |
| **如无能力，勿增限制** | 不做超能力承诺 | RAG Assistant |
| **如无资源，勿增承诺** | 不做交付承诺 | Structured Writer |

第四条原则 **"如无必要，勿增实体"** 统摄全部——这三个智能体不是"为了用 LLM 而造"的实体，每个都解决了不可替代的问题。不增加第四个智能体去做同样的事。

## 三、三智能体对四原则的具体印证

### 3.1 Orchestrator × 如无规矩，勿增操作

Orchestrator 的核心设计是"没有自由操作"——每个技能调用必须预先编排到 Pipeline 中，LLM 不决定调用哪个技能。

这条原则在 Orchestrator 中的具体体现：

- **无规则不执行**：每个 Pipeline 节点必须有 mode（seq/par/loop）和参数，缺少任何一项都不执行
- **无契约不接入**：每个技能必须通过 skill-sub 的黏连检查才能进入 Pipeline，不满足契约的技能不会出现在可选列表中
- **无路径不推进**：LLM 不参与路径选择，路径在编排时已经确定。执行时 LLM 只填当前步骤的输出

### 3.2 RAG Assistant × 如无能力，勿增限制

RAG Assistant 的核心约束是"先分解再检索"——这条约束的合法性来自 LLM 确实有能力做实体/属性分解。

这条原则在 RAG Assistant 中的具体体现：

- **能力证据驱动限制**：没有 LLM 分解实验的数据支撑，不会强制要求"先分解再检索"
- **限制不超出能力**：分解粒度控制在 entities + attrs + rel 三个维度，不要求 LLM 做更深层的语义推理
- **能力不足时有回退**：实体/属性分解失败时降级为普通聊天，不卡死在等待 LLM 输出的状态

### 3.3 Structured Writer × 如无资源，勿增承诺

Structured Writer 不做"输出完整无误文章"的承诺——它承诺的是"在可用资源内尽力交付"。

这条原则在 Structured Writer 中的具体体现：

- **不承诺每个子结构都成功**：资源（token budget、RAG 可用性、LLM 响应状态）不足时跳过子结构
- **不承诺每篇文章都完整**：可用子结构数量不足时交付部分完成版本
- **资源边界显式化**：max_tokens、RAG 超时、续写次数等资源边界都在配置中显式定义，不靠 LLM 自觉把控

## 四、回到当下——有限决策范式的工程意义

### 4.1 为什么是"回到当下"

"回到当下"在这里的含义是：**以今天 LLM 的实际能力为设计原点，不以未来的可能性为假设。**

这不是悲观——恰恰相反。三个智能体都证明了：在明确的能力边界内，LLM 可以产出高质量的工作。乐观应该建立在"现在能做到的事"上，不是"未来可能做到的事"上。

### 4.2 有限决策与第七条的关系

第七条的四条原则是对"加法"的约束——防止方法论体系无限膨胀。

第八篇的有限决策是对"减法"的补充——在约束加法之后，回答"减法应该减到什么程度"：减到 LLM 只做填空题为止。

两者共同构成了一个完整的架构辩证：

```
第七条：不要加不需要的东西（约束加法）
第八篇：不要指望 LLM 做它做不到的事（确定边界）
```

第七条管"加什么"，第八篇管"靠什么"——两篇合在一起才是完整的架构方法论。

### 4.3 已知盲区

| 问题 | 描述 | 状态 |
|------|------|------|
| **能力证据的时效性** | LLM 版本升级后，能力边界可能变化。当前的证据在三个月后是否仍然有效？ | 📌 需持续更新 |
| **填空题 schema 的通用化** | 三种填空题（技能输出/查询切片/正文填充）是否有统一的形式化描述？ | 📌 待设计 |
| **确定性系统的复杂度** | 当确定性组件（状态管理器、错误处理器、编排器）的复杂度超过 LLM 调用代码时，是否应该重新评估分工？ | 📌 待论证 |
| **"未来 AGI"的预留接口** | 如果未来的 AGI 真的能做到路径决策，当前的架构是否需要预留升级路径？ | 📌 暂不考虑 |

---

## 五、一句话总结

> 有限决策不是对 LLM 的不信任，而是对"现在"的尊重。三个智能体各自证明了同一件事：把 LLM 的填空能力用到极致，比让 LLM 做决策更可靠。架构设计的参考系，应该是"现在的 LLM 能做什么"，而不是"未来的 LLM 应该能做什么"。等到 AGI 来了，再给它选择权。
