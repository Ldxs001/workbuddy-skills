# 结构化写作 (Structured Writer) 构建的方法论沉淀：分层注入与原子容错的长程生成范式

> 从"期望 LLM 调用不出错"到"接受出错并隔离错误"——在 20+ 轮依赖型 LLM 调用管线中，容错不是 retry，而是 isolation。
> 更新：2026-07-26（对齐 Structured Writer v0.2.5b4）

---

## 一、背景：长程依赖型 LLM 管线的三个死法

### 1.1 "调用 LLM → 得到结果"的隐含假设

在大多数 LLM 应用中，对 LLM 的调用是独立的、一次性的：给一个 prompt，得到一个回答，交互结束。

Structured Writer 面对的是完全不同的场景——它需要在一个写作会话中连续调用 LLM 20-30 次，每次的输入依赖前一次的输出：

```
子结构 1 → LLM → 输出 → 写入 context_buffer
  → 子结构 2 → LLM（输入含子结构 1 输出）→ 输出 → 写入 context_buffer
    → 子结构 3 → LLM（输入含子结构 1+2 输出）→ ...
```

这是一条**依赖型长程管线**。每一步都依赖上一步的结果，管线长度 = 子结构数量（多为 12-20）。在这个场景中，"调用 LLM 一定会返回有效结果"的假设被反复打破。

### 1.2 三种失效模式

| 失效模式 | 触发场景 | 在依赖型管线中的影响 | 根因 |
|---------|---------|-------------------|------|
| **Token 耗尽** | 推理模型的思维链消耗了大部分 max_tokens | content = ""，子结构无输出，但管线继续 | reasoning_tokens 不可预测 |
| **外部依赖超时** | RAG 查询 8767 端口超时或断连 | 子结构缺少参考材料，但 LLM 调用仍然执行 | 跨进程 HTTP 调用不可靠 |
| **LLM 格式崩塌** | LLM 输出了无法解析的格式或乱码 | 子结构内容不可用，污染前文缓冲区 | LLM 概率生成的固有特性 |

这三种失效的共同特征是：**它们不是"异常"，而是"常态"**。在一个 20 次调用的管线中，至少 1-2 次调用会出现上述问题。不处理，整篇文章就出现空洞或乱码。

### 1.3 核心矛盾的识别

传统容错策略是**重试（retry）**：

```
调用失败 → 重试 → 再失败 → 再重试 → ... → 放弃
```

但在推理模型场景中，重试不解决根本问题——token 耗尽的原因是推理模型的思维链长度不可预测，重试一次可能吃掉同样多的 token。依赖型管线中，重试还可能导致上下文污染（失败的输出被写入 context_buffer）。

真正的矛盾是：**LLM 调用在长程管线中必然部分失败，但管线不能因此停止。需要的是"隔离"（isolation）而非"修复"（repair）。**

## 二、核心命题

> **在依赖型长程 LLM 管线中，容错不是"确保每个调用都成功"，而是"确保每个调用的失败被隔离在最小粒度内，不污染上下文、不阻断管线。"**

### 2.1 基本判断

| 维度 | 单次调用范式 | 长程依赖型管线范式 |
|------|-------------|-------------------|
| **对 LLM 的期望** | 每次调用都返回有效结果 | 接受部分调用失败，隔离失败 |
| **容错策略** | 重试（retry） | 隔离（isolation） |
| **失败域粒度** | 整次任务 | 单个子结构（500 字） |
| **上下文处理** | 失败时回滚 | 失败时不写入 context_buffer |
| **RAG 依赖** | RAG 失败 = 任务失败 | RAG 失败 = 无参考资料段，继续生成 |
| **管线进度** | 失败停在原地 | 失败跳过当前子结构，继续下一个 |
| **输出完整性** | 全或无 | 部分完成即可交付 |
| **LLM 输出截断** | 丢弃截断内容 | 续写（有内容时）/ 跳过（无内容时） |

### 2.2 核心命题的分解

**命题 A：重试不能解决推理模型的 token 耗尽问题**

推理模型的 token 预算中，reasoning_tokens 占比 50-90%，且不可预测。当 max_tokens = 4096 时，一次调用可能消耗 2047 个 reasoning_tokens、输出 2049 个 content tokens；另一次调用可能消耗 4000 个 reasoning_tokens、输出 96 个 content tokens。重试不能改变这个分布，只会浪费更多 token。

真正的解法是**续写（continuation）**：检测 `finish_reason = "length"`，已写内容通过 assistant 消息传递，追加"请继续写"指令再调一次。续写不是重试——它不丢弃已有的内容，而是从断点继续。

**命题 B：RAG 失败时不应注入 prompt**

传统做法：RAG 超时时将错误信息写入 prompt（`"[RAG 查询失败: timeout]"`）。这导致 LLM 尝试"解释"这条错误信息，输出内容偏离主题。

正确的做法：RAG 失败时，prompt 中不出现参考资料段。LLM 的写作 prompt 在没有外部资料时仍然完整——它仍然有主题、标题、写作要点、前文上下文。缺少的只是"参考资料"这一可选段。

这意味着 RAG 必须作为**可选增强层**设计，而非**必需输入层**。RAG 的可用性不能影响 LLM 的基本生成能力。

**命题 C：子结构是自然的事务边界**

每个子结构有独立的输入（标题 + 写作要点 + 字数 + 前文）和独立的输出（正文）。它的失败不依赖其他子结构的成功。这种事务级隔离的设计意味着：

- 一个子结构的空输出不影响下一个子结构的输入
- 一个子结构的 RAG 超时不影响其他子结构的 RAG 查询
- 所有子结构都失败时，整节不输出，但不阻断后续节的生成

事务级隔离的实现关键：**context_buffer 不写入失败子结构的内容**。成功子结构的内容参与构建上下文，失败子结构的内容被隔离。

**命题 D：跨智能体调用需要"冷启动协议"**

Structured Writer 不内嵌 RAG 能力——它调 RAG Assistant 的外部 API（8767 端口）。这意味着 RAG Assistant 是一个独立进程，需要被启动、健康检测、错误恢复。

"冷启动协议"包含三层：

1. **端口协商**：Structured Writer 启动 RAG Assistant 子进程，指定 `--port 18765 --api-port 8767`，避免端口冲突
2. **编码修复**：子进程的 stderr 需要 `PYTHONIOENCODING=utf-8`，否则 emoji（如 ✅）导致 GBK 崩溃
3. **异步健康检测**：子进程启动后后台线程轮询 8767 端口，不阻塞 HTTP 服务器

这是一个编排层（Structured Writer）调用领域智能体（RAG Assistant）的完整实现案例，对应第四篇（编排范式）的"LLM 做胶水"命题——这里的"胶水"是 HTTP 协议 + 子进程管理，而非 LLM。

## 三、设计原理

### 3.1 原理一：分层材料注入

**基本判断**：LLM 在一段 prompt 中看到多段资料时，会自然地对资料做"优先级排序"。如果所有资料放在一个段落里，它会等权重对待所有资料。

**解决方案**：两级 RAG，节级（背景）+ 子结构级（针对性），在 prompt 中分两段注入：

```
【背景资料】（本节整体相关）
（节级别检索结果——宽泛相关，提供领域上下文）

---

【针对性资料】（针对当前子结构）
（子结构级别检索结果——精准匹配，提供具体论据）
```

两级资料之间的边界标记（`---`）让 LLM 明确区分"背景"和"论据"。实验观察：当两级资料都存在时，LLM 倾向于在引言和过渡中使用背景资料，在论证和引用中使用针对性资料。这种分层引用行为是自动出现的，不需要在 prompt 中显式要求。

### 3.2 原理二：事务级错误隔离

**基本判断**：在依赖型管线中，错误的传播路径是 context_buffer——前一个子结构的输出被写入 buffer，作为后一个子结构的上下文。如果前一个子结构的输出是乱码或空内容，它会被传递给后一个子结构。

**解决方案**：每个子结构的输出在写入 context_buffer 之前经过验证。只有"成功完成"（status = done）的子结构内容进入 buffer。"空跳过"或"异常跳过"的子结构不进入 buffer。

```
子结构 1 → LLM 返回 500 字 → 写入 buffer ✅
  → 子结构 2 → LLM 返回 "" → 跳过，不写入 buffer
    → 子结构 3 （buffer 中只有子结构 1 的内容，没有子结构 2 的污染）
```

这种隔离机制意味着：即使 20% 的 LLM 调用失败（空内容），文章仍然有 80% 的内容可用，且阅读体验不受影响——失败的子结构在最终输出中被跳过，不留下空标题或乱码。

### 3.3 原理三：续写作为资源再分配

**基本判断**：推理模型的 token 预算消耗遵循"推理优先、生成为辅"的模式。在 max_tokens 固定时，推理消耗越多，生成的越少。

**解决方案**：检测 `finish_reason = "length"` 后，不丢弃已生成的内容，而是通过 assistant 消息传递给下一次调用。续写本质上是"把被推理吃掉的生成 token 重新分配给后续调用"。

```
首次调用：
  max_tokens = 4096
  reasoning_tokens = 2047, content_tokens = 2049
  finish_reason = "length"（因为内容被截断）
  → 取已生成的 2049 tokens 作为 assistant 消息
  → 追加"请继续写，不重复已写内容"
  
续写调用：
  LLM 接续前文继续生成
  finish_reason = "stop"（正常完成）
  → 两次输出拼接 = 完整子结构
```

这个设计的边界条件是：当 `content = ""` 时（推理吃光了所有 token），续写没有意义——assistant 消息为空，LLM 不知道从哪继续。此时放弃续写，跳过该子结构。

### 3.4 原理四：跨智能体调用使用"可降级协议"

**基本判断**：Structured Writer 调 RAG Assistant 时，RAG Assistant 可能不在线（未启动）、超时（负载高）、或返回空结果（无匹配资料）。这些情况都不能阻止 Structured Writer 继续生成。

**解决方案**：RAG 调用使用"可降级协议"——调用失败或空结果时，prompt 中不出现参考资料段，LLM 仅基于主题和摘要写作。

```
RAG 在線 → 查詢成功 → prompt 有兩段資料 → LLM 引用資料寫作
RAG 在線 → 查詢返回空 → prompt 無資料段 → LLM 僅基於主題寫作
RAG 離線 → 冷啟動 → probe 8717 → 超時 → status_text 提示用戶
```

这种设计将 RAG 从"必需能力"降级为"可选增强"。RAG 的可用性变化不影响写作管线的完整性。

## 四、与现有方法论体系的关系

### 4.1 对应的方法论维度

Structured Writer 填补了方法论体系中"长程依赖型 LLM 管线"的空缺：

- **第一篇（运行时硬中断）** 讨论的是**单步**的硬约束——步骤原子化、边界检查。但未涉及当步骤数量扩展到 20+ 时，硬中断策略是否仍然适用。
- **第八篇的贡献**：当步骤数量从 5 扩展到 20+ 时，硬中断的成本变得不可接受（中断一个步骤意味着丢失其后的所有进度）。因此第八篇提出"隔离"替代"中断"——失败步骤被隔离，而不是中断整个管线。

- **第五篇（RAG Assistant）** 讨论的是**单次查询**如何覆盖多个实体属性维度。RAG Assistant 的每次查询是独立的，不依赖前一次查询的结果。
- **第八篇的贡献**：两级 RAG 不是"查两次"，而是"查两个不同粒度"——节级定领域，子结构级定论据。这是一种分层检索增强策略，与 RAG Assistant 的"穷举组合"策略互补而非重叠。

- **第四篇（编排范式）** 提出了"LLM 做胶水"的概念，但编排器调用的都是确定性技能（固化工具），不涉及"调另一个 LLM 智能体"的场景。
- **第八篇的贡献**：Structured Writer 调 RAG Assistant 是编排层调用领域智能体的实际案例——HTTP 协议 + 子进程管理 + 健康检测，构成了"LLM 做胶水"在智能体协作层面的工程实现。

### 4.2 与第五篇（RAG Assistant）的互补关系

| 维度 | 第五篇：RAG Assistant | 第八篇：Structured Writer |
|------|---------------------|-------------------------|
| **核心问题** | 单轮 RAG 查不全 | 长程 LLM 管线不停机 |
| **解决策略** | 穷举组合 × 多路检索 | 分层注入 × 原子隔离 |
| **LLM 角色** | 查询策略规划者 | 段落填充器 |
| **依赖关系** | 查询之间独立 | 步骤之间依赖 |
| **错误处理** | 切片级失败不影响其他切片 | 子结构级失败不污染前文缓冲区 |
| **RAG 查询粒度** | entities × attrs 穷举 | 节背景 + 子结构针对性 |

两者可以串联使用：Structured Writer 的子结构 RAG 查询调用的是 RAG Assistant 的外部 API——这构成了"编排层 → 领域智能体"的调用链，是第四篇（编排范式）的直接实现。

### 4.3 已知盲区

| 问题 | 描述 | 状态 |
|------|------|------|
| **续写与推理模型的交互** | 推理模型在续写调用中可能会重新开始推理，而非仅继续生成——浪费 token | 📌 待验证 |
| **context_buffer 的截断策略** | 当前硬编码 800 字截断，没有依据内容类型或 LLM 上下文窗口动态调整 | ⚠️ 需配置化 |
| **RAG 路由的冷启动延迟** | 首次 RAG 查询需要加载嵌入模型，延迟可达 30+ 秒 | 📌 后续版本 |
| **跨智能体的认证与隔离** | 8767 端口无认证，同一机器上的其他进程可随意查询知识库 | 📌 需安全加固 |
| **子结构粒度的自适应** | 2-4 个子结构/节是固定配置，没有根据主题复杂度或字数自动调整的逻辑 | 📌 待设计 |

---

## 五、一句话总结

> 长程 LLM 管线不能假设每个调用都成功。分层材料注入确保 RAG 失败不污染 prompt，原子级事务隔离确保单个子结构的失败不污染整篇文章。Structured Writer 的两个关键设计——"写"和"查"的分离（写作系统 + RAG 智能体）、"成功"和"失败"的隔离（context_buffer 不写入失败的输出）——共同构成了一个能在 30% 调用失败率下仍然交付完整文章的自愈管线。
