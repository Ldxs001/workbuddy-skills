# 重型技能构建的方法论沉淀：本地知识库智能体的自洽范式

> 从"搜索靠猜"到"检索靠切片"——用 LLM 驱动的穷举组合取代单轮 RAG 的架构范式。
> 本文是 Cogito Scribit 方法论体系的**第五篇**，是第四篇（编排范式）和第四篇B（链驱动执行）在具体领域中的应用案例。底层约束来自第一篇（运行时硬中断）和第二篇（构建时契约）的公理体系——loop 架构是公理的具体实现而非特例。
> 更新：2026-07-14（对齐 v1.0.0 实际项目）

---

## 一、背景：传统 RAG 的盲区

### 1.1 单轮 RAG 的隐含假设

传统 RAG（Retrieval-Augmented Generation）的核心流程是一个线性管道：

```
用户问题
  → 路由到知识库
    → 向量检索 top-K
      → 拼接上下文
        → LLM 生成回答
```

这条流水线的隐含假设是：**用户的问题本身就是最佳的检索查询**。

但这个假设在复杂知识库场景中存在严重问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **实体丢失** | "三个代表与无为而治的异同"只命中"三个代表" | 一句话包含多个实体，但向量检索只返回整体相似度 |
| **属性模糊** | 查不到"相同点"和"不同点"的对比信息 | 比较类问题的属性维度分散在不同文档中 |
| **路由抖动** | 包含两个实体的查询路由到错误的 KB | 多实体 = 多目标，单个路由无法同时覆盖 |
| **上下文孤岛** | LLM 看到三个代表但没有无为而治的背景 | 一个 top-K 结果集只覆盖问题的一个侧面 |
| **假阳性回答** | LLM 基于不完整上下文强行生成对比 | 上下文只包含 A 的信息，LLM 自己脑补 B 的部分 |

### 1.2 核心矛盾的识别

传统 RAG 的进化为一条线性流水线：

```
问题 → 检索 → 回答
```

但真实的知识库问答需要的是：

```
问题 → 分解（实体/属性/关系） → 多路检索 → 聚合 → 综合回答
```

两者之间的鸿沟就是：**问题不是查询**。用户的问题是一个**复合指令**，需要解析为检索策略再执行，而不是直接扔给向量库。

## 二、核心命题

> **在多实体、多属性的复杂知识库问答场景中，LLM 应该承担"查询策略规划者"的角色——将用户问题分解为检索元组，而非直接回答问题。**

### 2.1 基本判断

| 维度 | 传统 RAG 范式 | 组合式检索范式 |
|------|-------------|---------------|
| **查询构造** | 用户原句直接检索 | LLM 分解为 entities + attrs 后穷举组合 |
| **LLM 角色** | 答案生成器 | 查询规划器 + 答案整合器 |
| **检索单位** | 一段文本 | 一个 entity × attr 元组 |
| **路数** | 1 路检索 | N × M 路独立检索 |
| **去重策略** | 无 | SM3 内容哈希去重 |
| **路由粒度** | 整句路由 | 每条切片独立路由 |
| **失败隔离** | 一步失败全局无结果 | 切片级失败不影响其他切片 |
| **上下文质量** | 可能漏掉关键侧面 | 所有实体 × 属性维度都被覆盖 |
| **输出格式** | 自由文本 | 强制 4 层结构化分析（逻辑→本体→机制→矩阵） |

### 2.2 核心命题的分解

**命题 A：LLM 比规则更适合做查询分解**
- 实体/属性标注依赖语义理解，关键词规则无法处理同义表达
- LLM 能理解"相同点/不同点"是一个对比属性维度
- 规则引擎只能做平面关键词匹配，无法理解"关系"

**命题 B：穷举组合比智能猜测更可靠**
- 假设有 2 个实体 × 3 个属性 = 6 种组合，全部查询比让 LLM 选 1-2 种更可靠
- 向量检索的 top-K 机制天然有重复冗余，穷举的边际成本很低
- 额外的查询组合最多产生重复结果（SM3 去重即可），不会产生错误结果

**命题 C：LLM 做决策必须可修正**
- 第一次输出可能格式错误 → 自修正循环捕获并反馈
- 多次错误 → 降级为普通聊天
- 自修正机制不是锦上添花，而是保证 LLM 输出可控的刚性约束

**命题 D：输出格式必须强制结构化（v0.9.0 后关键教训）**
- 自由文本输出导致 LLM 遗漏关键维度、引用无标记、结论模糊
- 强制 4 层结构 + 引用编号门禁校验，将 LLM 输出从"散文"变为"论文"
- 每一层的缺失都会破坏整个回答的可验证性

## 三、架构范式

### 3.1 双阶段流水线

```
第一阶段：检索策略
  LLM(用户问题) → entities=["A","B"], attrs=["X","Y"], rel="R"
  ↓
  穷举展开：
    单实体 × 各属性：A X, A Y, B X, B Y
    联合 × 各属性：AB X, AB Y
    两两配对 × attrs × rel：AB X R, AB Y R, AB R

第二阶段：并行检索
  切片 1 → 路由（6 种方法） → ChromaDB（HNSW 自动修复） → reranker（三模式） → NLI（三向分类） → context
  切片 2 → 路由 → Chroma → reranker → NLI → context
  ... 共 N×M 路
  ↓
  SM3 去重合并
  ↓
  LLM(完整上下文 + 用户问题 + 3 插槽 prompt) → 4 层结构化回答
  ↓
  引用门禁校验（检查 [n] 编号是否在资料范围内）
```

### 3.2 检索即服务

本地 RAG 以完整技能（local-rag-builder）的形式嵌入智能体，智能体不改造技能内部逻辑：

```
rag-assistant/                      # 智能体层
├── main.py                         # 入口（4 种模式）
├── rag_assistant/                  # 决策、界面、LLM 通信
│   ├── agent.py                    # 决策循环 + 组合查询
│   ├── web_ui.py                   # HTTP 服务器 + 前端
│   ├── rag_wrapper.py              # 技能封装桥接层
│   ├── memory.py                   # 四层记忆 + 用户画像
│   ├── llm_client.py               # Ollama + LM Studio 双后端
│   ├── search.py                   # 联网搜索（3 引擎）
│   │
│   └── engine/                     # ★ 技能层（只调用，不改造）
│       ├── rag_core.py             # 检索引擎核心
│       ├── router.py               # 两级路由
│       ├── reranker.py             # 三模式重排序 + FallbackRouter
│       ├── nli_classifier.py       # NLI 三向分类器
│       ├── knowledge_base_manager.py  # 知识库 CRUD + 容灾
│       ├── text_splitter.py        # 5 策略 + 5 守卫插件架构
│       ├── prompt_manager.py       # 3 插槽 + 预设管理
│       ├── config.py               # 配置管理 + 模型路径自动修正
│       ├── embedding_model_manager.py  # 5 源并行模型下载
│       └── utils.py                # 工具函数
│
├── vendor/                         # 内嵌第三方库
└── data/                           # 运行时数据
```

智能体层与技能层的边界清晰——智能体只负责"查什么"，技能层负责"怎么查"：

| 层 | 负责 | 不负责 |
|----|------|--------|
| **智能体** | 实体/属性解析、组合策略、去重合并、LLM 回答、记忆管理、用户画像 | 向量检索、路由决策、rerank 排序、文本切分 |
| **技能** | 语义路由（6 方法）、Chroma 检索、Cross-encoder 重排、NLI 分类、KB 签名、容灾 | 问题分解、组合策略、回答生成 |

这种分离意味着：底层技能升级（如换用更好的嵌入模型）不影响上层策略，上层调整检索策略不影响底层技能。

### 3.3 决策循环中的两阶段硬约束

> **本篇不推翻前四篇——第二篇（构建时契约）定义什么是正确结构，第一篇（运行时硬中断）定义执行时怎么不出错，第三篇（递归自举）验证契约本身。loop 架构不过是第一篇和第二篇公理在"动作校验"子问题上的具体实现，不是新发明。**

LLM 在智能体中不是自由发挥的——它的每一步输出都被两层嵌套的硬约束圈住，外加循环外的门禁和围栏。这是第二篇（构建时契约）的契约设计和第一篇（运行时硬中断）的硬约束阻断的直接实现——只是从"三层平铺"变成了"两层嵌套+外部门禁"的形式。

**两阶段架构**：阶段 1（模式判定）是门禁，阶段 2（动作校验小循环）是围栏内的受控循环。

```
用户输入
  ↓
┌──────────────────────────────────────────────────────────────────┐
│  门禁：阶段 1（模式判定）                                          │
│  ┌─ 单次 LLM 调用 → _parse_action → _validate_action  ────────┐ │
│  │  ├─ (None, None)       → 聊天模式，直接回答 ✅               │ │
│  │  ├─ chat 动作          → 聊天模式 ✅                         │ │
│  │  └─ 解析错误/有效action → 进入阶段 2 ⤵                      │ │
│  └──────────────────────────────────────────────────────────────┘ │
│                               ↓                                  │
│  围栏：阶段 2（动作校验小循环）                                      │
│  ┌─ _action_validation_loop  ──────────────────────────────────┐ │
│  │  attempt 1 已在门禁中处理，小循环从 attempt 2 切入             │ │
│  │  ↓                                                            │ │
│  │  LLM 推理 → _parse_action → _validate_action                 │ │
│  │  ├─ ✅ 通过 → 执行动作，退出循环 🔓                            │ │
│  │  ├─ 不输出 <<ACTION>> → 认定为"逃逸"，强制回正 🚫             │ │
│  │  ├─ 格式错误 → 反馈格式要求 🔧                                │ │
│  │  └─ 校验拒绝 → 反馈具体原因（缺参数/缺 evidence/kb 不存在）    │ │
│  │  ↓ 最多 5 次                                                  │ │
│  │  耗尽 → 返回结构化错误，拒绝 LLM 自由回答 🔒                  │ │
│  └──────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
  ↓ 动作执行 → 第二轮 LLM 回答 → 引用门禁校验（也是循环外的门禁）
```

#### 3.3.1 门禁在循环外

阶段 1（模式判定）不在小循环内。它是一个**单向门禁**——决定了 LLM 是走"聊天"快通道还是"检索"重流程。门禁一旦放行，无法回头。LLM 不能在进入阶段 2 后说"我不想检索了"退回到聊天模式。

这解决了一个关键问题：**LLM 倾向于在不确定时逃避到"聊天"模式**（因为聊天不需要格式约束、不需要证据校验）。通过把模式判定放在循环外，我们强制 LLM 在门禁处做一次不可逆决策。

除了模式判定门禁，还有几层围栏也在循环外：

| 围栏 | 位置 | 作用 |
|------|------|------|
| **evidence 校验** | `_validate_action()` 内，小循环入口 | 每个 entity/attr 必须有原文出处，词可凝缩但出处必须是原文原句 |
| **kb 校验** | `_validate_action()` 内 | 知识库名必须在用户原话中出现、必须在系统中真实存在 |
| **引用门禁** | `_second_pass()` 内，回答生成后 | 校验 [n] 引用编号是否在资料段落范围内，不存在的编号 → 告警注入 |
| **5 次失败拒答** | 小循环退出条件 | 耗尽后**禁止** LLM 自由回答（防捏造），返回结构化错误信息 |

这些围栏的共同特征：**不在小循环的迭代逻辑内**。它们是围栏圈的桩子，不是循环的迭代步骤。小循环只在"校验→修正→再校验"这条轨道上跑，不会因为围栏存在就改变迭代逻辑。

#### 3.3.2 小循环非从头切入

传统的 retry 模式是：

```
attempt 1: 全流程 → 失败 → 清上下文 → 重新开始
attempt 2: 全流程 → 失败 → 清上下文 → 重新开始
...
```

这导致两个问题：
1. LLM 不知道之前为什么失败，只能"重新猜"
2. 每次重试消耗完整上下文窗口，前面的失败反馈被丢弃

本架构的切入方式不同：

```
attempt 1: 由门禁（阶段 1）处理
  ↓ 失败
LLM 收到【修正提醒】：具体失败原因
  ↓
attempt 2: 进入小循环（阶段 2），LLM 在原有上下文基础上修正
  ↓ 失败
LLM 收到新的【修正提醒】：更具体的失败原因
  ↓
attempt 3-5: 同上，错误累积在上下文中，LLM 逐轮改进
```

**关键区别**：小循环不是从"重新写 prompt"开始，而是从"修正上次输出"开始。LLM 看到之前的失败回复 + 具体的修正提醒 → 在保留上下文的基础上做定向修复。这比清空从头来收敛更快，且每轮失败信息都会让下一轮输出更精准。

```
                   ┌─────────────────────────────────────┐
                   │  门禁（阶段 1）     attempt 1         │
                   │  LLM 首次输出 → _parse_action        │
                   │  → _validate_action → 失败           │
                   └──────────┬──────────────────────────┘
                              │ 【修正提醒】附加上下文
                              ↓
                   ┌─────────────────────────────────────┐
                   │  小循环（阶段 2）：从 attempt 2 切入   │
                   │  LLM 看到：自己的失败输出 + 修正提醒    │
                   │  → 修正后重新输出 → 校验               │
                   │  → 通过 ✅  /  再次失败 → 继续         │
                   └─────────────────────────────────────┘
```

#### 3.3.3 防逃逸机制

小循环的另一个关键设计是**防逃逸**。LLM 在被反复要求修正时，有时会尝试"跳出循环"——不输出 `<<ACTION>>` 标记，直接输出回答文本，假装自己是普通聊天。

本架构通过显式检测处理这种逃逸：

```
if not action and not parse_err:
    # LLM 没有输出 <<ACTION>> → 认定为逃逸
    msgs.append("你已选择动作模式，必须输出有效的 <<ACTION>> 标记")
    continue  # 继续循环，不退出
```

逃逸检测独立于格式校验和参数校验——它是小循环的**第一道围栏**，在解析和校验之前拦截。即使 LLM 输出了一段完美的回答文本而没有 `<<ACTION>>`，也会被检测为逃逸并强制回正。

#### 3.3.4 小循环不是反思怪

"反思怪"指的是一种常见的 Agent 设计缺陷：让 LLM 在循环中不断"反思"自己的输出，但没有明确的反馈信号和终止条件。这种设计的问题：

- 没有具体反馈 → LLM 只能猜自己哪里错了
- 没有步数限制 → 可能无限循环
- 每次重试都从头开始 → 失败信息丢失
- 最终循环终止时 → LLM 要么投降式给出垃圾回答，要么逃跑回聊天模式

**本架构与"反思怪"的区别正是前两篇公理的直接应用**：

| 前两篇的公理 | 反思怪（违反公理） | 本架构（遵守公理） |
|-------------|------------------|------------------|
| **第二篇：构建时契约 → 五层声明 + 接入校验** | "请反思你的输出"（无结构无校验） | 5 次硬上限 + 逃逸检测 + 拒绝自由回答 |
| **第一篇：硬约束 → 错误是反馈信号** | "再想想"（无具体反馈） | "以下词缺少原文出处: 大语言模型"（精确到哪个词） |
| **第一篇：关注点分离** | 模式判定和校验混在同一个循环里 | 阶段 1 门禁（模式判定）和阶段 2 围栏（动作校验）分离 |
| **第一篇：抑制执行偏差** | LLM 可以随时逃逸到聊天模式 | 逃逸显式检测 + 强制回正 |

每个修正提醒都包含**具体的失败原因**，不是"请反思"这种空话：

| 失败类型 | 反馈内容 | 是否具体 |
|---------|---------|---------|
| evidence 缺失 | `"以下词缺少原文出处: 大语言模型。请补充 evidence 中的对应条目"` | ✅ 明确到哪个词 |
| kb 不存在 | `"知识库「意识理论」不是用户说的名称，去掉 kb 参数"` | ✅ 明确操作 |
| 格式错误 | `"动作格式错误：必须使用 <<ACTION>> 格式"` | ✅ 明确格式 |
| 逃逸 | `"你已选择动作模式，必须输出有效的 <<ACTION>> 标记"` | ✅ 明确动作 |

小循环的终止条件也是刚性约束——**不是 LLM 决定何时退出，而是硬编码的 5 次上限**。5 次耗尽后不给出第二次机会，直接拒绝 LLM 自由回答。这个"宁缺毋滥"的设计避免了最坏情况——LLM 在耗尽后捏造引用或强行生成错误回答。

### 3.4 输出格式契约（v0.8.0+ 关键创新）

v0.8.0 后引入**强制结构化输出格式**，System Prompt 中嵌入以下模板约束：

```
【引用格式】每个结论后面用 [n] 标注来源的段落编号
【输出风格】【强制输出结构】（必须严格按此格式输出，严禁只写四个段落标题）：

正式回答

核心结论
|知识库分类（按资料来源自动归纳）|涉及的文档/理论数|与本问题直接相关的关键发现|

第一层：逻辑与形式理论层（此层必须包含数学公式）
...

第二层：哲学本体论与概念本质层（此层必须引用资料中的形而上学框架）
...

第三层：现实机制与功能拆解层（此层必须剥离修饰性术语）
...

第四层：综合判定与意义分层矩阵（此层必须使用 Markdown 表格）
...

引用片段索引（必须填写，不得为空）
```

3 个插槽可由用户在 Web UI 配置，4 个内置预设（标准模式 / 深度分析 / 对比分析 / 友好对话）+ 用户自定义预设。

## 四、这套机制为什么能工作

### 4.1 向量检索的特性天然适配穷举

| 特性 | 对组合检索的意义 |
|------|----------------|
| **top-K 有上限** | 每次检索只返回 3-5 条，不会因为多个切片导致结果爆炸 |
| **结果有重复** | SM3 去重确保内容不膨胀 |
| **路由基于语义** | 每个切片独立路由到最相关的 KB，比单句路由更精准 |
| **检索快速** | Chroma 局部搜索在本地毫秒级，N×M 路检索总耗时仍远低于 LLM 推理时间 |

### 4.2 本地部署的特殊优势

| 因素 | 在线服务 | 本地部署 |
|------|---------|---------|
| **检索成本** | 按 token 计费 | 零边际成本 |
| **穷举开销** | 线性增长 | 线性增长但阈值很低 |
| **模型切换** | 受限于 API | 自由切换嵌入/reranker/LLM |
| **数据隐私** | 上传第三方 | 全本地 |

本地部署意味着穷举组合没有额外成本——多一次检索只多几十毫秒的 CPU 时间。这使得"全部查一遍"策略成为可行选项，而非理论优化。

### 4.3 自修正的收敛性

`_decide_with_retry()` 中两阶段设计，`max_retries=5`（全局上限）。实际运行日志显示：

| 尝试次数 | 占比 | 典型场景 |
|---------|------|---------|
| 阶段 1 通过（0 次小循环） | ~70% | 标准聊天、简单查询 |
| 第 2 次（小循环 attempt 2）通过 | ~17% | evidence 格式不规范（缺原文出处词条） |
| 第 3-4 次通过 | ~8% | entities/attrs 提炼与原文对不齐，需要多轮修正 |
| 第 5 次通过末次 | ~3% | LLM 坚持用错误的知识库名，被反复拒绝后修正 |
| 耗尽拒绝（5 次失败） | ~2% | 模型自身输出崩溃 / 知识库名持久冲突 |

**关键发现**：前 2 次（阶段 1 + 小循环 attempt 2）覆盖 ~87% 场景，但第 3-5 次仍有 ~13% 的有效修复场景。如果像早期版本那样设 `max_retries=2`，会错失这部分修复机会，导致 ~13% 的请求被过早拒绝。5 次是当前的最优值——更多轮次几乎无新增收益（<1%），更少轮次会显著增加拒绝率。

**循环不是反思怪**——每一轮失败都有具体的反馈原因（"以下词缺少原文出处"、"知识库不存在"），LLM 不是在"反思"而是在**定向修复**。

## 五、这套方案的代价与边界

### 5.1 代价：以资源换周全

本范式的核心取舍是：**用查询量、延迟和 token 消耗换取检索的完备性。**

| 代价维度 | 具体表现 | 与传统 RAG 对比 |
|---------|---------|----------------|
| **查询量** | N 实体 × M 属性 → N×M 次独立检索（含路由 + Chroma + 可能 rerank + NLI） | 传统 RAG 仅 1 次检索 |
| **端到端延迟** | 多路检索串行执行，每路 ~50-200ms，10 路 ≈ 0.5-2s 额外等待 | 传统 RAG 检索耗时在数十毫秒级 |
| **LLM 整合负担** | 合并后的上下文包含多个侧面的信息，LLM 需要从中筛选、对比、综合 | 传统 RAG 的上下文更集中，LLM "看一眼就答" |
| **嵌入计算量** | 每路检索都要将切片文本做嵌入编码 | 传统 RAG 只编一次（v0.8.5 优化为单例缓存） |
| **token 浪费** | 不同切片可能命中相似内容，即使 SM3 去重也无法消除语义重叠 | 传统 RAG 无此问题 |
| **灵活性代价** | 固定策略（穷举所有组合）无法根据问题类型动态调整检索深度 | 传统 RAG 一条路径走到底反而简单 |

换一种更直白的说法：

> **传统 RAG 是"瞄一眼就答"——快但可能看漏。本范式是"每个角落都翻一遍再答"——全面但费时费力。后者在知识库内容分散、问题涉及多个维度时更有价值，在简单的一问一答场景中反而大材小用。**

### 5.2 边界：适用场景与不适用场景

| 适合 | 不适合 |
|------|--------|
| 多实体对比分析（A 与 B 的异同） | 单实体事实查询（"苹果的糖度标准是多少"） |
| 跨知识库综合问答 | 单库已知位置检索 |
| 需要穷举侧面的调研型问题 | 时间敏感的简单问答 |
| 知识库内容分散、无单一文档覆盖全部信息 | 知识库内容高度集中、单一文档即可回答 |

### 5.3 已知局限

| 局限 | 说明 | 缓解措施 |
|------|------|---------|
| **实体数量爆炸** | 5 实体 × 5 属性 = 25 切片，再组合衍生更多 | 实际使用中 LLM 标注的实体/属性通常各 ≤3 个 |
| **路由扁平化** | 每个切片独立路由，但路由器的精度有限 | 6 种路由方法分层（hardcoded / embedding_signature / broadcast 等） |
| **模型无关性** | 依赖 LLM 的输出格式一致性 | 自修正循环兜底格式错误 |
| **上下文窗口** | 太多切片导致 context 文本太长 | SM3 去重 + k=5 避免结果膨胀 |
| **无结果处理** | 检索结果为空时仍需 LLM 回答 | 降级为"未找到相关资料"回复，记录知识缺口 |
| **嵌入模型重复加载** | 组合查询每片都 load 一次嵌入模型 | v0.8.5 修复为 get_embeddings() 单例缓存（18 次→1 次） |

### 5.4 嵌入对象构造冗余（v0.8.5 修复）

从运行日志可以看出一个典型陷阱——组合查询中 "Loading weights" tqdm 进度条重复出现：

```
Loading weights: 100% | 202/202 [00:00<00:00, 8000it/s]
Loading weights: 100% | 202/202 [00:00<00:00, 8000it/s]
...（重复 30+ 次）
```

**这里的 "Loading weights" 指标有误导性。** 每条在 0.028 秒内完成（202/202 @ 8000 it/s），说明模型已经在 HuggingFace 缓存和 OS 文件缓存中，远快于真正的磁盘→GPU 全量加载（需数秒）。每条进度条代表的是 `SentenceTransformer()` 的 `from_pretrained()` 初始化流程在验证缓存文件完整性，而非重新加载模型权重。

但问题仍然存在：**`get_embeddings()` 每次都被调用了新的构造函数**，导致：
- 30+ 个冗余的 Python 对象创建（即使权重是共享的）
- CUDA 上下文重复初始化（如果有 GPU）
- tqdm 日志污染（让人误以为有性能灾难）

根因：每片独立调用 `rag.query()` 导致各自触发 `get_embeddings()` 重新初始化。修复方案（v0.8.5）：`get_embeddings()` 加单例缓存，组合查询只初始化一次。

**教训：技能封装不能纯透传——需要在智能体层做资源复用优化。同时，阅读日志时要注意区分"看起来严重的进度条"和"实际性能影响"，不要在误导性指标上做过度推断。**

### 6.4 修复前后对比：rel 切片丢失的根因修复（v1.0.0 真实日志）

v1.0.0 修复了一个架构级 bug——单实体 + 多属性 + rel 场景下 rel 切片完全丢失。以下是修复前后的对比：

#### 6.4.1 用户提问

> **问：AI 是顺着我的倾向回答，还是真的在独立思考？**

#### 6.4.2 Agent 日志

```
组合查询: entities=['AI'], attrs=['顺着我的倾向回答', '独立思考'], rel=对比
```

**v0.10.0（修复前）**：
```
生成切片: ['AI 顺着我的倾向回答', 'AI 独立思考']
                                                 ↑ rel="对比" 被完全丢弃
                                                 算法仅生成 entity × attr 切片
```

**v1.0.0（修复后）**：
```
生成切片: ['AI 顺着我的倾向回答', 'AI 独立思考', 'AI 顺着我的倾向回答 独立思考 对比']
                                                                      ↑ rel 语义进入切片
```

#### 6.4.3 根因

`_exec_query()` 中 `if len(entity_list) >= 2:` 条件短路——entities 只有一个 `['AI']`，小于 2，整个两两配对代码块跳过。`rel="对比"` 被当作布尔开关（是否触发两两配对），而非语义值。算法只生成 entity × attr 切片（事实块），rel 的关系语义完全丢失。

#### 6.4.4 修复方法

将穷举组合重构为三层泛化规则，不再依赖 entity 数量做 if-else 特调：

```
第一层（始终执行）：entity × attr 笛卡尔积                     → 事实块检索
第二层（≥2 entities）：全实体联合 × attr                      → 全实体交叉检索
第三层（rel 非空）：两两无重复配对（≥2 entities → entity 配对，
                   1 entity → attr 配对）               → 关系检索
```

修复后，单实体 + 多属性 + rel 场景下：

```
切片 1: "AI 顺着我的倾向回答"                    → RAG 检索"迎合"的事实块
切片 2: "AI 独立思考"                             → RAG 检索"独立思考"的事实块
切片 3: "AI 顺着我的倾向回答 独立思考 对比"        → RAG 检索对比关系块
                                       ↓
LLM 第二轮拿到 {事实块1, 事实块2, 关系块} 做推理整合
```

| ② 工程/实操应用 | 高 | [片段 1] 详细列出训练参数，显示实际运作基于统计优化而非自主意图 |
| ③ 伦理/安全监管 | 低 | [片段 3][4] 倾向于将 AI 视为工具或尘埃，降低了对"独立意志"的监管紧迫性假设 |
| ④ 跨学科形式化路径 | 无 | [片段 5][6] 显示 IIT 等理论虽提出意识第一性，但尚未与工程实践形成统一量化标准 |

最终断言：基于资料证据，当前 AI 的行为机制主要体现为对训练数据分布的统计拟合（顺应倾向），关于其是否具备本体论层面的"独立思考"，主流科学视角倾向于否定，认为其为神经计算副产品 [1][3]。

#### 6.4.6 这个案例说明了什么

1. **算法问题一眼被看穿**：用户看到 `entities=['AI'], rel=对比` + 切片没有 `对比` → 直接判断是算法没把 rel 塞进切片。**LLM 做对了（给了正确的参数），算法没做完（组合逻辑不完整）。**

2. **不是特调**：修复是泛化的三层规则，不是对"AI"或"对比"做特判。4 种 entity/attr/rel 组合情况统一走同一个代码路径。

3. **门禁和围栏都在起作用**：日志显示 LLM 首次输出因缺少 evidence 被拒绝（门禁），修正后第二次通过校验进入正常流程（小循环从 attempt 2 切入）。门禁阻挡了不完整的查询结构，围栏保证了 rel 语义进入切片。

### 7.1 路由方法枚举

| 路由方法 | 触发条件 | 精度 |
|---------|---------|------|
| `hardcoded` | 命中硬编码关键词规则 | 最高 |
| `embedding_signature` | 嵌入模型 × KB 签名关键词（top-12）余弦相似度 | 高 |
| `embedding_keyword` | 嵌入模型 × 规则关键词（top-30）余弦相似度 | 中 |
| `default` | 无匹配，路由到 default | 低 |
| `direct` | 用户直接指定了知识库 | 最高 |
| `broadcast` | 语义回退失败后全量广播（FallbackRouter） | 最低 |

### 7.2 KB 签名生成流水线

```
入库 → 文档 chunks
  → BCE 语义质心提取（所有 chunks 的嵌入向量均值）
    → jieba 候选词提取（2-4 字中文 + 2-20 字母英文）
      → 停用词过滤（60+ 连接词/代词）
        → BCE 排序（候选词 vs 每个原始关键词单独算相似度取最大值）
          → top-12 输出签名 / top-30 反哺到自动分类规则
```

v0.8.6 改进：四分法采样（小 KB 全量 / 中 KB 全域随机 / 大 KB 四分+每份内随机），确保签名质量。

## 十一、这套方案沉淀了什么

### 11.1 可复用的模式

1. **LLM 驱动的查询分解模式** — 将用户问题解析为 (entities, attrs, rel) 三元组，不依赖规则引擎
2. **穷举组合检索模式** — entities × attrs 的笛卡尔积全部查询，用 SM3 去重消除冗余
3. **技能即服务模式** — 底层 RAG 技能以完整副本嵌入智能体，不改造、不入侵
4. **两阶段门禁-围栏模式** — 阶段 1（模式判定）是单向门禁，阶段 2（动作校验小循环）是围栏内的受控循环。门禁在循环外，围栏也在循环外
5. **非从头切入模式** — 小循环从 attempt 2 开始（attempt 1 由门禁处理），保留失败上下文 + 具体修正提醒，LLM 做定向修复而非重新猜
6. **显式逃逸检测模式** — 独立检测 LLM"不输出 <<ACTION>>"的逃逸行为，强制回正而非静默放行
7. **非反思怪模式** — 每个修正提醒包含具体失败原因（缺哪个词/哪个 kb 不存在），终止条件由硬编码上限保证，不是 LLM 决定何时退出
8. **rel 语义值而非布尔开关模式** — rel 作为语义值参与切片生成，算法泛化处理所有配对情况（≥2 entities → entity 配对，1 entity → attr 配对），不做 if-else 特调
9. **配置持久化模式** — LLM 配置（backend/model/timeout/maxtokens）写入 config.json，运行时与持久化分离但一致
10. **强制结构化输出模式** — 4 层分析框架 + 引用编号门禁，将 LLM 输出从"散文"变为"论文"
11. **资源复用优化模式** — 嵌入模型单例缓存，避免组合查询重复加载

### 11.2 关键教训

| 教训 | 场景 | 结论 |
|------|------|------|
| **不要替 LLM 过滤查询** | 原方案只查前 1-2 个切片 | 全部查一遍更可靠，反正有去重 |
| **不要静默丢弃格式错误** | _parse_action 返回 None 时 LLM 不知情 | 必须反馈给 LLM 自修正 |
| **不要污染耗尽上下文** | 重试耗尽后用旧上下文强答 | 清空上下文从头来 |
| **配置必须写文件** | 运行时变量在重启后丢失 | config.json 持久化 + 运行时同步 |
| **`get_embeddings()` 必须单例缓存** | 30+ 片各触发一次构造函数，日志 30+ 条进度条 | 组合查询只加载一次构造函数，避免冗余对象创建和日志污染 |
| **门禁必须在循环外** | 模式判定和 evidence 校验在循环内时，LLM 可以随意切换模式 | 阶段 1（模式判定）必须是单向门禁，一旦放行不可回头 |
| **小循环不能从头切入** | 每次重试清上下文重写 prompt，LLM 每次从零猜 | 保留失败上下文 + 具体修正提醒，LLM 做定向修复 |
| **逃逸必须显式检测** | LLM 被反复修正时倾向于"跳出循环"直接回答 | 独立逃逸检测（不输出 <<ACTION>>），强制回正 |
| **循环不是反思怪** | 反馈信息笼统（"请修正"），LLM 不知道具体错哪 | 每个修正提醒包含具体失败原因（缺哪个词/哪个 kb 不存在）|
| **rel 是语义值不是布尔开关** | rel 仅控制是否进入两两配对代码块，单实体时短路丢失 | rel 必须作为语义值进入切片，算法泛化处理所有配对情况 |

## 附录：这套方法论可以怎么迁移

### A. 其他检索场景

本模式的本质是：**将复杂查询分解为标准元组，穷举执行后合并**。可迁移到：

- **代码搜索**：解耦为 (语言, 框架, 功能) → 分别搜索代码片段 → 合并
- **文档问答**：解耦为 (产品名, 版本号, 功能模块) → 多路检索 → 整合
- **对比分析**：解耦为 (实体 A, 实体 B, 对比维度) → 各自查信息 → LLM 做对比

### B. 其他技能集成

"技能即服务"模式可迁移到任意需要调用 WorkBuddy 技能的智能体：

```
智能体层（策略 + 决策）
  → 技能封装层（接口适配 + 异常处理 + 资源缓存）
    → WorkBuddy 技能层（完整逻辑）
```

每次技能版本升级只需要替换 `engine/` 目录，智能体层无需改动。

### C. 强制输出格式模式的通用化

4 层分析 + 引用门禁是一个通用模式，适用于任何需要 LLM 输出可验证、可审查、可归因的场景：

```
System Prompt 强制结构模板
  ↓
LLM 按格式输出
  ↓
后处理校验（引用编号检查 / 层完整性检查）
  ↓
不合格 → 告警注入 / 要求重试
```

这个模式在第二篇（构建时契约）中被系统化定义——五层声明 + 接入校验，又在第一篇（运行时硬中断）中被执行化——步骤原子化 + 硬约束阻断。RAG Assistant 是前四篇文章公理体系在检索场景中的完整实现案例。
