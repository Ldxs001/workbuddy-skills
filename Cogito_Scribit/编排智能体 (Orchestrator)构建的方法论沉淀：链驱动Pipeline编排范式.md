# 编排智能体 (Orchestrator) 构建的方法论沉淀：链驱动 Pipeline 编排范式

> 从"LLM 当大脑"到"链是主体"——用确定性 Pipeline 执行替代 ReAct 自由对话的架构范式。
> 更新：2026-07-10

---

## 一、背景：ReAct 的盲区

### 1.1 ReAct 循环的隐含假设

传统智能体架构的核心模式是 ReAct（Reasoning + Acting）循环：

```
用户输入 → LLM 思考 → 调用工具 → 观察结果 → LLM 再思考 → ... → 最终回答
```

这条循环的隐含假设是：**LLM 有能力在每一步做出正确的路径决策**。

但这个假设在技能编排场景中存在严重问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **路径不可复现** | 同一个 Pipeline 执行两次结果不同 | LLM 每次的路径选择是概率性的 |
| **决策循环失控** | LLM 陷入"思考→调用→再思考"的死循环 | 没有硬性的步骤数上限或路径约束 |
| **技能调用混乱** | LLM 调用 load_skill 后不知道下一步该干什么 | 缺乏预定义的执行顺序和输出契约 |
| **上下文污染** | 上一次调用的输出影响下一次的路径选择 | ReAct 循环的历史消息是状态敏感的 |
| **审计困难** | 无法回溯某次执行中 LLM 为什么选了这个技能 | 路径决策是隐式的，没有显式记录 |

### 1.2 核心矛盾的识别

ReAct 的进化为一条自由循环：

```
用户输入 → [LLM 决策 → 工具调用]^N → 回答
```

但技能编排需要的是：

```
用户输入 → 编排好的技能链 → 逐步骤执行（串行/并行/循环） → 输出
```

两者之间的鸿沟就是：**LLM 做路径决策不是优势，而是负担**。当技能链是确定的（用户或编排器已经定义好顺序），ReAct 循环中 LLM 的"思考"就变成了多余开销。

## 二、核心命题

> **在技能编排场景中，LLM 不应是"大脑"而应是"执行器"——链是主体，对话是附属，LLM 只负责执行链中的每个步骤。**

### 2.1 基本判断

| 维度 | ReAct 范式 | 链驱动范式 |
|------|-----------|-----------|
| **执行主体** | LLM 决策 → 调用工具 | 预编排的技能链 |
| **LLM 角色** | 决策者 + 执行者 | 步骤执行器 + 输出生成器 |
| **路径决策** | 运行时动态决定 | 编排时静态确定 |
| **可复现性** | 概率性，不保证重复 | 确定性，相同链相同输出 |
| **状态管理** | 隐含在对话历史中 | 显式步骤间参数传递 |
| **技能组合** | LLM 自己决定调哪个 | 用户编排 seq/par/loop |
| **失败恢复** | LLM 自行修正 | 步骤级重试 + 黏连点转换 |

### 2.2 核心命题的分解

**命题 A：链是主体，对话是附属**
- 用户先编排 Pipeline（技能、参数、模式），再通过对话下达任务
- 没有链就没有对话——系统不存在"闲聊"模式
- Pipeline 编辑器是主界面，对话区是执行结果展示

**命题 B：LLM 应执行而不是决策**
- 技能的执行顺序由编排器决定，LLM 不需要"思考"下一步做什么
- LLM 在每个步骤中负责执行当前技能并输出结果
- 步骤间数据传递是自动的（前一步输出 → 后一步输入）

**命题 C：Seq/Par/Loop 是真执行，不是标签**
- seq：前一步输出传递到下一步，真 LLM 调用
- par：ThreadPoolExecutor 真并行，多路同时执行
- loop：for 循环真重复 N 次

## 三、架构范式

### 3.1 三阶段执行流

```
第一阶段：需求分析（Round 1）
  LLM(用户任务 + 技能链) → 分析任务与链的关系
  ↓

第二阶段（可选）：skill-sub 优化（Round 2）
  读 SKILL.md → 算法黏连检查 → LLM 模糊回退 → 里程碑标记
  ↓

第三阶段：逐步执行（Round 3+）
  步骤 1 → LLM 执行 → 输出
  步骤 2 → LLM 执行（输入 = 步骤 1 输出） → 输出
  ... 直到链结束
```

### 3.2 技能链数据模型

每个 Pipeline 节点包含：

```
{
  "name": "skill-name",       // 技能 slug
  "display": "显示名称",       // 前端展示
  "mode": "seq|par|loop",     // 执行模式
  "params": {},               // 技能参数（可选）
  "children": [],             // 子节点（par/loop 用）
  "loop_times": 3,            // 循环次数（loop 用）
  "extra": {}                 // skill-sub 优化数据（黏连点/里程碑）
}
```

三种模式的真实执行：

| 模式 | 实现方式 | 说明 |
|------|---------|------|
| **seq** | `llm.chat()` 单次调用 | 前一步输出清洗后传入下一步 |
| **par** | `ThreadPoolExecutor` | 多线程并行，所有完成后再继续 |
| **loop** | `for` 循环 | 指定次数重复执行子节点 |

### 3.3 LLM 即执行器

LLM 在链驱动架构中的角色被严格限定：

```
链定义时：LLM 不参与（用户编排）
需求分析时：LLM 分析任务（Round 1）
优化时：LLM 仅做模糊黏连判断（Round 2，可选）
执行时：LLM 执行每个步骤（Round 3+）
    每个步骤 = llm.chat(技能描述 + 上一步输出 + 参数)
```

对比 ReAct 中 LLM 的角色：

| 维度 | ReAct | 链驱动 |
|------|-------|--------|
| 每轮调用次数 | 3-20+ 次 LLM 调用 | 1 次 LLM 调用 / 步骤 |
| 决策负担 | LLM 决定调用什么工具 | 编排器决定，LLM 只执行 |
| 输出不确定性 | 高（路径 + 参数 + 格式） | 低（只需输出结果） |
| 超时风险 | 高（ReAct 循环可能死循环） | 可控（每步有超时配置） |

### 3.4 skill-sub 优化（可选层）

skill-sub 不是 ReAct 中的自由优化，而是算法主导的链分析：

```
1. 读 SKILL.md → 提取 tags/triggers/description
2. 算法比较步骤间输入输出兼容性
   - 分析类→生成类：不兼容，插入转换步骤
   - 数据类→图表类：兼容，直接传递
3. LLM 模糊回退（仅当算法无法确定时）
4. 自动标记里程碑（"完成/结果/报告"等关键词）
```

## 四、这套机制为什么能工作

### 4.1 确定性取代概率性

| 特性 | ReAct 循环 | 链驱动 |
|------|-----------|--------|
| **执行路径** | LLM 运行时决定 | 编排时静态确定 |
| **步骤数** | 不确定（3-20+） | 确定的 N 步 |
| **技能调用** | LLM 自主选择 | 预编排的固定序列 |
| **输出格式** | 需要 JSON 解析 | 自然语言直接输出 |
| **审计** | 需要分析 LLM 推理轨迹 | 链 + 每步输出即可还原 |

### 4.2 本地部署的实践优势

| 因素 | ReAct | 链驱动 |
|------|-------|--------|
| **LLM 调用次数** | 多（3-20+/次任务） | 少（N 步 = N 次调用） |
| **单次调用耗时** | 短（简单思考） | 长（需要生成完整输出） |
| **总耗时** | 不确定（循环次数波动） | 可预估（N × 平均步时） |
| **超时可配置** | 困难的（循环内嵌套循环） | 简单（每步独立超时） |
| **LLM 失联** | 整个对话不可用 | 步级失败隔离 |

### 4.3 配置驱动的适应性

超时和 max_tokens 从配置读取（不是硬编码）：

```
配置页 → llm.timeout（默认 180 秒，可调至 1800）
       → llm.max_tokens（默认 4096，可调至 131072）
```

每步执行从配置读取上述值，用户可根据模型速度自行调节。

## 五、这套方案的代价与边界

### 5.1 代价：以灵活性换取确定性

| 代价维度 | 具体表现 | 与 ReAct 对比 |
|---------|---------|--------------|
| **编排负担** | 用户需要先在 Pipeline 编辑器中编排技能链 | ReAct 零配置，LLM 自己决定 |
| **技能必须预装** | 链中引用的技能必须已安装并在扫描路径中 | ReAct 中 LLM 可选任意可用工具 |
| **步骤间耦合** | 前一步输出格式必须能被下一步理解 | ReAct 中 LLM 自己处理格式转换 |
| **缺乏应急路径** | 链是线性执行，没有异常分支 | ReAct 中 LLM 发现工具不可用会换方案 |
| **不支持自由对话** | 没有选链就无法对话 | ReAct 天然支持问答 |

换一种更直白的说法：

> **ReAct 是"先走再看"——灵活但路径不可控。链驱动是"先看再走"——路径确定但缺乏应变。前者适合探索型任务，后者适合已知流程的自动化执行。**

### 5.2 边界：适用场景与不适用场景

| 适合 | 不适合 |
|------|--------|
| 多技能协作的固定流程（数据采集→分析→报告） | 开放式探索（"帮我查一下最近的 AI 新闻"） |
| 需要可复现、可审计的流水线执行 | 需要 LLM 自主判断路径的场景 |
| 已知技能链的批量处理 | 单次简单问答（用不到链） |
| 并行/循环加速的数据处理 | 需要动态调整执行顺序的场景 |

### 5.3 已知局限

| 局限 | 说明 | 缓解措施 |
|------|------|---------|
| **链执行不兼容 ReAct** | 链中每步用 `llm.chat()` 而非 `agent.run()` | ReAct 作为无链时的回退（极少使用） |
| **并行线程安全问题** | ThreadPoolExecutor 中多个 llm.chat() 同时调用 | LM Studio 等本地 LLM 后端需支持并发 |
| **黏连点需要 LLM 确认** | 算法无法确定的兼容性仍需 LLM 回退 | 限制 LLM 回退调用次数（≤1 次/链） |
| **无跨链状态共享** | 每条 Pipeline 独立执行，不共享中间结果 | 通过文件 I/O 或参数传递间接实现 |

## 六、这套方案沉淀了什么

### 6.1 可复用的模式

1. **链驱动执行模式** — Pipeline 是主体，LLM 是执行器，替换 ReAct 自由对话
2. **三阶段编排模式** — 需求分析 → (优化) → 逐步执行，每轮独立展示
3. **真并行/真循环执行模式** — par 用 ThreadPoolExecutor，loop 用 for
4. **算法主导的 skill-sub 优化模式** — 读 SKILL.md → 标签匹配 → LLM 仅回退
5. **配置驱动的超时/容量控制模式** — timeout 和 max_tokens 从配置读取，可调

### 6.2 关键教训

| 教训 | 场景 | 结论 |
|------|------|------|
| **不要在链步骤中用 agent.run()** | 每步走 ReAct 循环导致死循环/超时 | 每步直接 `llm.chat()`，不做工具决策 |
| **不要特化智能体身份** | prompt 中写"你是 WorkBuddy" | 删除所有身份描述，只描述任务 |
| **LLM 不可用时不回退** | 无 LLM 时返回文字模拟 | 直接抛异常，没有 LLM 不执行 |
| **链必须有技能列表** | 空链还执行是浪费 | 空链直接返回错误 |

### 6.3 与其他方法论文章的关联

| 本体系的其他文章 | 关联点 |
|-----------------|--------|
| **第一篇：硬约束架构** | 每步独立 llm.chat() 是步骤原子化 + 硬中断的实现 |
| **第二篇：构建时契约** | Pipeline 节点中的 params/extra 是 L4 接口声明的体现 |
| **第三篇：递归自举** | 链驱动架构文档自身应可用 Orchestrator 验证 |
| **第四篇：编排范式** | 链驱动是编排范式的工程实现——技能是积木，编排是图纸 |
| **第五篇：领域智能体** | RAG Assistant 可作为链中的一个技能节点被编排 |

## 附录：这套方法论可以怎么迁移

### A. 其他编排场景

本模式的本质是：**预定义技能链 + 逐步骤 LLM 执行 + 步骤间数据传递**。可迁移到：

- **数据采集流水线**：爬取→清洗→分析→报告，每个步骤一个技能
- **文档生成流水线**：搜索→大纲→初稿→校对→发布，串行执行
- **质量检测流水线**：（并行检测 A || 检测 B）→ 汇总报告，并行加速

### B. 与第四篇的关系

本篇文章是第四篇（编排范式）的**工程实现文档**。第四篇是方法论的理论阐述，本文是具体代码架构。两者构成了编排方法的完整闭环：

```
第四篇：编排范式（理论） → 提出"LLM 是胶水"
    ↓ 工程实现
Orchestrator（链驱动执行） → 实现"链是主体，LLM 是执行器"
    ↓ 方法论文档
本文（架构范式） → 沉淀编排范式在工程中的实践经验
```

### C. 链驱动模式的通用化

链驱动执行是一个通用模式，适用于任何需要将多个 LLM 技能组合为确定流程的场景：

```
编排链 → 遍历步骤 → 执行（llm.chat） → 传递输出 → 下一轮
```

这个模式在第四篇中被系统化描述，Orchestrator 是它的一个具体实现案例。
