# 反模式（Anti-Patterns）

> 本文件收录 skill 编写过程中的常见反模式，帮助 AI 和开发者避开典型坑点。
> 每个反模式均含：错误做法 → 正确做法 → 深层原因。

## 结构设计反模式

### AP-01：在 SKILL.md 正文中写大量详细教程

**错误做法：**
```markdown
## 详细教程
### 步骤一：安装依赖
...（50行）
### 步骤二：配置环境
...（80行）
```
正确做法：
教程类内容拆分到 `references/guide.md`，主文件只留摘要 + 引用：
```markdown
## 快速开始
\```bash
python -m scripts.skill_audit create my-skill --confirmed --mode create
\```
→ 详细教程见 `references/guide.md`（按需加载）
```

**深层原因：** 渐进式加载的核心原则是 `SKILL.md ≤ 230 行`。详细教程通常远超此限制，必须拆分。

---

### AP-02：根目录散落文件（未做三级复杂度归类）

**错误做法：**
```
my-skill/
├── SKILL.md
├── _meta.json
├── helper.py        ← 散落在根目录
├── examples.md      ← 散落在根目录
└── config.json      ← 散落在根目录
```

**正确做法：**
```
my-skill/
├── SKILL.md
├── _meta.json
├── scripts/
│   └── helper.py
├── references/
│   └── examples.md
└── assets/
    └── config.json
```

**深层原因：** 三级复杂度（minimal/standard/full）是 skill 可维护性的基础。根目录只保留 `SKILL.md` + `_meta.json`。

---

### AP-03：Frontmatter 字段缺失或格式错误

**错误做法：**
```yaml
---
name: my-skill
# 缺少 version、description
---
```

**正确做法：**
```yaml
---
name: my-skill
version: 1.0.0
description: 简短描述本 skill 的核心功能
---
```

**深层原因：** `name`、`version`、`description` 是 R-01~R-26 强制检查的字段，缺失会导致审查不通过。

## 触发词反模式

### AP-04：触发词过于宽泛导致误触发

**错误做法：**
```yaml
# 触发场景
- "画图"
- "帮我"
```

**正确做法：**
```yaml
# 触发场景
- "使用 drawio 画流程图"
- "生成架构图"
```

**深层原因：** 触发词须含具体动作或对象（R-07 检查）。过于宽泛的触发词会导致 skill 在无关场景下被错误加载。

---

### AP-05：缺少否定条件，导致过度触发

**错误做法：**
```yaml
# 触发场景
- "生成图表"
# 缺少否定条件
```

**正确做法：**
```yaml
# 触发场景
- "使用 drawio 生成图表"
- **否定条件**：除非用户明确提到其他工具（如 mermaid、plantuml），否则优先使用本 skill
```

**深层原因：** 否定条件（R-07 检查）是防止 skill 误触发的关键机制。没有否定条件，多个相似 skill 会同时被触发。

## 渐进式加载反模式

### AP-06：SKILL.md 超过 230 行且不拆分

**错误做法：**
`SKILL.md` 有 400 行，所有内容都堆在主文件里，不引用任何 `references/` 文件。

**正确做法：**
1. 识别可独立成文档的大段落（详细教程、大量示例、FAQ）
2. 在 `SKILL.md` 中保留摘要 + 引用语法指向 `references/`
3. 将详细内容移入对应 `.md` 文件

**深层原因：** `SKILL.md` 是 AI 加载 skill 的入口，必须快速可理解。超过 230 行会拖慢加载速度，也违反渐进式加载规范。

---

### AP-07：渐进式文件存在但 SKILL.md 没有引用

**错误做法：**
```
my-skill/
├── SKILL.md        ← 没有任何引用 references/ 的语句
└── references/
    └── guide.md   ← 存在但永远不会被加载
```

**正确做法：**
在 `SKILL.md` 里添加引用：
```markdown
→ 详细教程见 `references/guide.md`（按需加载）
```

**深层原因：** 渐进式文件的设计初衷是"按需加载"。如果 `SKILL.md` 没有引用，AI 不会知道这些文件的存在，也就不会加载它们。

## 审查规则反模式

### AP-08：R-07 触发词检查只检查章节存在性，不检查质量

**错误做法：**
R-07 只检查 `## 触发场景` 章节是否存在，不检查触发词是否具体、是否有否定条件。

**正确做法：**
R-07 应检查：
1. 章节存在
2. 正向触发词 ≥ 3 个
3. 每个触发词含具体动作或对象（不应过于宽泛）
4. 有否定条件 ≥ 1 个

**深层原因：** 只检查章节存在性是不够的。一个只有"帮我"、"生成"这样宽泛触发词的 skill，会严重误触发。

---

### AP-09：审查规则 FAIL 但不提供修复建议

**错误做法：**
```
R-07: FAIL
  触发场景章节存在性: PASS
  正向触发词数量: FAIL (仅1个，要求≥3)
  # 没有修复建议
```

**正确做法：**
```
R-07: FAIL
  触发场景章节存在性: PASS
  正向触发词数量: FAIL (仅1个，要求≥3)
  建议: 在 ## 触发场景 章节添加更多触发词，例如：
    - "使用 <skill-name> 执行 <具体任务>"
    - "按照 <skill-name> 规范进行 <具体操作>"
```

**深层原因：** 审查的目的是帮助修复，而不仅仅是报告问题。没有修复建议的 FAIL 报告对开发者帮助有限。

## 版本管理反模式

### AP-10：SKILL.md 和 _meta.json 版本号不一致

**错误做法：**
```yaml
# SKILL.md frontmatter
version: 2.0.0
```
```json
// _meta.json
{"version": "1.9.0"}
```

**正确做法：**
```yaml
# SKILL.md frontmatter
version: 2.0.0
```
```json
// _meta.json
{"version": "2.0.0"}
```

**深层原因：** R-10 强制检查 `SKILL.md version == _meta.json version`。不一致会导致审查失败，也会让用户困惑哪个是正确版本。

---

### AP-11：版本号升级没有遵循 SemVer 规范

**错误做法：**
- 加了新功能，版本号从 `2.0.0` → `2.0.1`（应为 `2.1.0`，minor 递增）
- 做了不兼容的更新，版本号从 `2.0.0` → `2.1.0`（应为 `3.0.0`，major 递增）

**正确做法：**
| 更新类型 | 示例 | SemVer 规范 |
|---------|------|------------|
| Patch（补丁） | Bug 修复，无功能变化 | `2.0.0` → `2.0.1` |
| Minor（次版） | 新增向后兼容的功能 | `2.0.0` → `2.1.0` |
| Major（主版） | 不兼容的重大更新 | `2.0.0` → `3.0.0` |

**深层原因：** SemVer 是生态系统版本管理的通用语言。遵循 SemVer 让用户能预判版本升级的影响范围。

## 排错与止损反模式

### AP-12：把审计工具的警告当成被审计技能的 bug 来"修复"

**错误做法：**
审计输出里出现 `SyntaxWarning: invalid escape sequence '\Z'`，于是：
1. 去被审计技能的 `.py` 文件里搜索 `\Z`（用 Grep，默认正则模式）
2. 搜不到 → 换各种参数继续搜
3. 搜到后"修复" → 实际上修错了地方
4. 反复循环，什么都不奏效

**正确做法：**
1. **先定位警告来源**：警告是哪一行的代码触发的？是 `structure_checker.py` 的 `compile()` 调用，还是被审计文件里的字面 `\Z`？
2. **区分"审计工具的问题"和"被审计技能的问题"**：
   - 若警告来自审计工具自身（如 `compile()` 触发 `SyntaxWarning`）→ 修审计工具
   - 若警告来自被审计文件 → 修被审计文件
3. **搜索字面反斜杠用 `grep -F` 或 `Grep glob`**：`\Z` 在正则里是"字符串结尾"元字符，普通 Grep 永远搜不到字面 `\Z`，必须用 `-F`（fixed string）模式

**深层原因：** 审计输出里的警告有两种来源——审计工具自身的问题，或被审计技能的真实问题。不分清来源就动手"修复"，必然走偏。

---
### AP-13：同一失败模式重复尝试 ≥3 次不换思路

**错误做法：**
- 用 `Grep pattern='\Z'` 搜不到 → 再试一次同样的 Grep
- 用 `compile()` 触发警告 → 加 `warnings.catch_warnings()` 但拼错函数名 → 再试一次同样的错误拼写
- 重复同样的工具调用，期望不同结果

**正确做法：**
当同一工具调用连续失败 ≥2 次时，强制停止并切换思路：
1. 读工具的真实输出（完整 stderr，不只是摘要）
2. 问自己：我对这个工具的理解对吗？（如：`\Z` 在 Grep 里是正则元字符，不是字面字符）
3. 换工具或换角度（Grep 搜不到 → 用 `python -c "open(f).read()"` 直接看文件内容）
4. 若 3 种不同思路都失败 → 向用户说明情况并请求澄清，而不是继续空转

**止损触发条件（AI 自查清单）：**
- [ ] 同一操作失败 ≥2 次 → 停止，换思路
- [ ] 用户说了"又停了"/"死循环"/"你在干什么" → 立即停止当前操作，向用户说明当前状态和下一步计划
- [ ] 超过 5 轮对话还没有实质性进展 → 向用户承认困境并请求指引

## 总结

| ID | 反模式 | 影响级别 |
|----|--------|---------|
| AP-01 | 在 SKILL.md 写大量详细教程 | 🔴 高（违反渐进式加载） |
| AP-02 | 根目录散落文件 | 🔴 高（结构混乱） |
| AP-03 | Frontmatter 字段缺失 | 🔴 高（审查失败） |
| AP-04 | 触发词过于宽泛 | 🟡 中（误触发） |
| AP-05 | 缺少否定条件 | 🟡 中（过度触发） |
| AP-06 | SKILL.md 超过 230 行 | 🔴 高（加载慢） |
| AP-07 | 渐进式文件存在但无引用 | 🟡 中（文件不会被加载） |
| AP-08 | R-07 只检查章节存在性 | 🟡 中（质量无保障） |
| AP-09 | 审查 FAIL 无修复建议 | 🟢 低（体验差） |
| AP-10 | 版本号不一致 | 🔴 高（审查失败） |
| AP-11 | 版本号不遵循 SemVer | 🟡 中（生态混乱） |
| AP-12 | 把审计工具警告当被审计技能 bug | 🔴 高（修错地方 + 空转） |
| AP-13 | 同一失败模式重复尝试不换思路 | 🔴 高（死循环） |
