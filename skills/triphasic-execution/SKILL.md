# Triphasic Execution Framework v5.7

执行 → 审查 → 推进。每次交互只做一件事，三者缺一不可。

---

## ⚠️ 监控能力边界（重要说明）

### 全局模式 vs 临时调用

| 功能 | 全局模式（Global） | 临时调用（按需） |
|------|-------------------|-----------------|
| **问题记录** | ✅ 自动（Shell 命令失败/中断） | ✅ 任务结束后强制执行 |
| **风险记录** | ✅ 自动（Shell 命令异常） | ✅ 任务规划时强制执行 |
| **经验积累** | ❌ 手动调用 merge-to-lessons | ❌ 手动调用 merge-to-lessons |

### 全局模式的实际覆盖率

> **✅ 全局模式可以监控**：通过 `exec_wrapper.py` 执行的 **Shell 命令**。

- ✅ **能自动记录**：
  - Shell 命令执行失败（退出码非零）
  - Shell 命令被中断（Ctrl+C / SIGTERM）
  - Shell 输出中匹配错误模式的文本

- ❌ **无法自动记录**：
  - Read/Write/Edit 等直接工具调用
  - ToolSearch/DeferExecuteTool 等 API 调用
  - AI 推理错误、幻觉
  - 逻辑错误（命令成功执行但结果错误）

**实际覆盖率**：约 **30-40%**（仅 Shell 命令部分）

### 临时调用的实际行为

> **⚠️ 重要**：临时调用模式下，记录是**任务结束后的强制步骤**，不是可选的。

- ✅ **任务结束后强制记录**：
  - 识别问题 → 必须调用 `add`
  - 识别风险 → 必须调用 `add-risk`
  - 任务完成 → 必须调用 `merge-to-lessons`

- ✅ **用户触发时必须执行**：
  - 用户说"记录问题" → 立即调用 `add`
  - 用户说"记录风险" → 立即调用 `add-risk`
  - 用户说"总结经验" → 立即调用 `merge-to-lessons`

## 问题、风险、经验调用方式

### 1. 问题记录（Problem Logging）

**触发时机**：任务执行过程中发现错误/异常时

```bash
# 标准调用
python {SKILL_DIR}/scripts/problem_logger.py add \
  --scene "API测试" \
  --symptom "HTTP 503" \
  --cause "服务端限流" \
  --solution "增加重试机制" \
  --task "用户头像接口"

# 最小调用（仅必填项）
python {SKILL_DIR}/scripts/problem_logger.py add \
  --scene "文件读取" \
  --symptom "FileNotFoundError"
```

### 2. 风险记录（Risk Logging）

**触发时机**：任务规划（Phase 1）时识别到潜在风险

```bash
# 标准调用
python {SKILL_DIR}/scripts/problem_logger.py add-risk \
  --description "网络不稳定可能导致API调用失败" \
  --impact "用户体验下降，转化率降低" \
  --mitigation "增加重试机制和降级策略" \
  --task "用户头像接口"

# 最小调用（仅必填项）
python {SKILL_DIR}/scripts/problem_logger.py add-risk \
  --description "第三方服务可能宕机"
```

### 3. 经验积累（Lessons Learned）

**触发时机**：任务完成后或定期（如每天/每周）

```bash
# 合并问题清单和风险手册到经验教训登记册
python {SKILL_DIR}/scripts/problem_logger.py merge-to-lessons

# 查看统计
python {SKILL_DIR}/scripts/lessons_register.py stats
```

当用户触发记录时，AI应执行以下流程：

```
### 📋 任务后记录

**问题记录**：
python {SKILL_DIR}/scripts/problem_logger.py add \
  --scene "任务执行" \
  --symptom "错误描述" \

```

### 强制记录规则

> **⚠️ 重要**：每次任务执行完成后，AI必须执行以下记录步骤：
>
> 1. **任务结束时自动记录**（强制，非可选）：
>    - 回顾执行过程，识别问题 → 调用 `add`
>    - 回顾执行过程，识别风险 → 调用 `add-risk`
>    - 执行完成后 → 调用 `merge-to-lessons`
>
> 2. **用户触发时记录**（必须执行）：
>    - 用户说"记录问题" → 立即调用 `add`
>    - 用户说"记录风险" → 立即调用 `add-risk`
>    - 用户说"总结经验" → 立即调用 `merge-to-lessons`
>
> 3. **定时任务触发时记录**（必须执行）：
>    - 定时任务完成后推送摘要，用户回复"有问题要记录"
>    - 用户主动触发"审查刚才的定时任务"

### 再次呼出设置界面

**方式 1：通过 Agent 对话（推荐）**
- 向 Agent 发送："打开 triphasic 设置"、"修改配置"、"打开设置界面"

  1. 运行 `python {SKILL_DIR}/scripts/settings.py --serve-only`，解析输出中的 `SERVER_STARTED:<port>`

（脚本会自动启动服务器、打开浏览器、阻塞等待设置完成）

## 双模式设计（v4.1 核心更新）

### 核心理念：用户习惯决定启动方式
> **当前配置：🟢 按需调用模式（默认）**

| 维度 | 按需调用模式（默认） | 全局自动模式（可选） |
|---|---|---|
| **触发条件** | 用户主动加载技能 | 配置 `mode: global` + 启动 daemon |
| **记录行为** | 调用时才记录三步框架 | 所有任务自动应用三步框架 |
| **后台守护** | 不启动 daemon | `problem_daemon.py` 持续监控 |
| **异常捕获** | 靠 Agent 主动调用 CLI 命令记录 | 自动捕获 + 写入 PROBLEMS.md |
| **适用场景** | 日常简单任务、跨平台协作 | 复杂多步骤项目、长期维护 |

### 按需调用模式（默认，符合"不调用就不记录"习惯）

用户主动加载技能后，Agent 遵循三步框架，通过 CLI 命令手动记录问题。

### 全局自动模式（可选，适合长期项目）

```bash
# 安装时选择 global 模式
python install.py --mode global

# 启动守护进程（仅一次）
python problem_daemon.py start

# 此后所有命令异常 → 自动捕获 → 自动写入 PROBLEMS.md
```

注意：daemon 不自启，必须手动 `problem_daemon.py start`。

## 核心规则

### Phase 1 -- 执行 (EXECUTE)
- 执行前**重述任务目的**，确认当前步骤要达成什么
- 实际运行命令、调用工具、测试代码
- 只跑一个主要命令（可并行多个独立命令）
- 不提前分析结果，不跳到审查阶段

### Phase 2 -- 审查 (REVIEW)
- 分析执行结果，对照**任务目的**给出明确判断：✅成功 / ❌失败 / ⚠️部分
- 列出具体证据（数据、错误码、状态）
- 不执行新操作

### Phase 3 -- 推进 (ADVANCE)
- 基于审查结论决定下一步
- 明确：继续 / 换方向 / 结束 / 向上返回
- **更新进度追踪表**，标记当前步骤状态
- 不直接执行，只规划

## 临时进度文件机制（v5.6 核心更新）

### 为什么需要临时进度文件

> **问题**：任务执行中途意外中断（会话超时、网络断开、AI 重启）后，进度全部丢失，重新执行时不知道从哪里继续。

> **解决方案**：任务规划后立即创建临时进度文件，每步执行后更新，任务完成后删除。中断后读取文件即可恢复。

### 核心原理

```
任务规划
  └─→ 创建临时进度文件（init）
         │
         ├─ 步骤1 执行 → 更新文件（update）
         ├─ 步骤2 执行 → 更新文件（update）
         ├─ 步骤3 执行 → 更新文件（update）
         │   ...
         │
         └─ 任务完成 → 删除进度文件（complete）
             中断/异常 → 保留文件，下次 resume 恢复
```

### 文件路径与命名

| 项目 | 说明 |
|------|------|
| **目录** | `TRIPHASIC_HOME/.active_tasks/` |
| **命名** | `{任务名}_{时间戳}.json` |
| **编码** | UTF-8 |
| **格式** | JSON（机器可读）+ 配套 Markdown 摘要（人类可读） |

例：`修复登录Bug_20260518_195030.json`

### 生命周期

| 阶段 | 命令 | 调用时机 | 文件状态 |
|------|------|---------|---------|
| 创建 | `init` | 任务规划后，执行前 | 新建文件，状态 `active` |
| 更新 | `update` | 每步 Execute→Review→Advance 后 | 更新对应步骤状态 |
| 恢复 | `resume` | 中断后、用户问"继续上次任务" | 读取文件，输出恢复信息 |
| 完成 | `complete` | 所有步骤成功，任务结束 | 删除文件 |
| 中止 | `abort` | 用户取消任务 | 标记 `aborted`，保留文件 |
| 清理 | `clean` | 定期维护 | 删除 `completed`/`aborted` 状态文件 |

### AI 调用时机（强制执行）

| 时机 | 必须调用的命令 | 说明 |
|------|----------------|------|
| 任务规划输出后、执行前 | `init` | 创建进度文件，记录规划和步骤 |
| 每个步骤 Execute 开始前 | `update --step N --status running` | 标记步骤为执行中 |
| 每个步骤 Review 后 | `update --step N --status success/failed --review "..."` | 更新审查结论 |
| 每个步骤 Advance 后 | `update --step N --advance "..."` | 更新推进决策 |
| 任务全部完成后 | `complete` | 删除进度文件 |
| 用户说"继续"、"恢复"、"刚才做到哪了" | `resume` | 读取进度文件，输出恢复信息 |
| 用户说"取消任务"、"停止" | `abort --reason "..."` | 标记中止，保留文件备查 |

### 命令速查


## 任务规划与拆分（v5.5 核心更新）

### 核心原则：规划必做，拆分看规模

> **⚠️ 关键区分（v5.5 强制）**：
> - **任务规划**：**所有任务必须执行**，无论大小。规划 = 明确任务目的、要求、工具、预期结果。
> - **任务拆分**：**仅大任务执行**（3步以上）。拆分 = 将大任务分解为多个子步骤。
>
> **判断标准**：如果任务可以一步完成（如读一个文件、执行一个命令），仍需规划但不需拆分。

### 判断流程

```
收到任务
  │
  ├─ 第一步：任务规划（必做，所有任务）
  │   → 明确：任务目的、具体要求、使用工具、预期结果、潜在风险
  │
  ├─ 第二步：判断是否需要拆分
  │   ├─ 单步任务（1个操作可完成）→ 直接进入执行
  │   └─ 多步任务（2个以上操作）→ 任务拆分，列出子步骤
  │
  └─ 第三步：进入 Execute→Review→Advance 循环
```

### 一、任务规划模板（所有任务必做）

每个任务（无论大小）开始前，**必须**输出以下规划：


### 七、用户跳过机制

- **默认行为**：问题/风险/经验记录是强制步骤

- **不跳过**：按步骤1执行，任务结束后强制执行三个记录步骤

## 循环规则

1. **规划先行** = 所有任务必须先输出任务规划，明确目的和要求
2. **临时文件持久化** = 规划后立即创建进度文件（init），每步更新（update），完成删除（complete）
3. **最小单元** = 单次工具调用，每步必须立即审查+推进
4. **最多 3 次重试** -- 3 次失败后必须换方案或向上回溯
5. **大任务才拆分** -- 3步以上任务输出步骤列表；单步任务只做规划不拆分
6. **每步更新进度** -- 执行后更新进度文件和进度追踪表
7. **完成后必须输出总结** -- 目标/结果/关键发现/异常记录，不可静默消失
8. **中断可恢复** -- 进度文件保留，重启后 resume 恢复

## 禁止行为

- ❌ 不做规划直接执行（无论任务大小）
- ❌ 不创建临时进度文件（规划后必须 init）
- ❌ 每步执行后不更新进度文件（必须 update）
- ❌ 任务完成后不删除进度文件（必须 complete）
- ❌ 连续执行不审查
- ❌ 只审查不推进
- ❌ 同一操作重复 3 次以上无策略调整
- ❌ 任务完成后不输出总结
- ❌ 遇到问题硬跑不换思路
- ❌ 步骤执行前不重述任务目的
- ❌ 执行后不更新进度追踪表

## 两种调用方式

### 方式 1：直接调用（Skill 模式，推荐）

Agent 加载本技能后，遵循三步框架。问题由 Agent 通过 `problem_logger.py` 自主记录。

```bash
# 初始化数据目录（首次使用）
python {SKILL_DIR}/scripts/problem_logger.py init

# 记录问题（任务执行中发现错误时）
python {SKILL_DIR}/scripts/problem_logger.py add \
  --scene "API测试" --symptom "HTTP 503" \
  --cause "服务端限流" --solution "增加重试机制"

# 记录风险（任务规划时识别到潜在风险）
python {SKILL_DIR}/scripts/problem_logger.py add-risk \
  --description "网络不稳定可能导致API调用失败" \
  --impact "用户体验下降" \
  --mitigation "增加重试机制"

# 搜索历史问题（执行前检索，避免重复踩坑）
python {SKILL_DIR}/scripts/problem_logger.py search "503"

# 列出最近问题
python {SKILL_DIR}/scripts/problem_logger.py list --recent 10

# 更新问题（补充原因/解决路径）
python {SKILL_DIR}/scripts/problem_logger.py update --id P001 --cause "xxx" --solution "yyy"

# 生成经验教训登记册（任务完成后或定时调用）
python {SKILL_DIR}/scripts/problem_logger.py merge-to-lessons
```

### 方式 2：注册为 exec 全局管理（Wrapper 模式）

自动拦截所有 shell 命令，后台 daemon 实时监控异常。

```bash
# 启动后台监控守护进程
python {SKILL_DIR}/scripts/problem_daemon.py start

# 查看守护进程状态
python {SKILL_DIR}/scripts/problem_daemon.py status

# 停止守护进程
python {SKILL_DIR}/scripts/problem_daemon.py stop

# 使用 exec_wrapper 拦截命令
python {SKILL_DIR}/scripts/exec_wrapper.py "your command here"
```

**全局注册（可选）：**

```bash
# Linux/Mac (.bashrc / .zshrc):
export TRIPHASIC_HOME=~/.workbuddy/triphasic
alias exec="python3 {SKILL_DIR}/scripts/exec_wrapper.py"

# Windows (PowerShell Profile):
```

## 脚本清单（v5.6 更新）

| 脚本 | 功能 | 依赖 |
|------|------|------|
| `install.py` | 安装/卸载（支持 --mode --target --home） | 无 |
| `settings.py` | HTML 设置界面（v5.0 新增） | 无 |
| `problem_logger.py` | 问题/风险 CRUD + 合并登记册（add/add-risk/list/search/update/merge-to-lessons） | 无 |
| `exec_wrapper.py` | 命令执行拦截器 | 无 |

| `lessons_register.py` | 登记册管理（generate/diff/stats） | 无 |
